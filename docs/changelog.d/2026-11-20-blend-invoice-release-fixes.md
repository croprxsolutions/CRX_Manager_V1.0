## 2026-11-20 — Blend-ticket invoice: three #1990 release fixes

- From the #1990 apply review and final Sol (round 53, Mason 2026-11-20). New migration `20270129190000_blend_invoice_release_fixes.sql` re-emits two functions from `20270129180000`, each changed only as below:
  - **Actor error** (rls-security-reviewer CHECK 5): `create_invoice_from_blend_ticket` raises the charter token `ACTOR_MISMATCH` instead of `p_created_by does not match authenticated user`. The app already reads it here (`src/lib/blendTicketPricing.ts`), and no screen depends on the old text.
  - **Two bills for one job at once** (Sol r53 #4): under REPEATABLE READ, two transactions billing different tickets for the same job could both commit, because the second's snapshot predated the first invoice. The function now runs only under READ COMMITTED (READ UNCOMMITTED behaves the same in PostgreSQL) and refuses REPEATABLE READ and SERIALIZABLE (`BLEND_INVOICE_NEEDS_READ_COMMITTED`), as the booking guard does (`20270129150000`). The app runs READ COMMITTED, where the job-row lock serializes the two bills.
  - **Billed ticket keeps its job** (Sol r53 #3): the trigger `_blend_ticket_billed_keeps_job_20270129` trusted `payment_status` only. A ticket marked unbilled while its invoice was still live could move to another job, and billing a second ticket for the first job would miss that invoice. It now also holds the job while any live invoice (not voided or cancelled, not deleted) points at the ticket. It runs SECURITY DEFINER (owner postgres, no grants), so that check sees every invoice whatever the updater's own invoice access is.
- Proof: a local synthetic DB, with staging migrations up to `20270129180000` applied inside one rolled-back transaction, then this file.
  - A call whose `p_created_by` is not the signed-in user fails with `ACTOR_MISMATCH`.
  - X1: a billed ticket marked unbilled with its invoice still live moves to another job before this file and is refused after it (`BLEND_TICKET_BILLED_JOB_LOCKED`). With no live invoice left, it can move.
  - RR: a blend ticket bills inside REPEATABLE READ before this file and is refused after it. READ COMMITTED billing is unchanged.
  - Every blend and field-app scenario from #2053 (R1–R8, M1–M9 and the KI-81 unit scenarios) gives the same result as before this file; only generated ids differ.
  - The postflight passes: the new bodies; the blend function's security mode, volatility, search_path, owner and grants as before; the trigger function postgres-owned, SECURITY DEFINER, no grants; the trigger still BEFORE UPDATE OF job_id FOR EACH ROW. A second apply stops at the preflight, and so does a function whose security settings drifted.
