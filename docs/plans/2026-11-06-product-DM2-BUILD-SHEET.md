# DM-2 build sheet: weight per gallon and dry net weight

**Status: PLAN, 2026-11-06. NOT STARTED.** This is DM-2's own build-sheet section, required by `docs/plans/2026-11-04-product-stage2-BUILD-SHEET.md` section 7 ("before any of these packages is built, it gets its own full build-sheet section and its own Sol review against PAR-1 and PAR-2 as built"). It replaces that sheet's outline (section 7.1) and settles DM-2's row in its section 7.8. Words (parent, size, copied value, pass, retry key, harness) mean what they mean there. The Stage 2 sheet's section 3 rules all apply; this sheet names only where DM-2 adds to them. The review record is section 9.

**Goal.** Store how much a liquid weighs per gallon (one value per formulation) and how much one package of a dry product weighs, each reviewed before use, and show the crew the weight where they mix: the job's loader worksheet and the blend ticket. Fix the blend checker so a dry blend with liquid parts is a checked total (C-39). No saved record changes.

## 2. Corrections to the Stage 2 outline (section 7.1 and 7.8), from current code

1. **Nothing to group yet.** The outline assumed parents would exist; live has 0, and PAR-2's grouping switch is off. DM-2's mechanism can ship now; real weights wait for PAR-2's data step. Until a liquid size has a parent it shows "put this product in a parent to record its weight", as the outline said.
2. **No dry product needs a stored net weight today.** All 83 active dry products are stocked in a weight unit. The stored net-weight table is still built (a new dry product may be stocked in `Ea` or `Unit`), but its live use starts at zero, and DATA-4's dry list is empty unless such a product is added.
3. **Weight units are `Lb`/`LB`, `Dry oz`, `g` and `MG`**, read from `unit_conversions` (`unit_type = 'dry'`), not "lb, oz, kg". `oz` and `Oz` are fluid ounces in this database (`unit_type = 'liquid'`); DM-2 never treats them as weight. The app's existing converter (`fieldAppPricedQuantity`, `chemCalculator.ts:471-503`) lower-cases units, reads `oz` as a weight ounce for dry, and does not know `g` or `MG`, so DM-2 does **not** use it for weight; it uses the database's own factors (section 4.1).
4. **A count unit is `Ea` or `Unit`** (`unit_type = 'both'`). The outline's "bag, box" are container types, not stock units; no stock unit is called bag or box.
5. **The snapshot cannot ride on "the ticket's save RPC".** Three RPCs write ticket lines (`create_blend_ticket`, `save_blend_ticket`, `commit_blend_ticket_ocr_result`, the last called by the `process-blend-ticket` Edge Function), and `authenticated` still holds column `INSERT`/`UPDATE` grants with RLS write policies, so a direct API write is possible even though no screen makes one (section 3.4). So the snapshot is taken by a trigger at the line boundary, which catches every writer, as section 7.8's direction says.
6. **Key the snapshot by ticket and product, not by line.** `commit_blend_ticket_ocr_result` deletes the lines nobody corrected and re-inserts them; `save_blend_ticket` deletes lines missing from the save and inserts new ones. A snapshot keyed by line ID would be lost on those paths and re-taken at today's weight, changing a saved record. Keyed by (`blend_ticket_id`, `product_id`) and written "first time only, never changed", a re-saved, OCR-replaced or re-ordered line keeps the weight its ticket first used.
7. **Saved loader worksheets get their own snapshot, taken when the worksheet is saved** (7.8's round-8 item). `job_loader_worksheets` stores only plan settings and every product amount is recomputed from the job's lines, so there is no line to hang a weight on. DM-2 adds a per-(worksheet, product) snapshot written by a trigger on `job_loader_worksheets` (section 3.4b). The legacy loader (a job with no worksheet row) and the batch (master mix) summary are live views, labelled "current approved weights".
8. **There is no blend-ticket printout.** The outline said the ticket "prints" its weight. No per-ticket PDF exists; the only blend PDF is the ticket list export (`BlendTickets.tsx:200-222`), which has no quantities. The ticket screen shows the saved weight; no printout is added.
9. **The checker cannot check a spray tank with dry parts.** A gallon total with dry rows would need the dry product's volume, which no one records. Only a weight total whose unit is in the unit table (`Lb`/`LB`, `Dry oz`, `g`, `MG`, in any letter case) becomes a checked total, by converting liquid and package rows to pounds and then to the header unit through the database's factors. A `ton` or `kg` header (no row in `unit_conversions`) with liquid rows stays "not checked", with that reason. A spray tank keeps today's one-sided bound; when a `units` map is passed (every DM-2 screen), a non-liquid row now makes the volume total "not checked" instead of being left out quietly (section 4.4).
10. **Seed and each products never have a weight.** The outline did not say. They are refused by name ("weight isn't tracked for seed or each products"), and the checker's existing seed/each notice stays.
11. **The loader worksheet does not know which product a line is.** Its input (`LoaderProductInput`, `loaderWorksheet.ts:31-38`) carries only name, total and unit. The screen PR adds `product_id` and `product_form` to it at its two sources (`loaderWorksheetFetch.ts`: the `job_chemicals` row type `:42`, the query `:65`, the mapping `:173-179`; `JobDetail.tsx:2392-2403`) and through `masterMixSummaryFetch.ts`; the outline's file list missed these.
12. **The outline's file list misses the PDF and fetch files.** `masterMixSummaryData.ts` only builds data; the batch PDF is `masterMixSummaryPdf.ts`, and its inputs come from `masterMixSummaryFetch.ts` and `chemicalApplicationReportFetch.ts`. Section 4 lists the real set.
13. **An admin's typed value is approved, not a draft.** The Stage 2 sheet's section 7 (`:319`) says a value an admin types on the product page is that admin's reviewed entry, and only agent-drafted or uploaded values land as drafts. The outline's "every value is a draft" is narrowed to match: the public setters save an **approved** value with who and when; only DM-1b's workbook (through the private helpers) saves drafts, which an admin then approves (section 3.3).
14. **The admin-RPC write rule has a narrow, named exception.** The Stage 2 sheet's section 3 says new tables are written only through admin-checked RPCs, but its own 7.1 "Unit edits" (a trigger on `products` returns a net weight to draft) and 7.8 (a snapshot "at the `blend_ticket_products` line boundary for every writer") need triggers. So DM-2's snapshot tables, and the return-to-draft and clearing steps, are written only by private `SECURITY DEFINER` trigger functions that take no caller input: they copy or demote an already-approved weight and can never create or approve one (section 3.4). Every value anyone enters still goes through an admin-checked RPC.

## 3. Database PR: migration `<stamp>_product_weights`

### 3.1 New tables

All follow the Stage 2 rule 2 lock-down (the snapshot table's read policy differs, below): RLS on, `SELECT` policy `USING ((SELECT public.is_active_profile()))` to `authenticated`, `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role, metabase_ro`, then `GRANT SELECT … TO authenticated` (the PAR-1 pattern, `20261108120000:184-199`). No write grant to any role. Owner `postgres`.

- **Basis kept with each value** (both value tables): `basis jsonb NOT NULL`, set by every writer when the row is saved, holding what the value depends on: for a density, the parent's `product_form`, `formulation_type` and `safener`; for a net weight, the size's `container_size`, `container_type`, `container_unit`, `inventory_unit` and `unit_size`. It lets a later re-apply find values whose basis changed while the triggers were off (section 3.7).
- **`product_parent_density_values`**: `id uuid` primary key; `parent_id uuid NOT NULL` FK `product_parents(id) ON DELETE RESTRICT`; `lb_per_gal numeric(10,4) NOT NULL CHECK (lb_per_gal > 0 AND lb_per_gal <= 25)`; `entered_value numeric NOT NULL`, `entered_unit text NOT NULL CHECK (entered_unit IN ('lb_per_gal', 'specific_gravity'))`; `source text NOT NULL CHECK (source IN ('measured', 'sds', 'label', 'supplier'))`; `source_note text` (trimmed, ≤ 1000); `review_state text NOT NULL CHECK (review_state IN ('draft', 'approved', 'superseded'))`; `reason`, `evidence` (required on corrections and on a lower-trust draft, section 3.3; NULL otherwise); `created_by`, `created_at`, `reviewed_by`, `reviewed_at`, `superseded_at`. Partial unique indexes: **one `approved` row per parent** and **one `draft` row per parent**.
- **`product_size_net_weight_values`**: the same shape per size: `product_id uuid NOT NULL` FK `products(id) ON DELETE RESTRICT`; `net_lb numeric(12,4) NOT NULL CHECK (net_lb > 0 AND net_lb <= 4000)` (the net pounds of **one stock unit**: one `Ea`, one `Unit`); no `entered_unit` (entered in pounds); the same source, review, who/when columns and the same two partial unique indexes. **The two upper bounds are typo guards, not physics**: farm chemicals run about 7 to 13 lb/gal, so 25 lb/gal (three times water) catches a misplaced decimal or a value typed in the wrong unit; 4,000 lb covers the largest one-unit packs sold (bulk bags and totes are roughly 1,000 to 2,500 lb). A real value past either is refused by name and needs a new migration to widen the check.
- **`product_parent_density_state(parent_id uuid PRIMARY KEY` FK, `density_version bigint NOT NULL)`** and **`product_size_net_weight_state(product_id uuid PRIMARY KEY` FK, `net_weight_version bigint NOT NULL)`**. A missing row means version 0. Every write takes the row (`INSERT … ON CONFLICT DO NOTHING`, then `SELECT … FOR UPDATE`), checks the caller's expected version, and adds one. So two writers on one subject serialize on this row, and a stale screen is refused by name.
- **Review fields on every state change** (both value tables): saved approved by a typed entry or `approve_weights` → `reviewed_by`, `reviewed_at` set to the approver and now; becoming `superseded` → `superseded_at` = now, review fields kept (history); an approved row returned to `draft` by a pack or identity change → `reviewed_by` and `reviewed_at` cleared to NULL (the event keeps who had approved it), so a draft never shows a reviewer. A table `CHECK` enforces it: `review_state = 'approved'` requires both review fields, `'draft'` requires both NULL, `'superseded'` requires `superseded_at`.
- **`product_weight_events`**: append-only (update, delete and truncate refused by trigger, as `product_parent_events`, `20261108120000:201-215`). `id bigint` identity, with its sequence locked down like PAR-1's (`REVOKE ALL ON SEQUENCE … FROM PUBLIC, anon, authenticated, service_role, metabase_ro`, `20261108120000:196`); `subject_kind` in (`parent_density`, `size_net_weight`); `parent_id`, `product_id` (exactly one set, by kind); `event_type` in (`draft_saved`, `draft_replaced`, `approved`, `corrected`, `returned_to_draft`); `value_id`; `before_value jsonb`, `after_value jsonb`; `reason`, `evidence`; `actor_kind text NOT NULL CHECK (actor_kind IN ('user', 'system'))`, `changed_by uuid` and `changed_by_name text` (both **nullable**, unlike `product_parent_events.changed_by`, which is `NOT NULL`, `20261108120000:154`; do not copy that column, or a system-trigger event would fail and roll back the pack edit): `auth.uid()` and `profiles.full_name` when a user is signed in (a profile with no name leaves the name NULL, never an error), or `actor_kind = 'system'` with both NULL when there is none (a service-role, migration or background update reaching the section 3.5 trigger); `changed_at`. Indexes for the history screen: `(parent_id, changed_at DESC, id DESC) WHERE parent_id IS NOT NULL` and `(product_id, changed_at DESC, id DESC) WHERE product_id IS NOT NULL`. Only the section 3.5 triggers and a re-apply's reconciliation (section 3.7) can write a `'system'` event; every RPC requires an admin first.
- **`blend_ticket_product_weights`** (the saved-record snapshot): primary key (`blend_ticket_id`, `product_id`); `blend_ticket_id` FK `blend_tickets(id) ON DELETE CASCADE`; `product_id` FK `products(id) ON DELETE RESTRICT`; `weight_kind` in (`density`, `net_weight`, `unit_weight`, `none`); `value_id uuid` (the density or net-weight row used, null for `unit_weight` and `none`); `lb_per_unit numeric` (unconstrained, so `MG`'s 0.0000022046225 is kept exactly) and `per_unit text` (`Gal` for density; the stock unit for the other two); `unit_factors jsonb NOT NULL` (the `units` map of section 3.2 as it was at capture, 11 keys live after lower-casing, so a later factor change cannot move a saved weight); `source`; `none_reason` (per kind, enforced by a `CHECK`: `density` and `net_weight` have `value_id`, `lb_per_unit`, `per_unit` and the value's `source`, and NULL `none_reason`; `unit_weight` has `lb_per_unit` and `per_unit`, `source = 'unit'`, NULL `value_id` and `none_reason`; `none` has `none_reason` and NULL `value_id`, `lb_per_unit`, `per_unit` and `source`) (`no_parent`, `no_approved_weight`, `seed_or_each`, `unit_not_convertible`); `captured_how text NOT NULL DEFAULT 'at_save' CHECK (captured_how IN ('at_save', 'backfill_at_apply'))`; `captured_at`. Written only by the trigger in section 3.4. **Its read policy is the ticket's, not the catalog's**: `SELECT` to `authenticated` `USING (public.is_admin() OR public.is_sales_rep())`, the same test as `blend_tickets_office_select` and `blend_ticket_products_office_all` (`20260714230100:16-37`), so exactly the users who can see a ticket's lines can see its weights. If those ticket policies change later, this one changes in the same migration.
- **`job_loader_worksheet_weights`** (the saved-worksheet snapshot): primary key (`worksheet_id`, `product_id`); `worksheet_id` FK `job_loader_worksheets(id) ON DELETE CASCADE`; `product_id` FK `products(id) ON DELETE RESTRICT`; the same weight columns as the ticket snapshot (`weight_kind`, `value_id`, `lb_per_unit`, `per_unit`, `unit_factors`, `source`, `none_reason`, `captured_at`). Written only by the trigger in section 3.4b. **Its read policy is the worksheet's**: `SELECT` to `authenticated` `USING (EXISTS (SELECT 1 FROM public.job_loader_worksheets w WHERE w.id = worksheet_id))`; the subquery runs under the reader's own worksheet policy (`20260713000000:48-62`), so exactly the users who can see a worksheet (office, its job's applicator, a current dispatchee) see its weights.

### 3.2 Reading the one approved weight

**Every new function** (readers, writers, private helpers, trigger functions) is created with an explicit security mode, owner `postgres`, `SET search_path = public, pg_temp`, and `REVOKE ALL ON FUNCTION … FROM PUBLIC, anon, authenticated, service_role` right after it is created (PostgreSQL otherwise lets `PUBLIC` execute a new function). Only the public RPCs named below then get `GRANT EXECUTE … TO authenticated`. "Private" in this sheet means that revoke and no grant, as PAR-1's helpers (`20261108120000:509-521`). The proof reads back every function's `prosecdef`, owner, `proconfig` and grants from `pg_proc`.

- **`_product_weight(p_product_id uuid, p_units jsonb DEFAULT NULL) RETURNS jsonb`** (`p_units` NULL reads `_weight_unit_factors()` itself; a capture passes the map it already read; private, `STABLE`, `SECURITY DEFINER`). The one place every reader and the snapshot trigger resolve a size's weight:
  - `liquid`: the size's parent (`product_parent_members`), then that parent's `approved` density row. Returns `{kind: 'density', lb_per_unit: lb_per_gal, per_unit: 'Gal', value_id, source, reviewed_at, reviewed_by, reviewed_by_name}` (net weights carry the same who/when fields). No parent: `none` / `no_parent`. Parent but no approved row: `none` / `no_approved_weight`. A draft beside it is ignored.
  - `dry` with a stock unit whose `unit_conversions.unit_type = 'dry'` (looked up in `_weight_unit_factors()`, the same map every reader uses, by `lower(trim(inventory_unit))`; a stock unit left out of the map for a name collision resolves to `none` / `unit_not_convertible`, so the resolver and every reader agree): `{kind: 'unit_weight', lb_per_unit: factor_oz / 16, per_unit: inventory_unit}`. Nothing stored; the stock unit is locked once set, so this is the product's reviewed setup data.
  - `dry` with a count stock unit (`unit_type = 'both'`): the size's `approved` net-weight row, `{kind: 'net_weight', lb_per_unit: net_lb, per_unit: inventory_unit, …}`, else `none` / `no_approved_weight`.
  - `dry` with any other or missing stock unit: `none` / `unit_not_convertible`. `seed` or `each`: `none` / `seed_or_each`.
- **`get_product_weights(p_product_ids uuid[])`**: `STABLE`, **`SECURITY DEFINER`, owner `postgres`, `SET search_path = public, pg_temp`** (it must call the ungranted `_product_weight`), `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role`, `GRANT EXECUTE … TO authenticated`. It refuses a caller who is not `is_active_profile()` before reading anything; read-only, no key; at most 500 IDs. Returns, for each ID, `_product_weight` plus, for the screens that show review state, the current draft (its `id`, value, entered value and unit, source, note, reason, evidence, who/when), the subject's kind and ID, and its version, which is everything an `approve_weights` item needs; and once per call a `units` map (built by the private `_weight_unit_factors()`, which the snapshot triggers also use) from `unit_conversions`: every `dry` unit's pounds per unit (`factor_oz / 16`), every `liquid` unit's gallons per unit (`factor_oz / 128`), and every count unit's (`both`: `Ea`, `Unit`) count factor, each entry tagged with its kind (`weight`, `volume`, `count`), keyed by `lower(trim(unit))` (the table's unit-name column is `unit`), because the checker and old OCR lines lower-case units. Live, every lower-cased name that appears twice (`Lb`/`LB`, `Qt`/`qt`, `oz`/`Oz`) has the same type and factor; if two rows ever share a lower-cased name with a different type or factor, that name is left out of the map (so it is refused by name, never guessed), and the proof checks this. No cost or price. Everything it returns is catalog data every active user can already read (`products`, `product_parents`, `unit_conversions`).
- **`get_blend_ticket_weights(p_blend_ticket_id uuid)`**: **`SECURITY INVOKER`**, `EXECUTE` to `authenticated` only (after the revoke above, so `anon` cannot call it). Returns one jsonb object `{basis_unit_factors, lines}`, so the ticket's basis comes back even when it has no lines; `lines` holds **one entry per current line** of the ticket (`blend_ticket_products`, by line `id`) left-joined to the snapshot on (ticket, product), so a deleted line's kept snapshot never reaches a screen or total, and a line with no `product_id` (allowed by `create_blend_ticket` and the OCR commit, `20260714230100:732-740`, `:1081-1094`) comes back with `weight_kind = 'none'` and reason `unlinked` ("not linked to a product, so it has no weight"). A linked line with **no snapshot row at all** (saved while the capture trigger was off after a rollback) comes back with reason `not_recorded` ("weight not recorded for this ticket"), distinct from a captured `none` ("no weight when saved"). The snapshot table's office-only policy (section 3.1) decides what comes back: a user who cannot see the ticket gets no rows. Each row carries its own captured `unit_factors`; `basis_unit_factors` is the ticket's row in `blend_ticket_weight_basis` (NULL when it has none), used for every line, saved or previewed.
- **`get_loader_worksheet_weights(p_worksheet_ids uuid[])`**: for saved worksheets (`SECURITY INVOKER`, at most 200 IDs), returning each worksheet's snapshot rows for products still on its current job; `EXECUTE` granted to `authenticated` only, after the blanket revoke; the worksheet snapshot's policy decides access.

Every caller converts its own quantities through a `units` map (section 4.1): a saved record's own captured map, or the current map for a live view. So the database stores one basis per subject and never a pre-multiplied total, and the app and the database use one set of factors.

**Unit factors are treated as fixed.** `unit_conversions` factors are setup data; DM-2 reads them live for live views and new captures. A saved ticket or worksheet is unaffected by a later factor change (its snapshot stores `lb_per_unit` and the `unit_factors` it used). Any future migration that changes a `dry` or `liquid` factor must name its effect on DM-2 weights in its plan; DM-2 adds no runtime guard for it.

### 3.3 Writers

All `SECURITY DEFINER`, `SET search_path = public, pg_temp`, owner `postgres`, `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role`, `GRANT EXECUTE … TO authenticated`. Each one: `_product_parent_require_admin()` first, then `_product_parent_replay(p_idempotency_key, '<rpc name>', md5(request))` (so authorization runs before the replay lookup, a NULL key is refused, a repeat returns the first result, and the same key with a different request is refused), then the work, then `save_idempotency` last. This is PAR-1's pattern unchanged (`20261108120000:492-521`).

- **`set_parent_density(p_parent_id, p_expected_density_version, p_value numeric, p_unit text, p_source text, p_source_note text, p_idempotency_key)`**: the admin's own typed value, saved **approved** with `reviewed_by`/`reviewed_at` = the caller (correction 13). Refuses: a parent that is missing, inactive or not `liquid` (`PRODUCT_WEIGHT_NOT_LIQUID`); a stale version (`PRODUCT_WEIGHT_STALE`, naming the parent); a value out of range or non-finite; an unknown unit or source. Converts specific gravity once: `lb_per_gal = round(p_value × 8.345404, 4)` (`WATER_LB_PER_GAL`, pinned in the migration); a `lb_per_gal` entry is rounded to 4 decimals, half-up. **Trust order** (measured > SDS > label > supplier): a source lower than the approved row's source is refused (`PRODUCT_WEIGHT_LOWER_TRUST: the approved value is from the <source>; use Correct weight with a reason and evidence`). The trust order is checked against the approved row only (the draft helpers' variant is below). The old approved row becomes `superseded`, an open draft (if any) becomes `superseded` too (a typed value replaces both), the version moves by one, and one `approved` event records before and after.
- **`set_size_net_weight(p_product_id, p_expected_version, p_net_lb, p_source, p_source_note, p_idempotency_key)`**: the same for one dry size whose stock unit is a count unit, with the same trust order. Refuses a size that is not dry (`PRODUCT_WEIGHT_NOT_DRY`) and a dry size stocked in a weight unit (`PRODUCT_WEIGHT_FROM_UNIT: "<name>" is stocked in <unit>, so its weight comes from the unit`), or with no stock unit. `p_net_lb` is rounded half-up to 4 decimals **first** and the range is checked on the rounded value, so `4000.00004` saves as `4000.0000` and `4000.00005` (rounds to `4000.0001`) is refused.
- **`correct_parent_density(…, p_reason, p_evidence, p_idempotency_key)`** and **`correct_size_net_weight(…, p_reason, p_evidence, p_idempotency_key)`**: the same arguments plus a required reason and evidence (`_product_parent_reason`). The only way to replace an approved value with one from a lower-trust source. Saved approved, as above. Event `corrected`, with reason and evidence.
- **`approve_weights(p_items jsonb, p_idempotency_key)`**: approves drafts saved by DM-1b's workbook, and re-stamps each approved row's `basis` from the subject's current fields (as every writer does on save), so a weight re-approved after a pack change carries the new pack. Each item is `{kind, subject_id, draft_id, expected_version}`; at most 200 items; all or nothing. Locks every subject's version row in a fixed order (kind, then ID), checks each version and that `draft_id` is still that subject's draft, applies the trust order against the current approved row (a lower-trust draft needs its draft to carry a reason and evidence, saved by the helper), then for each: the old `approved` row becomes `superseded`, the draft becomes `approved` with `reviewed_by`/`reviewed_at`, the version moves, one `approved` event. A draft that has since been replaced, or a version that moved, refuses the whole call by name. The same subject appearing twice in `p_items` refuses the whole call (`PRODUCT_WEIGHT_DUPLICATE_ITEM`) before any lock is taken.
- **Private helpers for DM-1b's Weights tab** (`SECURITY DEFINER`, revoked from every app role per section 3.2, no key of their own; Stage 2 rule 3): `_save_parent_density_draft(p_parent_id, p_expected_version, p_value, p_unit, p_source, p_source_note, p_reason, p_evidence)` and `_save_size_net_weight_draft(…)`. They run the same checks as the public setters (form, unit, range, specific-gravity conversion, version), except the trust order: a draft from a lower-trust source than the approved value is **accepted only with a reason and evidence** (the correction rule, applied at draft time), and `approve_weights` re-checks it against the approved value at approval. So the one rule is: lower trust always needs reason and evidence; the public setters refuse it (use the correctors), the draft helpers require it. They save a **draft**: an open draft becomes `superseded` (`draft_replaced` event), the new one is inserted (`draft_saved` event), the version moves. DM-1b adds its own public RPC around them with admin check and key; DM-2 ships them unused.

  - a later approval or correction never changes a saved ticket's weight;
  - a ticket saved before its product had a weight shows "no weight when saved" for that product, permanently (no saved record changes);

### 3.5 A changed pack returns its net weight to draft

`trigger_return_net_weight_to_draft`: `AFTER UPDATE OF container_size, container_type, container_unit, inventory_unit, unit_size ON public.products FOR EACH ROW`, function `return_net_weight_to_draft()` (`SECURITY DEFINER`, pinned, no grant). When any of those values actually changed (`IS DISTINCT FROM`) and the size has an `approved` or a `draft` net-weight row: an open draft becomes `superseded` (it was entered for the old pack); the approved row, if any, becomes `draft` again; the size's version moves by one (taking its version row as the writers do, so an in-flight approval of the old draft is refused as stale); and one `returned_to_draft` event records the changed values (actor per section 3.1, `'system'` when no user is signed in). A size with no net-weight rows still has its version moved (its state row inserted at 1 if missing), so a weight screen opened before the pack change is refused as stale; nothing else is written for it. The same trigger also **deletes that size's `net_weight` rows from `job_loader_worksheet_weights`** (a `density` row is per gallon of the parent's formulation and does not depend on the pack, so it is kept): the pack's meaning changed, and a worksheet's amounts stay live in that pack's units, so an old per-unit weight would mis-state the load (2 `Unit` of a pack that grew from 5 lb to 10 lb). Those worksheets then show the size's current weight (or its refusal until re-approved), marked as current, and capture it on their next save. Blend ticket snapshots are **not** touched: a ticket records what was mixed with the pack as it was. `container_unit` and `inventory_unit` can only be filled when blank (`guard_product_setup_fields`), and a size with a stored net weight already has a stock unit, so in practice the cases are a container size, type or `unit_size` edit. The guard is an `AFTER` trigger, so it adds nothing to the `BEFORE` order PAR-1 checks.

**Worksheet capture versus clearing.** The worksheet capture trigger (3.4b) and every step that clears worksheet snapshots (a pack change, a parent identity correction, a size moving parent) take **one** transaction lock, `pg_advisory_xact_lock(hashtextextended('dm2-weights', 0))`, **before** reading a weight or deleting rows. So a capture that read the old weight cannot insert after the clearing deleted: one waits for the other to commit, and the capture then reads the new state. A single lock (not one per size) means DM-2's own locks never cross. It does not change ordinary row locking: two statements that update the same rows (worksheets, ticket lines, sizes) in opposite orders can still deadlock on those rows, as they can today, and PostgreSQL aborts one whole transaction, leaving nothing half-saved; worksheet saves and pack, move or identity edits are rare, so serializing them costs nothing noticeable. **Every DM-2 trigger** (ticket header, ticket line and worksheet capture; pack, member and identity) **and every writer of section 3.3** (including `approve_weights` and the private draft helpers) **takes this one lock first**, before any state-row lock. So two DM-2 steps never hold state rows while waiting for each other: whoever holds the lock finishes, then the next starts. (A capture locking subjects in line order and `approve_weights` locking them in sorted order can therefore never cross.) A trigger waiting for the lock holds only the rows its own statement changed (ticket lines, a worksheet, `products` or parent rows); a writer holding it only reads `products` and parents without a row lock, and its foreign-key checks take `KEY SHARE`, which a non-key `UPDATE` does not block. Weight edits, ticket saves and worksheet saves are rare, so serializing them costs nothing noticeable. Two multi-row edits that update the same sizes in opposite orders still meet on those `products` rows first, as any two `UPDATE`s do today, and PostgreSQL aborts one whole.

**A size moving parent clears its worksheet snapshots.** `trigger_clear_worksheet_weights_on_member_change`: `AFTER INSERT OR UPDATE OF parent_id OR DELETE ON public.product_parent_members FOR EACH ROW`, private `SECURITY DEFINER`. When a size joins, leaves or moves parent (`move_product_size`, `20261110150000:207`, `add_product_size`, `approve_product_parent_groups`), its rows in `job_loader_worksheet_weights` **with `weight_kind = 'density'`** are deleted, because its density now comes from a different formulation. A dry size's `net_weight` or `unit_weight` row belongs to the size, not the parent, so it is kept. Ticket snapshots are untouched.

**Capture versus approval.** Both capture triggers (sections 3.4 and 3.4b) take the one `dm2-weights` lock (section 3.5) before reading `_product_weight`, and hold it to commit; every writer takes the same lock first. They take **no** state-row lock and **never write a version table** (a missing state row stays missing; it means version 0), so a sales rep's save writes only the snapshot tables. Each capture (ticket line or worksheet) reads `_weight_unit_factors()` once and passes that same map to `_product_weight` and into the stored `unit_factors`, so a weight and its map always come from one read. So an approval waits for a save in flight to commit, every line of one save reads the same approved value, and a save waits for an approval in flight.

**Lock order, one rule for every DM-2 writer:** take the subject's version row (`… FOR UPDATE`) first, then read `products` / `product_parents` **without** a row lock. A product or parent update already holds that row when its `AFTER` trigger then takes the version row, so the two never wait on each other in opposite orders. A writer that read the old pack and committed first is followed by the trigger, which returns its row to draft; a trigger that committed first makes the writer's version stale.

**A parent identity correction returns its density to draft.** `trigger_return_density_to_draft`: `AFTER UPDATE OF product_form, formulation_type, safener ON public.product_parents FOR EACH ROW` (the identity fields `correct_product_parent_identity` can change, `20261108120000:1411`), private `SECURITY DEFINER`. When any changed (`IS DISTINCT FROM`) and the parent has an approved or draft density: the open draft becomes `superseded`, the approved row becomes `draft`, the version moves and a `returned_to_draft` event records the change; and that parent's sizes' `density` rows in `job_loader_worksheet_weights` are deleted (`net_weight` rows belong to the size and are kept). A different formulation may weigh differently, so the density is checked again before use. A parent with no density rows still has its `density_version` moved (state row inserted at 1 if missing), so a density typed on a screen opened before the correction is refused as stale. Ticket snapshots are untouched.

**Product deletion.** The new `ON DELETE RESTRICT` references to `products` match PAR-1's `product_parent_members` (`20261108120000:139`). Products are retired with `is_active = false`; no screen or RPC hard-deletes a product (no `.from('products').delete()` in `src/`, no `DELETE FROM public.products` in any migration body), so no existing path changes. The proof isolates each foreign key: for each of the net-weight value, net-weight state, ticket snapshot and worksheet snapshot references, an **ungrouped** product holding only that one reference is hard-deleted as the table owner and refused naming that constraint, and `pg_constraint.confdeltype` is read back for every new FK.

### 4.1 One shared helper: `src/lib/productWeights.ts` (new)

- `fetchProductWeights(productIds)` calls `get_product_weights` (through `src/lib/db.ts`, `assertRpcResult`), de-duplicating the IDs and sending them in chunks of 500, merging the results; `fetchBlendTicketWeights(ticketId)` and `fetchLoaderWorksheetWeights(worksheetIds)` (chunks of 200) call the snapshot getters. Results are keyed by `product_id`, never by position.
- `lineWeightLb(name, quantity, unit, form, weight, units)` (`name` is the line's own product name, `product_name` on a ticket or job line, so an unlinked line can still be named) returns `{ lb }` or `{ refused, reason }` with a plain message naming the product. `units` is the map from the RPC or the snapshot (section 3.2); the line's unit is looked up as `lower(trim(unit))`, the same key the map uses (`Oz` and `oz` are fluid ounces). It never guesses and does **not** use `fieldAppPricedQuantity` (correction 3):
  - **A zero weight header is checked, not skipped** (today `:380` runs the total check only above 0, and `create_blend_ticket` allows 0, `20260714230100:626`): with a `units` map, a `0` weight header with any weighable line is a `mismatch`. Test: a 0 `Lb` header with one 10-lb line.
  - **The raw quantity is checked before any `|| 0`** (the checker today turns `NaN` into 0 and skips the row, `blendMathValidator.ts:405-408`): with a `units` map passed, a non-finite or negative raw quantity on **any** path, weight or spray tank, makes the total "not checked: <name> has an invalid amount" or "…a negative amount" instead of being skipped or subtracted. Tests: a `NaN` line against a weight header, and a negative liquid line against a `Gal` header.
  - **A non-finite quantity, or a computed weight that is not finite, is refused** ("<name>'s amount is too large to weigh"), so a huge direct-API quantity cannot put `Infinity` in a line or total. Test: `1e308` `Gal`.
  - **A negative quantity is refused** ("<name> has a negative amount"), so +10 lb and −2 lb can never sum to a checked 8 lb. On the checker's weight path, a negative or non-finite header total is reported "Total weight not checked: the total is negative" or "…is not a number" instead of being skipped or compared (today `:380` skips any total not above 0); a pound sum that is not finite (two `1e308 Lb` lines) withholds the total the same way, and `sumWeights` refuses a non-finite sum ("the total is too large to weigh"). Tests: a non-finite header and two `1e308 Lb` lines. Tests: one negative line, and a negative weight header.
  - **Refusals that come first, whatever the unit:** an `unlinked` line, a `not_recorded` line and a `seed_or_each` product are refused before the unit is looked at, so a seed line or an unlinked line recorded in `Lb` is never counted. Tests: a seed line in `Lb` and an unlinked line in `Lb`, each refusing the total by name.
  - Otherwise the line's unit decides the path, by its kind in the map:
  - **weight unit** (`Lb`, `Dry oz`, `g`, `MG`), liquid or dry product: the quantity already is a weight, `lb = quantity × lb_per_unit[unit]` (`Lb` 1, `Dry oz` 0.0625, `g` 0.0022046225, `MG` 0.0000022046225). No stored weight is needed. So both live `MG` products work, and a liquid recorded in `Lb` counts as those pounds.
  - **volume unit** (`Gal`, `Qt`, `Pt`, `Oz`, `oz`, `fl oz`): only a **liquid** with a `density` weight: `lb = quantity × gal_per_unit[unit] × lb_per_gal`. A dry product in a volume unit is refused ("<name> is dry but recorded in <unit>, a volume unit"), so a dry `Oz` line is never read as weight ounces.
  - **count unit** (`Ea`, `Unit`): a liquid line in a count unit is refused ("<name> is a liquid recorded in <unit>; record it in a volume unit"), since a density is per gallon and the picker offers `Ea`/`Unit` to every line (`units.ts:39-48`); otherwise only a **dry** size with a `net_weight` weight whose stock unit is also a count unit: `lb = quantity × count_factor[unit] / count_factor[stock unit] × net_lb` (both are 1 live, so `Ea` and `Unit` are interchangeable, as the picker offers both).
  - Anything else is refused, with a reason that says what would fix it, from the weight's `none_reason` or the unit test: `unlinked` → "<name> is not linked to a product, so it has no weight"; `not_recorded` → "<name>'s weight was not recorded for this ticket"; `no_parent` → "put <name> in a parent to record its weight"; `no_approved_weight` → "<name> has no approved weight yet"; `seed_or_each` → "weight isn't tracked for seed or each products"; a unit not in the map → "<name>'s unit <unit> isn't in the unit table", or, for a name the map leaves out for a collision (its `ambiguous` list), "<name>'s unit <unit> has conflicting entries in the unit table".
- `lbToUnit(lb, unit, units)` converts a pound total to a weight header unit through the same map (refuses a unit that is not `dry`).
- `sumWeights(lines)` counts only **contributing** lines (quantity not zero, as the checker skips zero rows, `blendMathValidator.ts:405-407`). It returns a total only when every contributing line has a weight; otherwise `{ refused, reasons }`, and every screen shows "Total product weight not shown:" followed by each refused line's own reason (for example "line 3 is not linked to a product", "<name> has no approved weight yet"), never a partial sum.
- Weights are computed unrounded; a weight of 1 lb or more is shown to 2 decimals, a smaller non-zero weight to 3 significant figures (`0.00220 lb`), so a real weight never shows as `0.00`; a total is the sum of unrounded line weights, formatted once by the same rule. Test: a 1,000 `MG` line shows `0.00220 lb`. No money is involved.
- Unit tests, hand-checked: 2.5 `Gal` at 8.3454 lb/gal = 20.8635 lb; 32 `Oz` of the same = 2.08635 lb; `LB`, `Lb` and `lb` all read 1 lb; 5 `Lb` of a liquid = 5 lb with no density; 2 `Unit` of a size stocked in `Ea` at 5 lb = 10 lb; specific gravity 1.15 saved as 9.5972 lb/gal; 50 `Lb` = 50 lb; 24 `Dry oz` = 1.5 lb; 1,000,000 `MG` = 2.2046 lb; 3 `Ea` of a 5-lb pack = 15 lb; a dry line in `Oz` refused (not 1 lb); and each refusal message.

## 7. Risks

- **A wrong or unreviewed weight reaching the loader worksheet.** Readers use only the approved row (one per subject, by index); a draft is never read; the proof shows a draft refused.
- **A saved ticket's weight changing.** The trigger writes first-time-only per (ticket, product), covers every writer including direct API writes, and the proof replays each route. A future writer that bypasses `blend_ticket_products` entirely (none exists) would need its own check.
- **The trigger blocking a ticket save.** It only reads products and writes one row; it never raises for a missing weight (it records `none`). The proof saves a ticket whose products have no parent.
- **Old browsers.** No existing screen or RPC changes behaviour; an old page simply shows no weights.
- **Unit spellings.** Weight conversion uses only `unit_conversions`, matched exactly; a fluid unit on a dry line (or the reverse) and an unknown unit are refused by name rather than guessed. The manual screen's unit picker offers `unit_conversions` names (`UnitSelect.tsx:35`) plus a line's already-saved value even when it is not in the table (`:32-34`); so an OCR line, or an older manual line, in another spelling ("gallons", "lbs") can be re-saved as is. Such a line gets no weight and the total stays "not checked" with that reason, as today. Rows the checker already converts keep today's conversion.
- **A unit factor changing.** Treated as fixed setup data (section 3.2); saved tickets keep their stored `lb_per_unit`.
- **Sibling packages.** DM-1's cost per lb of active reads DM-2's approved density and net weight through `_product_weight`; DM-1b's Weights tab saves through the two private draft helpers (section 3.3). Neither may read the value tables directly. Parallel migration PRs take distinct stamps and re-check the ledger at apply.

**Sol list:** both PRs. **Mason-gated:** none at apply (new objects, no live rows written); the apply still needs the exact-head Sol proof (section 3.6). Reviewing drafted weights (DATA-4) before an admin approves them is Mason's, once parents exist.

## 8. Questions for Mason

Each has a default the builder follows unless Mason says otherwise.

1. **A saved loader worksheet keeps the weights it was saved with; a correction only shows on new worksheets.** One exception, which overrides the Stage 2 rule for worksheets only: if the size's **pack changes**, the size **moves to another parent**, or the parent's **formulation identity is corrected**, the worksheet drops only the saved weight that depended on it (a pack change drops a dry size's per-pack weight; a move or identity correction drops a liquid's per-gallon density) and shows the current one (marked current), because the old weight would describe a different package or formulation than the job's lines now name. A worksheet does not save its amounts: they are re-read from the job each time, so an old 5-lb pack weight times today's count of 10-lb packs would print a wrong number. Tickets never drop a weight. If a product had no weight when the worksheet was saved, the sheet shows today's approved weight for it (labelled), and keeps it from the next save. A blend ticket is stricter: a product with no weight when the ticket was saved stays "no weight when saved", because a ticket records what was mixed; and a ticket keeps **one weight per product**, so a second line of the same product added later uses the weight the ticket already saved for it (one mix, one weight). **This departs from the Stage 2 rule** (`:325`) in two places: a product with no weight when saved later shows today's weight, and the three exceptions above drop a saved weight. **Default: accept this**, because a worksheet's amounts are re-read from the job and its loads are still being worked, so filling in a missing weight helps the crew. **The strict Stage 2 alternative:** a worksheet saved before a product had a weight shows "no weight when saved" for it forever (today every saved worksheet would, since no weights are approved yet). The alternative, a worksheet always showing today's weight, is simpler but means a sheet the crew already loaded from can change under them.
2. **Who may approve a weight.** **Default: any admin**, the same as other catalog data; no second approver. A weight an admin types is approved by that admin (the Stage 2 rule); agent-drafted weights wait for an admin's approval after your review (the Stage 2 rule, `:319`, makes your review a step before the admin approves, not a separate database check; the approval screen says "approve after Mason has reviewed" and each approval records the admin). Each approval records who and when.
3. **Saved weights are copied by the database, not by an admin action.** The Stage 2 sheet says new tables are written only through admin-checked actions, but it also says each saved ticket line keeps its weight "for every writer" (its 7.8), including sales reps saving tickets. DM-2 meets both by letting the database copy the already-approved weight at save (correction 14); no one can type into those copies. **Default: accept.** The alternative, only admins' saves keep a weight, would leave sales-rep tickets without one.

Not done, by choice (say if you want them): "water to add" per load (needs every product's volume, including dry), and a "use today's weight" button on an old ticket.
