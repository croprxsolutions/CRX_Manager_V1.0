## Outcome and authority

An admin who left Rate Review with any unanswered Confirm can either resume the exact saved intent safely or explicitly check a fresh workbook before another upload. Mason chose on 2026-11-14 to allow the explicit check-and-clear path after any unanswered save; no attempt count or expiry threshold is required. A damaged record cannot be replayed or displayed; show a generic recovery reminder independently of the workbook preview and block another upload/Confirm until the admin explicitly clears it after checking.

Keep the server operation unchanged. A valid retry uses the original `commit_rate_review` key, exact parsed upload, preview, and original `sentAt`. A unique dispatch fence is local metadata only and is never sent to the RPC. A retry rotates only the fence; it does not mint a new server operation or reset its expiry.

`commit_rate_review` remains authoritative: it derives the actor from auth and requires admin (`supabase/migrations/20270104110000_product_rate_review.sql:769-782`); the key is bound to actor and exact rates/outcomes (`:773-781`); it revalidates submitted rows and refuses the entire upload unless all are unchanged/change (`:782-798`). Expected row IDs/versions remain locators and concurrency checks. No recovery state grants permission or bypasses stale-version checks.

Mason's 2026-11-13 explicit Reconfirm choice remains unchanged (`docs/plans/2026-11-13-rate-review-followups-CONTRACT.md`, Business decision). This follow-up does not alter rates, outcomes, prices, or other business-data semantics.

Expected implementation files: `src/lib/pendingRetry.ts` adds a read-only inspection that distinguishes absent/valid/damaged/unknown and rate-review-only conditional update/clear helpers while preserving the legacy helper behavior used by `src/pages/QuoteBuilder.tsx`; `src/components/products/RateReviewWorkbookModal.tsx` uses the new path for every rate-review record read/write; update `src/lib/pendingRetry.test.ts` and `src/components/products/RateReviewWorkbookModal.test.tsx`. No migration, RPC, schema, grant, or permission change.

## State and failure

- For Rate Review, inspection distinguishes `absent`, `valid`, and `damaged` (present but invalid JSON, envelope, request shape, or actor binding). It does not delete damaged bytes or return them to the caller. A valid record whose `actorId` does not match the current profile is damaged for this scoped key: show no actor or payload details. Never log, toast, send to Sentry, or print raw damaged content. The existing `loadPendingRetry` behavior, including invalid-entry cleanup, stays unchanged for QuoteBuilder.
- A `sessionStorage` read exception is `unknown`, never proof of absence and never by itself proof that a pending request exists. Preview parsing may proceed read-only. Before any send, re-inspect and establish either `absent` or an exact `valid` existing intent (same actor, key, and upload); a different valid intent or `damaged` entry blocks the send. Never overwrite or clear a record after an `unknown` read, even if `setItem` succeeds. If the read still fails, refuse Confirm with a generic storage error; do not fabricate a persistent prior-request reminder or permanently lock the tab. When reads recover, inspect again and act on the actual absent/valid/damaged state. A write or read-back exception also means no RPC was sent; re-inspect before the next attempt because the record may or may not have been stored.
- A damaged reminder renders outside the upload/preview component, so it remains visible when no workbook is loaded and the damaged request cannot produce a preview. The user may download a fresh workbook for comparison. Clearing requires the existing explicit confirmation, with copy stating that the old rows are unavailable in the app and may still have been saved. Clear only after removal is verified; if storage refuses removal, retain the reminder and explain that it remains. Do not claim the app checked or settled the old request.
- Every Rate Review path (mount/restore, intent matching, file-upload guard, Confirm preflight/read-back, late callback and retry error handling) uses the non-deleting inspection. Never call legacy `loadPendingRetry`, `savePendingRetry`, `markPendingRetryForCheck`, or unconditional `clearPendingRetry` against a damaged Rate Review entry. Rate-review-only conditional updates preserve `sentAt`, the key, request, dispatch metadata and hand-check status; they mutate only a valid record whose current key/request/fence satisfies the operation. The read/compare/write is synchronous with no `await`. Other helper consumers retain existing semantics.
- Store only the dispatch fence as local Rate Review envelope metadata, never inside the RPC request. A missing fence on a valid pre-change record is accepted during restoration; the first send persists a fence. Local metadata never forms operation identity: key + actor + exact upload and preview do. A valid pre-change record restores with the same actor, key, upload, preview and `sentAt`.
- Each send persists a new unique dispatch fence before the RPC. A retry reuses the same server key, payload, preview and expiry but rotates only the fence. A late refusal or ambiguous response may update/clear a record only when its fence still matches; it cannot clear or mark a newer send. A matching success receipt for the same key and exact payload is authoritative and retires that operation even if returned by an earlier dispatch. Within the active view, record that key as settled so later callbacks for the same operation cannot recreate a reminder after its receipt. A different key/payload record is never cleared by an older success.
- After any unanswered save, offer the fresh-workbook check-and-clear action while preserving the option to retry the same key within the original safe window. Mason chose this behavior on 2026-11-14. The admin must explicitly confirm the clear; disable the action while this view has a commit in flight. No attempt count or threshold is stored or used. `IDEMPOTENCY_*`, expired, and otherwise unsafe receipts require a check immediately.
- The explicit clear action is disabled while the current modal is awaiting a commit response. The confirmation warns that a previously unanswered request may still finish on the server. If a late request later produces a success receipt for the same exact operation, that receipt settles it; if an old callback belongs to a different key/payload, it cannot alter the current reminder. A later upload continues to use server expected-version/idempotency checks.
- Pending records remain scoped to `rate-review:<profile id>`; another profile never sees the prior actor's preview or contents. Closing the browser tab still discards sessionStorage. A duplicated tab may copy sessionStorage and then diverge locally; cross-tab receipt lookup/coordination stays out of scope, with the server's current key, actor and version checks authoritative.
- No external file, email, or other side effect is added. Rate/outcome history and the server-recorded actor remain unchanged.

## Proof cases

1. With no entry, inspection reports absent and the normal file flow works. A valid legacy entry with no new metadata restores its exact upload, preview, key and `sentAt`, and no RPC runs on mount.
2. Malformed JSON, an invalid rate/outcome row, or a mismatched actor under the current profile's key reports damaged; the modal shows a generic reminder outside the preview, does not render/log raw contents or send an RPC, and blocks upload/Confirm. The reminder survives remount; only explicit check-and-clear removes it. If removal fails, it stays visible. If storage read/write itself fails, Confirm sends nothing, the UI reports only that storage cannot be checked, and no unreadable record is overwritten or cleared.
3. After any unanswered save, the manual-check action is available. Confirm may still retry before expiry with the same server key, exact payload, preview and original `sentAt`. No counter is stored.
4. If dispatch A is unanswered, retry B uses the same operation but a new fence. A later refusal/ambiguous reply from A cannot mutate B's record. A success receipt for that same operation settles it regardless of fence; a later B error cannot recreate the reminder after the active view has shown that receipt, and an old uncertain callback after remount cannot recreate a settled record. A different new key/payload remains untouched by A.
5. A definitive refusal of the only first dispatch can clear its matching intent; a refusal from an older overlapping dispatch cannot clear a newer retry. Explicit manual check is unavailable while the current commit is in flight; after checking, the admin must confirm clear, and copy warns an older request may still finish.
6. A second profile cannot see the first profile's record. QuoteBuilder continues to use legacy retry behavior, including its existing invalid-record cleanup. If storage cannot persist a new valid intent, no RPC is sent.
7. If `getItem` transiently throws while `setItem` would succeed, Confirm sends no RPC and does not overwrite the hidden bytes. A Confirm attempted while reads still fail sends nothing and changes no bytes. Once reads recover: an absent result clears the stale warning and permits preview; an exact valid intent restores its original key and `sentAt` without sending on that action; a different valid intent first restores its own upload and preview; a damaged record shows the generic manual-check reminder. Cover both hidden-valid and hidden-damaged fixtures.

Use focused helper/component tests for the state machine and a browser sessionStorage/navigation check for damaged-state UI, repeated ambiguous replies and clear. Update the existing damaged-row test (which currently expects deletion) and overlapping/remount tests. No production query/write is needed; no database function changes, so no migration proof is required. The existing RPC/migration tests remain guards for server authority.

## Open business decisions

None. #1829 asks for a recovery reminder and an earlier explicit check, not a new business-data outcome. Storage API failure is an unknown state, not absence: read-only preview may proceed, but no send or overwrite may proceed until a subsequent inspection establishes absent or the exact valid intent. Callback fencing, success settlement, and classification remain technical choices under the existing idempotency/version contract.
