Creates `get_deliveries_page(date,date,text,text[],uuid,text,uuid,date,date,text,boolean,integer,integer,uuid)` returning jsonb `{success, total_count, rows, summary}`: one page (`p_limit` 1-500, `p_offset`) of the Deliveries list (`p_limit` NULL is refused, so one response never holds more than 500 rows; exports, the calendar and the load sheet read pages of 500 by id, below), with the screen's search (case-insensitive contains over delivery number, customer, driver and farm group; `%`, `_` and `\` match literally; at most 200 characters; leading and trailing spaces are ignored, so a search of only spaces is no search), status (`p_statuses` NULL or empty means everything but cancelled and voided), driver, priority, customer and date-range filters, and its default order (today, upcoming soonest, past newest, delivery number) or one of seven column sorts (rows tied on the column keep the default order, as the screen's stable sort does), always ending with the delivery id. Only the returned page builds full rows, and item counts are read for the returned page only (for every matching delivery only when sorting by item count; indexed by delivery id), never the whole items table. Each row is the full delivery plus `customer_name`, `driver_name`, `item_count` and `farm_group_name`, and `sort_position` (its place in the chosen order). `summary` holds `visible_count`, `open_count`, `scheduled_today`, `in_progress`, `completed_this_week` (UTC date of `completed_at` against the browser's week start) and a 7-day `strip`, over every visible delivery not cancelled or voided. STABLE, SECURITY INVOKER, `search_path = public, pg_temp`; row level security decides visibility (admins and sales reps every delivery, drivers their own, anyone else only a delivery assigned to them, normally none). Revoked from PUBLIC and anon; granted to authenticated and service_role. The preflight refuses a second apply (`DELIVERIES_PAGE_ALREADY_EXISTS`); the postflight checks SECURITY INVOKER and the grants. Known difference (deferred): text column sorts use the database collation, not the browser's `localeCompare`, so names differing only in case or accents can order differently from the old screen; the database order is the one the screen now shows, consistent across pages.

Proof: `scripts/smoke/prove-deliveries-page-real-schema.mjs` replays the baseline and every later migration in a scratch container with no network, seeds 1,203 deliveries, and checks that pages equal the full read (pages of 500 joined) for the default order and all 14 sorts, that the read by id returns the same rows in id order and, sorted by `sort_position`, in the same order, that the default order equals the screen's comparator and every column sort equals the screen's stable sort, that 15 filter and search cases equal a direct query, that the summary equals direct counts, the role visibility, that an edit or an older insert leaves the first 100 rows in place, that a read by id across a cancel and two reactivations repeats nothing and misses no delivery that matched throughout, that bad arguments are refused, that a second apply is refused, and, at 60,000 deliveries (rolled back), that a rep's first page, a page by id and an export page stay under 8 s and under 3x a rep's plain read of the same deliveries; it also runs the live smoke chain `scripts/smoke/smoke-goal4-deliveries-page.sql`.

Whole-list reads (Sol, 2026-11-06): `p_after_id` returns the next `p_limit` matching rows after that delivery id, in id order (the nil uuid starts at the beginning, and no delivery has it: ids are `gen_random_uuid()` version-4 values; a non-zero `p_offset` with it is refused). Ids never change, so the screen's multi-page reads (export, load sheet, calendar, driver view) walk the list this way and include every delivery that matches for the whole read exactly once, whatever else is edited or re-sorted meanwhile; the screen then sorts the rows by `sort_position`. Accepted trade-off (Mason, 2026-11-06, `docs/manual/DECISION_LOG.md`): a delivery that starts or stops matching during the read (cancelled, reactivated, or moved in or out of the filters) may or may not appear, each page counts `sort_position` at its own moment and rows near an edit can sit a place or two out of order. The on-screen list still pages by offset (one page of 50 at a time, as every Goal 4 list does), so a delivery added or re-sorted between two clicks of Next can move a row onto the other page; the totals stay exact.

Speed (Sol and Taha, 2026-11-06): the first version counted items for every matching delivery on every page, and row level security checks each item row it reads, so at 60,000 deliveries a sales rep's first page took about 9 s on Taha's test copy (the `authenticated` statement timeout is 8 s). Items are now counted for the returned page only. Measured in the prover's scratch container at 60,000 deliveries and 138,000 items, before -> after: rep first page 3.2 s -> 1.2 s, rep page of 500 by id 2.2 s -> 1.0 s, rep export page of 500 at offset 30,000 2.4 s -> 1.0 s, admin first page 1.5 s -> 0.7 s, driver first page 2.3 s -> 1.3 s (Taha's test copy ran about 2.8x slower than this container). Remaining limit: sorting by item count still counts every match (rep about 3.5 s here, so roughly 10 s at 60,000 deliveries on a machine like Taha's and over the timeout from about 50,000), and every call pays the security check per delivery row (`del_select` and `del_items_select` call `is_admin()` and `is_sales_rep()` per row). Wrapping those calls as `(SELECT is_admin())` in the two policies took a rep's first page to 0.2 s and the item-count sort to 0.4 s in the same container; that is a separate policy change, logged in `docs/manual/KNOWN_ISSUES.md` when this applies.
