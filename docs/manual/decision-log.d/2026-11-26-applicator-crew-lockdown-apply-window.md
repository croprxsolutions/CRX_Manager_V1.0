## 2026-11-26 — No other admin schema changes while a database change is being applied

**Decision (Mason, 2026-11-26, in chat: "Yes, out of scope" and "Yes, settle it"):** another admin changing policies, grants, views or their helper functions at the same moment a migration (or its reverse script) is being applied is out of scope: migrations need not guard against it. Raised on the applicator crew base-read lockdown (migration `20270311160000`, PR 3 of the applicator price-hide plan).
**Why:** migrations are applied by one script, alone, in an apply window, and only admins can make these changes. Each check-then-commit patch for this race moved the gap rather than closing it: Sol round 1 MED, Luna HIGH and MED, then Sol round 2 HIGH #1, MED #3 and MED #4. A grant or function change made mid-apply is no different from the same change made one second after the apply.
**What this forbids/implies:** migrations are not required to add locking or re-checks against concurrent admin changes during an apply window. A migration still checks the state it relies on before and after its change, and still takes the locks needed for its own DDL. Concurrent changes by ordinary app users (rows, not schema) stay in scope.
