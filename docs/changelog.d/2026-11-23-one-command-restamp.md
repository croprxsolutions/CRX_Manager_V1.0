## 2026-11-23 - A stale migration stamp is one command, and keeps its Sol review

- New `node scripts/restamp-migration.mjs <old-stamp> [--to <stamp>]` (feature branches into staging): renames the migration and its `migrations.d` record to a new stamp (from `next-migration-stamp`), swaps the old stamp in the files the branch already changes, updates the SQL header's link to its record and the record's SQL sha256 pin, commits, and runs `--carry-restamp`. The SQL body is never touched. It refuses a migration already on staging or main, a stamp not above both, a branch migration between the stamps, and main/staging/release/hotfix branches.
- `--carry-restamp` (`restampProblem` in `scripts/write-codex-push-proof.mjs`) now also accepts the SQL header's link to its own record changing, with that record's pin set to the new SQL's hash; it newly refuses a record pin that is not the new SQL's hash and another branch migration between the old and new stamps (an order flip the old rule missed). Why: on 2026-11-23 #2324, #2331, #2338 and #2248 were all re-dated by hand while waiting to merge; #2338's carry refused only because its header comment named the record path.
- Unchanged: the PR stamp check, the live in-order rule, the apply proof gate (`--restamp-from` still needs byte-identical SQL) and every Sol gate. No `.github/` change.
- Tests: `scripts/restamp-migration.test.mjs`; the command run on #2338's pre-restamp head `94d9e864a3` produced the same tree as its hand restamp `31436d84de`; replayed the real restamp commits `31436d84de` (#2338), `b2b579c97d` (#2331) and `a9f282bc7b` (#2248): all carry. `22509a8cf2` (#2324, which also changed SQL) still refuses.
