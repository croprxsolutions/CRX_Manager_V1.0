# Keep vehicle registration in authorized logbook reports

The FAA, field, customer and applicator logbooks currently read registration from the vehicle on each application record. A local proof as an admin and a sales rep with Reports access returned the saved number for an invented inactive aircraft. In a rolled-back compatibility test, the proposed operational vehicle columns kept working and the current FAA query lost its registration read. These reports need a separate read before the vehicle register grants can narrow.

Keep all four report RPC signatures, grants, invoker security, results, scopes, filters and sorting. The only data source change is the registration column. Add `_logbook_vehicle_registrations()`, a stable read helper with `SECURITY DEFINER` and `SET search_path = public, pg_temp`. It checks the existing active admin or Reports-enabled sales rep boundary once, via `_require_page_access('reports')`. Return a fleet-sized set of vehicle IDs and stored registrations for which an application record exists, with one row per vehicle and no other register fields. A report left-joins that set by the ID on its existing vehicle join. The helper has no standalone lookup for vehicles without application records. The same authorized office roles already have access to all those records through the four existing logbooks. Record that dependency in the migration and pin the existing `app_records_select` policy before apply. Any future change that narrows what office roles can see in application records must update this helper with it.

The report itself keeps the ordinary application record, customer, profile, invoice, field and vehicle reads subject to the caller's privileges. Retain vehicle `id`, `vehicle_name`, `vehicle_type` and `category` in the planned operational grants. The FAA report still filters to aircraft via the existing inner join. Historical inactive aircraft are included. A missing vehicle or null registration stays null and an existing blank stays blank. Once-per-report lookup avoids rechecking page access and other rows for each result row or each item of a paged browser request.

The four current report functions on staging 98fa883bb are in 20270201100000. The read-only production catalog showed their preceding bodies, with neither the same helper nor that release's grant changes. Use the project stamp allocator so the new migration sorts after the staged report-access migration. Pin the four exact reviewed definitions before replacing them, verify exactly one signature each, and require the helper name to be unused. Pin the expected `is_admin()`, `is_sales_rep()` and Reports guard bodies and verify RLS is enabled with the one known SELECT policy on application records. Reject a new restrictive SELECT policy. Revoke helper access from PUBLIC, anon, authenticated and service_role before granting EXECUTE only to authenticated. Verify the effective grants afterward. The report change is additive to existing vehicle grants and requires no app change. Update the new record in `docs/reference/migrations.d/`, the internal report entry in `docs/reference/rpc-functions.md`, and `docs/changelog.d/`. Keep the existing Reports access smoke green alongside the new registration proof under `scripts/smoke/`.

Use a vehicles-first existence query against the indexed application-record vehicle ID so the helper does not deduplicate the full application history. Validate the query plan with many prior-season records. Rollback checks the registration column grant and the four replacement fingerprints first, restores all four original report bodies, then removes the unreferenced helper last, in one transaction.

The picker registration decision does not change who already uses the logbook. This migration changes neither the vehicles table grants nor the picker, admin register or report access roles. The final vehicle cutover must check all four new fingerprints and the helper's signature, fingerprint, security attributes, search path and grants before changing vehicle grants. It also needs the compatible Job Detail and admin register readers, retention of the four report columns, and verified retirement of older clients.

## Local proof

- In a migrated local database, insert invented tied records for an active aircraft, an inactive aircraft, a ground vehicle, an unlinked vehicle, and an application record with no vehicle. Verify result parity for all four reports as an authorized admin and rep, including row filters, shape, registration, and ordering. Verify the FAA aircraft filter and missing registration/null cases.
- Run the same four authorized reports while a local rollback-only transaction limits vehicle SELECT to the operational fields. Confirm the numbers still arrive. Verify the checked-in browser report uses the same RPC shape and renders the invented registration.
- Verify inactive office users, a Reports-denied rep, driver, applicator and anon cannot read the helper or the reports. An authorized caller's direct helper lists only the registration and IDs for vehicles connected to saved application records. Check unlinked vehicles, null and blank registration, and no duplicate join rows.
- Confirm row security on parent data, current page access behavior and non-report vehicle callers remain unaffected.
- Compare exact-count paged loads, matching the browser query, on a local season with multiple pages of invented aircraft records. Require result completeness and no repeatable slowdown greater than 25 percent or 25 ms per page, whichever margin is larger. Verify the lookup uses the application-record vehicle index with a representative local catalog.

There is no open business decision for preserving the registration already printed on the reports.
