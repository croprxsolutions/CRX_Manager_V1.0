## How it works

Preflight on live: every public table locked IN EXCLUSIVE MODE (10-second lock_timeout); refuses with `LIVE_RESET_SESSION` (not read committed, or session_replication_role not origin), `LIVE_RESET_PIN_EXPIRED` (older than 6 hours or in the future, checked after the locks), `LIVE_RESET_ALREADY_APPLIED`, `LIVE_RESET_PINS_MISSING`, `LIVE_RESET_SCHEMA_DRIFT` (a public table not in the pins or not in the set this file classified, `c_table_set_md5`, a foreign key from outside public into any table it deletes from, core or section, a partitioned or inherited public table, or a missing number sequence), `LIVE_RESET_COUNT_DRIFT`, `LIVE_RESET_CONTENT_DRIFT`, `LIVE_RESET_TRIGGER_DRIFT` (the DELETE triggers on a table it deletes from are not exactly the pinned names), `LIVE_RESET_COST_BASIS_FROM_PO` (a kept `product_cost_basis` row points at a PO line through a RESTRICT foreign key) or `LIVE_RESET_GUARD_STATE`. Backup: `CREATE TABLE AS` per deleted table, plus `_inventory_before`, `_customers_before`, `_sequences`, `_triggers_off`, `_manifest`; every grant except the owner's revoked. Guards: on each table it deletes from, every user trigger that fires on DELETE (64 on the current schema: the posted, immutable, append-only and lifecycle delete guards, and delete side effects that would write stock, ledger, audit, brand or receipt rows) is switched off by name with `ALTER TABLE ... DISABLE TRIGGER`, only around the deletes, then on again; foreign keys stay enforced. Delete order: `c_core` in the file, children first; jobs, invoices, blend_tickets and field_app_billing_sets reference each other and go in one statement. Sections (constants at the top of the DO block): `c_clear_logs` on, `c_clear_receipts` off (Taha 2026-11-24: idempotency_keys, offline_action_receipts and retired_uncertain_requests are kept, so a request whose response was lost before the reset cannot run again afterwards as a new one; a kept receipt only replays its old answer, which may name a deleted record), `c_clear_team_notes_on_cleared` off, `c_clear_backup_snapshots` ON (Mason 2026-11-24: every backup_snapshots and backup_runs row, backed up into `reset_backup_20261123` first; Taha confirmed the other defaults 2026-11-23). Postflight: cleared tables empty, each section table lost exactly its backed-up rows, every kept table at its pinned count with md5-identical rows (customers apart from prepay_balance_cents, row_version and updated_at; inventory apart from its quantities, last_counted_at and updated_at), every public trigger in its earlier state, prepay 0, stock 0, each backup table equal to what was deleted, the backup reachable by its owner only. The six sequences restart with `ALTER SEQUENCE ... RESTART WITH 1`, which is transactional: the proof runs the filled file then a failing statement in one transaction and shows every sequence, row and trigger unchanged afterwards.

Rollback, only before the trial issues new documents (afterwards restored numbers and balances collide with trial data and need reconciling first): a new reviewed migration inserting each table back from `reset_backup_20261123` in reverse delete order (generated columns left out, the same delete and insert guards off; jobs, invoices, blend_tickets and field_app_billing_sets in one statement, as they were deleted), restoring inventory quantities and `last_counted_at` and customer prepay from `_inventory_before` / `_customers_before`, and each number sequence put back with `ALTER SEQUENCE ... RESTART WITH <n>` from `_sequences` (the next value: last_value + 1 when is_called, else last_value), which a failed restore also undoes; never `setval`. Keep the schema until Mason confirms the trial data looks right, then drop it in a reviewed migration.
