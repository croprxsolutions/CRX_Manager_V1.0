## 2. Corrections to the Stage 2 outline (section 7.1 and 7.8), from current code

1. **Nothing to group yet.** The outline assumed parents would exist; live has 0, and PAR-2's grouping switch is off. DM-2's mechanism can ship now; real weights wait for PAR-2's data step. Until a liquid size has a parent it shows "put this product in a parent to record its weight", as the outline said.
2. **No dry product needs a stored net weight today.** All 83 active dry products are stocked in a weight unit. The stored net-weight table is still built (a new dry product may be stocked in `Ea` or `Unit`), but its live use starts at zero, and DATA-4's dry list is empty unless such a product is added.
3. **Weight units are `Lb`/`LB`, `Dry oz`, `g` and `MG`**, read from `unit_conversions` (`unit_type = 'dry'`), not "lb, oz, kg". `oz` and `Oz` are fluid ounces in this database (`unit_type = 'liquid'`); DM-2 never treats them as weight. The app's existing converter (`fieldAppPricedQuantity`, `chemCalculator.ts:471-503`) lower-cases units, reads `oz` as a weight ounce for dry, and does not know `g` or `MG`, so DM-2 does **not** use it for weight; it uses the database's own factors (section 4.1).
4. **A count unit is `Ea` or `Unit`** (`unit_type = 'both'`). The outline's "bag, box" are container types, not stock units; no stock unit is called bag or box.
5. **The snapshot cannot ride on "the ticket's save RPC".** Three RPCs write ticket lines (`create_blend_ticket`, `save_blend_ticket`, `commit_blend_ticket_ocr_result`, the last called by the `process-blend-ticket` Edge Function), and `authenticated` still holds column `INSERT`/`UPDATE` grants with RLS write policies, so a direct API write is possible even though no screen makes one (section 3.4). So the snapshot is taken by a trigger at the line boundary, which catches every writer, as section 7.8's direction says.
6. **Key the snapshot by ticket and product, not by line.** `commit_blend_ticket_ocr_result` deletes the lines nobody corrected and re-inserts them; `save_blend_ticket` deletes lines missing from the save and inserts new ones. A snapshot keyed by line ID would be lost on those paths and re-taken at today's weight, changing a saved record. Keyed by (`blend_ticket_id`, `product_id`) and written "first time only, never changed", a re-saved, OCR-replaced or re-ordered line keeps the weight its ticket first used.
7. **Saved loader worksheets get their own snapshot, taken when the worksheet is saved** (7.8's round-8 item). `job_loader_worksheets` stores only plan settings and every product amount is recomputed from the job's lines, so there is no line to hang a weight on. DM-2 adds a per-(worksheet, product) snapshot written by a trigger on `job_loader_worksheets` (section 3.4b). The legacy loader (a job with no worksheet row) and the batch (master mix) summary are live views, labelled "current approved weights".
8. **There is no blend-ticket printout.** The outline said the ticket "prints" its weight. No per-ticket PDF exists; the only blend PDF is the ticket list export (`BlendTickets.tsx:200-222`), which has no quantities. The ticket screen shows the saved weight; no printout is added.
9. **The checker cannot check a spray tank with dry parts.** A gallon total with dry rows would need the dry product's volume, which no one records. Only a weight total whose unit is in the unit table (`Lb`/`LB`, `Dry oz`, `g`, `MG`, in any letter case) becomes a checked total, by converting liquid and package rows to pounds and then to the header unit through the database's factors. A `ton` or `kg` header (no row in `unit_conversions`) with liquid rows stays "not checked", with that reason. A spray tank keeps today's one-sided bound; when a `units` map is passed (every DM-2 screen), a non-liquid row now makes the volume total "not checked" instead of being left out quietly (section 4.4).
10. **Seed and each products never have a weight.** The outline did not say. They are refused by name ("weight isn't tracked for seed or each products"), and the checker's existing seed/each notice stays.
11. **The loader worksheet does not know which product a line is.** Its input (`LoaderProductInput`, `loaderWorksheet.ts:31-38`) carries only name, total and unit. The screen PR adds `product_id` and `product_form` to it at its two sources (`loaderWorksheetFetch.ts`: the `job_chemicals` row type `:42`, the query `:65`, the mapping `:173-179`; `JobDetail.tsx:2392-2403`) and through `masterMixSummaryFetch.ts`; the outline's file list missed these.
12. **The outline's file list misses the PDF and fetch files.** `masterMixSummaryData.ts` only builds data; the batch PDF is `masterMixSummaryPdf.ts`, and its inputs come from `masterMixSummaryFetch.ts` and `chemicalApplicationReportFetch.ts`. Section 4 lists the real set.
13. **An admin's typed value is approved, not a draft.** The Stage 2 sheet's section 7 (`:319`) says a value an admin types on the product page is that admin's reviewed entry, and only agent-drafted or uploaded values land as drafts. The outline's "every value is a draft" is narrowed to match: the public setters save an **approved** value with who and when; only DM-1b's workbook (through the private helpers) saves drafts, which an admin then approves (section 3.3).
14. **The admin-RPC write rule has a narrow, named exception.** The Stage 2 sheet's section 3 says new tables are written only through admin-checked RPCs, but its own 7.1 "Unit edits" (a trigger on `products` returns a net weight to draft) and 7.8 (a snapshot "at the `blend_ticket_products` line boundary for every writer") need triggers. So DM-2's snapshot tables, and the return-to-draft and ticket clean-up steps, are written only by private `SECURITY DEFINER` trigger functions that take no caller input: they copy or demote an already-approved weight and can never create or approve one (section 3.4). Every value anyone enters still goes through an admin-checked RPC.

### 3.2 Reading the one approved weight

**Every new function** (readers, writers, private helpers, trigger functions) is created with an explicit security mode, owner `postgres`, `SET search_path = public, pg_temp`, and `REVOKE ALL ON FUNCTION … FROM PUBLIC, anon, authenticated, service_role, metabase_ro` right after it is created (PostgreSQL otherwise lets `PUBLIC` execute a new function). Only the public RPCs named below then get `GRANT EXECUTE … TO authenticated`. "Private" in this sheet means that revoke and no grant, as PAR-1's helpers (`20261108120000:509-521`). The proof reads back every function's `prosecdef`, owner, `proconfig` and grants from `pg_proc`.

- **`_product_weight(p_product_id uuid, p_units jsonb DEFAULT NULL) RETURNS jsonb`** (`p_units` NULL reads `_weight_unit_factors()` itself; a capture passes the map it already read; private, `STABLE`, `SECURITY DEFINER`). The one place every reader and the snapshot trigger resolve a size's weight. As a `STABLE` function it reads everything in the calling statement's one snapshot, so it always returns one committed approved row, never a draft or a mix of two moments:
  - `liquid`: the size's parent (`product_parent_members`), then that parent's `approved` density row. Returns `{kind: 'density', lb_per_unit: lb_per_gal, per_unit: 'Gal', value_id, source, value_basis, reviewed_at, reviewed_by, reviewed_by_name}`, where `value_basis` is that value row's `basis` (net weights carry the same basis and who/when fields), plus the subject's current generations (`pack_generation` for a net weight; `member_generation` and `identity_generation` for a density; 0 when no state row exists); a capture stores `value_basis` and the generations from this one result, never from a second read. No parent: `none` / `no_parent`. Parent but no approved row: `none` / `no_approved_weight`. A draft beside it is ignored.

### 3.3 Writers

All `SECURITY DEFINER`, `SET search_path = public, pg_temp`, owner `postgres`, `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role, metabase_ro`, `GRANT EXECUTE … TO authenticated`. - **`set_parent_density(p_parent_id, p_expected_density_version, p_value numeric, p_unit text, p_source text, p_source_note text, p_idempotency_key)`**: the admin's own typed value, saved **approved** with `reviewed_by`/`reviewed_at` = the caller (correction 13; the Stage 2 sheet's line 319 makes an admin's own entry its review, which this plan follows in place of its section 7.1 wording that setters save drafts; recorded here as the resolution of that conflict in the parent sheet). The trust order is checked against the approved row only (the draft helpers' variant is below). - **`approve_weights(p_items jsonb, p_idempotency_key)`**: approves drafts saved by DM-1b's workbook, and only ever approves a draft whose `basis` equals the subject's current fields (below), so an approved weight always carries the pack or identity it was entered for. Each item is exactly `{kind, subject_id, draft_id, expected_version}` (`kind` is `density` or `net_weight`, the IDs uuids, the version a JSON number that is a whole number from 0 to the `bigint` maximum, checked on the JSON value before any cast, so `1.2` or `1e30` is refused rather than rounded); a request that is not an array of 1 to 200 such objects, or any item with a missing, extra or wrongly typed key, or an unknown `kind`, is refused whole as `PRODUCT_WEIGHT_BAD_REQUEST` naming the first bad item's position, before any subject or version row is locked (only the retry-key lock of `_product_parent_replay`, `20261108120000:491-500`, comes first) (test); all or nothing. - **A worksheet row is valid** only while nothing it depended on has changed since capture. One function decides it, `worksheet_weight_is_valid(r public.job_loader_worksheet_weights) RETURNS boolean` (`STABLE`, **`SECURITY INVOKER`**, `SET search_path = public, pg_temp`, `EXECUTE` to `authenticated` after the blanket revoke, because the table's read policy calls it as the reader; it reads the worksheet and the job's lines **under the caller's own policies**, so for a worksheet the caller cannot see it returns false and reveals nothing, and the DM-2 state tables, whose `SELECT` policy is any active authenticated user, since they hold only version and generation counters), used by the capture, the getter and the table's read policy: the row's `job_id` is the worksheet's current job; its product is still on that job (`job_chemicals`), so a removed product's kept row is hidden from a direct read too; a `net_weight` row's `pack_generation` equals the size's current one; a `density` row's `member_generation` equals the size's current one (so any join, leave or move since capture sets it aside, even a move back) and its `identity_generation` equals its parent's current one; a `unit_weight` row is always valid (the stock unit is locked once set). Because generations only go up, a pack, membership or identity changed and changed back never revives an old row. This replaces deleting rows when a pack, parent or identity changes: nothing has to catch the change at the moment it happens, so a worksheet save racing a pack change, a size move or an identity correction can at worst store a row that is already invalid, which is never shown and is replaced on the next save (proof in section 6).
- So a worksheet keeps the weight each product had the first time the worksheet was saved while that product had a weight; marking a load done or changing a setting saves the worksheet again, which captures any product added to the job, or newly given a weight, since; a later approval or correction never changes a weight already captured.

It is put to Mason as question 1 with the strict alternative.
- **A worksheet moved to another job** (an `UPDATE` where `job_id` changed; office users can do this by RLS, though no screen does): the trigger first deletes **all** of that worksheet's snapshot rows (including a product on both jobs), then captures for the new job (test: a product on both jobs, weight corrected between, the moved worksheet shows the current weight). A moved worksheet is a new plan for a different job. `get_loader_worksheet_weights` also returns only products that are on the worksheet's current job.
- Deleting the worksheet removes its rows.
- **Live has 1 worksheet row and 0 stored weight values** (dry sizes stocked in a weight unit already resolve from their unit, section 3.2, so a capture must not wait for a stored value), so nothing needs back-filling: that row has no snapshot until its next save, and before then shows current weights with the caption. The apply locks `job_loader_worksheets` with the other tables (section 3.4), so a worksheet save during the apply waits and is captured by the new trigger; a save that committed just before has no snapshot and shows current weights, marked, until its next save.
- The trigger writes only the new table and reads `job_chemicals`, `products` and DM-2 tables; it never raises for a missing weight. `job_loader_worksheets` grants and policies are untouched (no `I approve`).

### 3.5 A changed pack returns its net weight to draft

`trigger_return_net_weight_to_draft`: `AFTER UPDATE OF container_size, container_type, container_unit, inventory_unit, unit_size ON public.products FOR EACH ROW`, function `return_net_weight_to_draft()` (`SECURITY DEFINER`, pinned, no grant). When any of those values actually changed (`IS DISTINCT FROM`) and the size has an `approved` or a `draft` net-weight row: an open draft becomes `superseded` (it was entered for the old pack); the approved row, if any, becomes `draft` again; the size's version moves by one (taking its version row as the writers do, so an in-flight approval of the old draft is refused as stale); and one `returned_to_draft` event records the changed values (actor per section 3.1, `'system'` when no user is signed in). A size with no net-weight rows still has its version moved (its state row inserted at 1 if missing), so a weight screen opened before the pack change is refused as stale; nothing else is written for it. It also moves the size's `pack_generation` by one (state row inserted if missing) and writes nothing to worksheet rows: a worksheet's `net_weight` row for the old pack simply stops being valid (section 3.4b), because its captured `pack_generation` is now behind (a `density` row is per gallon of the parent's formulation and stays valid). An old per-unit weight would mis-state the load (2 `Unit` of a pack that grew from 5 lb to 10 lb), so those worksheets show the size's current weight (or its refusal until re-approved), marked as current, and replace it on their next save. Blend ticket snapshots are **not** touched: a ticket records what was mixed with the pack as it was. `container_unit` and `inventory_unit` can only be filled when blank (`guard_product_setup_fields`), and a size with a stored net weight already has a stock unit, so in practice the cases are a container size, type or `unit_size` edit. The guard is an `AFTER` trigger, so it adds nothing to the `BEFORE` order PAR-1 checks.

**Locking: no DM-2-wide lock (Mason, question 5).** DM-2 adds no advisory lock of its own. Three rules: (1) **Captures** (the ticket line, ticket header and worksheet triggers) take no lock of their own, write no version table, and check no foreign key against a row their statement does not already hold (the snapshot tables' keys, section 3.1). `_product_weight` reads in one snapshot (section 3.2), so a capture copies one committed approved value with its ID and basis: the old one, or the new one if an approval commits in the same instant, never a draft or a mix. Two lines of one save may therefore hold the old and the new density of a parent approved in that same instant; each is labelled with its own value and basis, which Mason accepted (question 5). (2) **Every writer of section 3.3** (the setters, correctors, `approve_weights` and the private draft helpers) first locks its subjects' own rows `FOR NO KEY UPDATE`, the `product_parents` row for a density and the `products` row for a net weight, all parents before all sizes, each in ID order (the order PAR-1 locks them, parent then its sizes, `20261108120000:679-686`), and only then its version rows `FOR UPDATE`, in the same order; a writer's own inserts check foreign keys only against rows it already holds. (3) **The pack and identity triggers** fire inside the `UPDATE` of that same `products` or `product_parents` row, so they already hold it before they take its version row; the member-generation trigger, which fires on `product_parent_members`, locks the size's `products` row itself before its version row (below). So a version row is only ever taken by a transaction already holding its subject row in a mode that excludes every other version-row taker: two DM-2 steps meet on the subject row first and never hold version rows while waiting for each other. A writer never waits on a parent or size while holding a version row, so `add_product_size` and `move_product_size` (which lock parent then sizes `FOR UPDATE`, `20261110150000:194-207`) can only make it wait before it holds anything of DM-2's. **One deadlock DM-2 adds, accepted:** a capture inserting a (ticket, product) key waits if another open transaction has just inserted the same key. So two transactions that each change **several lines of the same ticket** through direct API writes, one of them later touching a line the other holds, can deadlock (the first captures (T, A) for line 1; the second changes line 2 to A and waits on that key; the first then updates line 2). Every app writer that can fire the capture works on one ticket under a header lock taken first (`save_blend_ticket` `20260714230100:1201-1205`, the OCR commit `:904-908`, `create_blend_ticket` on its own new header), so two app saves on one ticket queue at the header and never reach this; the fourth app writer, `set_blend_ticket_product_quote_price`, updates only `unit_price_cents` (section 3.4 table), so it never fires the capture (`UPDATE OF product_id, blend_ticket_id`) and never holds a (ticket, product) key; it can make a save wait on a line's row lock, which is ordinary row locking with no DM-2 key involved; it needs a **direct API line update** (or owner SQL) on a ticket at the same moment as another write to that ticket's lines: two such statements, or one of them racing a `save_blend_ticket`. The save changes its kept lines in one `UPDATE` (`:1343-1358`), and PostgreSQL runs row-level `AFTER` triggers only after that statement has locked and changed all its rows, so the save captures only once it holds every line it changes; the cycle is then: an open direct transaction has inserted a line of T for product A (holding the uncommitted (T, A) key, on a row the save cannot see), the save changes another line to A and its capture waits on (T, A), and the direct transaction then updates a line the save holds. No screen makes a direct line write, so two app users never meet this; it is accepted for the same reason as above, and proven both ways in natural order, with no harness-only trigger: two direct updates (section 6), and session 1 directly inserting a line of T for A and staying open, session 2 running `save_blend_ticket` that changes line 1 to A, seen with `pg_blocking_pids()` waiting on session 1, then session 1 updating line 1. PostgreSQL aborts one whole transaction, nothing half-saved, and the caller retries. A worksheet capture cannot meet this: its key belongs to one worksheet, whose row its own statement holds. Proof: the exact interleaving above, forced with harness barriers, ends with one side aborted whole and the other committed with its snapshot rows. What remains is ordinary row locking: two batch edits that lock the same rows in different orders (an `approve_weights` call and a multi-row product or parent update made outside DM-2; two `approve_weights` calls cannot, since both take the section 3.5 order) can deadlock on those rows, as any two `UPDATE`s can today, and PostgreSQL aborts one whole transaction, nothing half-saved; the admin retries. Weight edits are rare admin actions, so this is accepted. Proofs (section 6, each with forced interleaving): a ticket save and a worksheet save each racing `move_product_size`, `approve_weights` and a pack change on a product they name; a direct line `UPDATE` changing `product_id` racing `save_blend_ticket` on the same ticket; `set_parent_density` and `set_size_net_weight` racing `add_product_size` and `move_product_size` on that parent.

**A size moving parent moves its member generation.** `trigger_bump_member_generation`: `AFTER INSERT OR UPDATE OF parent_id OR DELETE ON public.product_parent_members FOR EACH ROW`, private `SECURITY DEFINER`. When a size joins, leaves or moves parent (`move_product_size`, `20261110150000:207`, `add_product_size`, `approve_product_parent_groups`), it moves that size's `member_generation` by one (state row inserted if missing); it writes nothing else. It does not rely on its caller having locked the size: it **first locks the size's `products` row `FOR NO KEY UPDATE`, then its state row `FOR UPDATE`**, the section 3.5 order, on every path (`move_product_size` and `add_product_size` already hold that row, so the lock is immediate; `approve_product_parent_groups` may not, and a member's foreign-key check takes only `KEY SHARE`, which does not exclude a DM-2 writer's `FOR NO KEY UPDATE`). So a DM-2 writer on that size and this trigger always meet on the `products` row first, and neither holds the state row while waiting for the other. Two batch statements that lock several sizes in different orders remain the ordinary accepted row-lock case above. Test (forced interleaving): `approve_product_parent_groups` adding a size to a group while `set_size_net_weight` on the same size holds its `products` row, and the reverse; each waits for the other and both finish, no deadlock. A worksheet's `density` row for the size then stops being valid (section 3.4b), so the worksheet shows the new parent's current density, marked current, and replaces it on its next save. A dry size's `net_weight` or `unit_weight` row belongs to the size and stays valid. Ticket snapshots are untouched.

**One unit map per capture.** Each capture (ticket line or worksheet) reads `_weight_unit_factors()` once and passes that same map to `_product_weight` and into the stored `unit_factors`, so a weight and its map always come from one read.

**Writer versus pack or identity edit.** A writer holds its subject row before it reads the pack or identity it stamps into `basis`, so a concurrent pack or identity `UPDATE` either commits first (the writer, its next statement seeing the change, finds its expected version moved and is refused as stale) or waits for the writer to commit (the trigger then returns the new value to draft).

**A parent identity correction returns its density to draft.** `trigger_return_density_to_draft`: `AFTER UPDATE OF product_form, formulation_type, safener, generic_epa_registration ON public.product_parents FOR EACH ROW` (`correct_product_parent_identity` can change only `formulation_type` and `safener`, `20261108120000:1370-1382`, `:1440`; `product_form` and `generic_epa_registration` are watched for any other path, such as a future REG-1 RPC, and proven by an owner `UPDATE`), private `SECURITY DEFINER`. When any changed (`IS DISTINCT FROM`) and the parent has an approved or draft density: the open draft becomes `superseded`, the approved row becomes `draft`, the version moves and a `returned_to_draft` event records the change. Whatever the density rows, the parent's `identity_generation` moves by one, so worksheet `density` rows for that parent's sizes stop being valid (section 3.4b); nothing else is written (`net_weight` rows belong to the size and stay valid). A different formulation may weigh differently, so the density is checked again before use. A parent with no density rows still has its `density_version` moved (state row inserted at 1 if missing), so a density typed on a screen opened before the correction is refused as stale. Ticket snapshots are untouched.

**Product deletion.** The new `ON DELETE RESTRICT` references to `products` match PAR-1's `product_parent_members` (`20261108120000:139`). Products are retired with `is_active = false`; no screen or RPC hard-deletes a product (no `.from('products').delete()` in `src/`, no `DELETE FROM public.products` in any migration body), so no existing path changes. The proof isolates each foreign key: for each of the net-weight value and net-weight state references (the snapshot tables deliberately have no product FK, which the proof also reads back), an **ungrouped** product holding only that one reference is hard-deleted as the table owner and refused naming that constraint, and `pg_constraint.confdeltype` is read back for every new FK. Snapshot rows hold no foreign key, so they never block a delete: a size referenced only by ticket or worksheet snapshot rows would be deleted and those rows kept unchanged, still carrying the captured name and form, shown only while a current line names that product.

### 3.7 Rollback (in the migration header)

**Mason's rule (2026-11-06): a rollback hides everything.** Nothing is reconciled while DM-2 is off.

**Rollback**, in this order:
1. Roll back every package that reads DM-2 weights first: DM-1's cost per lb and DM-1b's Weights tab, if landed. To find them, query `pg_proc` for functions whose body names **any** DM-2 function or table (the private helpers, the three public getters, the writers, and the eight tables), **excluding DM-2's own functions** (listed by name in the migration header), and `pg_depend` for views, policies and triggers that depend on a DM-2 table or function, **excluding DM-2's own policies and triggers** (also listed by name in the migration header); anything left belongs to a package that is rolled back before this one, and the rollback refuses to run while the query returns a row.
2. Search the source (`src/`, `supabase/functions/`, `scripts/`) for every DM-2 table and function name; any reader outside the DM-2 screen PR (a direct client table read, an Edge Function or a script) is removed first, because step 3 revokes the grants it relies on, and the rollback does not proceed while the search finds one. Then revert the DM-2 screen PR and confirm the live bundle no longer calls `get_product_weights`, `get_blend_ticket_weights` or `get_loader_worksheet_weights`.
3. One migration: `REVOKE ALL` on every DM-2 table (the two value tables, both state tables, the events table and the three snapshot tables) from `PUBLIC`, `anon`, `authenticated`, `service_role` and `metabase_ro`, so no browser or other direct reader can see a weight that may go stale while the triggers are off; drop the worksheet snapshot table's read policy (it calls `worksheet_weight_is_valid`, so it must go before that function); drop all seven triggers (`trigger_capture_blend_ticket_weight_basis`, `trigger_capture_blend_ticket_product_weight`, `trigger_capture_loader_worksheet_weights`, `trigger_return_net_weight_to_draft`, `trigger_return_density_to_draft`, `trigger_delete_blend_ticket_weights`, `trigger_bump_member_generation`); and drop every DM-2 function **except** the append-only guard on `product_weight_events` and its triggers. The tables are kept, unreadable, as history.

While rolled back: no DM-2 code reads or writes the DM-2 tables; only the foreign-key effects below can. A product or parent referenced by a kept weight or state row cannot be hard-deleted (no path does this today); deleting a worksheet still removes its snapshot rows (foreign key); a hard-deleted ticket (table owner only) leaves its snapshot rows, unreadable, and its `blend_ticket_weight_basis` row is removed by that table's `ON DELETE CASCADE`. **Turning DM-2 back on after a rollback is not part of this plan (Mason, 2026-11-07); it needs its own plan, written and reviewed at that time from the facts then. Until then the kept tables stay unreadable.**

Tests: a `NaN` line against a weight header, and a negative liquid line against a `Gal` header.

## 7. Risks

- **A wrong or unreviewed weight reaching the loader worksheet.** Readers use only the approved row (one per subject, by index); a draft is never read; the proof shows a draft refused.
- **A saved ticket's weight changing.** The trigger writes first-time-only per (ticket, product), covers every writer including direct API writes, and the proof replays each route. A future writer that bypasses `blend_ticket_products` entirely (none exists) would need its own check.
- **The trigger blocking a ticket save.** It only reads products and writes one row; it never raises for a missing weight (it records `none`). The proof saves a ticket whose products have no parent.
- **A rare older weight on a ticket** (Mason question 5): a ticket line saved in the same instant a new weight is approved may keep the previous approved weight. It is labelled with the value and basis it used. Re-saving the ticket does not change it (a ticket keeps the first weight per product, section 3.4).
- **Old browsers.** No existing screen or RPC changes behaviour; an old page simply shows no weights.
- **Unit spellings.** Weight conversion uses only `unit_conversions`, matched exactly; a fluid unit on a dry line (or the reverse) and an unknown unit are refused by name rather than guessed. The manual screen's unit picker offers `unit_conversions` names (`UnitSelect.tsx:35`) plus a line's already-saved value even when it is not in the table (`:32-34`); so an OCR line, or an older manual line, in another spelling ("gallons", "lbs") can be re-saved as is. Such a line gets no weight and the total stays "not checked" with that reason, as today. Rows the checker already converts keep today's conversion.
- **A unit factor changing.** Treated as fixed setup data (section 3.2); saved tickets keep their stored `lb_per_unit`.
- **Sibling packages.** DM-1's cost per lb of active reads DM-2's approved density and net weight through `_product_weight`; DM-1b's Weights tab saves through the two private draft helpers (section 3.3). Neither may read the value tables directly. Parallel migration PRs take distinct stamps and re-check the ledger at apply.

**Sol list:** both PRs. **Mason-gated:** none at apply (new objects, no live rows written); turning DM-2 back on after a rollback needs its own plan (section 3.7); the apply still needs the exact-head Sol proof (section 3.6). ## 8. Questions for Mason

Each has a default the builder follows unless Mason says otherwise.

**Answered 2026-11-06:** Mason accepted the defaults for questions 1-4 as written, and for question 5 chose the recommended option: no shared lock.

1. **A saved loader worksheet keeps the weights it was saved with; a correction only shows on new worksheets.** One exception, which overrides the Stage 2 rule for worksheets only: if the **worksheet is moved to another job** (it then starts fresh, every weight re-captured, even for a product on both jobs), or if the size's **pack changes**, the size **moves to another parent**, or the parent's **formulation identity is corrected**, the worksheet stops using only the saved weight that depended on it (a pack change drops a dry size's per-pack weight; a move or identity correction drops a liquid's per-gallon density) and shows the current one (marked current), because the old weight would describe a different package or formulation than the job's lines now name. A worksheet does not save its amounts: they are re-read from the job each time, so an old 5-lb pack weight times today's count of 10-lb packs would print a wrong number. Tickets never drop a weight. If a product had no weight when the worksheet was saved, the sheet shows today's approved weight for it (labelled), and keeps it from the next save. A blend ticket is stricter: a product with no weight when the ticket was saved stays "no weight when saved", because a ticket records what was mixed; and a ticket keeps **one weight per product**, so a second line of the same product added later uses the weight the ticket already saved for it (one mix, one weight). **This departs from the Stage 2 rule** (`:325`) in two places: a product with no weight when saved later shows today's weight, and the three exceptions above drop a saved weight. **Default: accept this**, because a worksheet's amounts are re-read from the job and its loads are still being worked, so filling in a missing weight helps the crew. **The strict Stage 2 alternative:** a worksheet saved before a product had a weight shows "no weight when saved" for it forever (today every saved worksheet would, since no weights are approved yet). The alternative, a worksheet always showing today's weight, is simpler but means a sheet the crew already loaded from can change under them.
2. **Who may approve a weight.** **Default: any admin**, the same as other catalog data; no second approver. A weight an admin types is approved by that admin (the Stage 2 rule); agent-drafted weights wait for an admin's approval after your review (the Stage 2 rule, `:319`, makes your review a step before the admin approves, not a separate database check; the approval screen says "approve after Mason has reviewed" and each approval records the admin). Each approval records who and when.
3. **Saved weights are copied by the database, not by an admin action.** The Stage 2 sheet says new tables are written only through admin-checked actions, but it also says each saved ticket line keeps its weight "for every writer" (its 7.8), including sales reps saving tickets. DM-2 meets both by letting the database copy the already-approved weight at save (correction 14); no one can type into those copies. **Default: accept.** The alternative, only admins' saves keep a weight, would leave sales-rep tickets without one.
4. **Blend tickets show their saved weight on screen, not on paper.** The Stage 2 sheet says a saved ticket "prints" its weight, but there is no per-ticket printout today (correction 8). **Default: show it on the ticket screen only**, and add it to a ticket printout when one is built. The alternative is to build a per-ticket PDF now, which is a separate screen package.
5. **What happens if a weight is approved at the exact moment a ticket or worksheet is being saved? Answered: no shared lock.** The earlier design made the two wait for each other through one shared database lock; three reviews in a row found ways for that lock to make two saves wait on each other forever. Now a save copies whatever weight is approved at that instant. In the rare case an admin approves a new weight in the same second a ticket is saved, the ticket may keep the previous approved weight, labelled with which weight and pack it used (re-saving the ticket does not change it, since a ticket keeps its first weight per product; a worksheet never keeps a weight that no longer fits its product, section 3.4b). The rejected alternative was capturing only inside the ticket and worksheet save functions.
