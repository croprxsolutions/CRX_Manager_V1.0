# Delivery proof bound to the load: behavior contract

Read at `origin/staging` 015566676 and PR #2324 head bd06a4d1a (2026-11-23). Follow-up to Sol round 7 on #2324 (findings 1 and 2, skipped there by Mason as pre-existing). Revised after the Astra cold challenge (46 findings; settlement at the end).

## Outcome and authority

- **Business result:** when the app captured the customer's proof (an on-screen signature, or a photo of the signed paper ticket), the screen knew which products were on the load. A completion using that proof is refused, in plain words, if the load is no longer those products. The driver reloads and gets fresh proof, or calls the office if the goods already left.
- **What the app can and cannot know:** it knows what the driver's screen showed when the proof was captured. It cannot read the paper itself or tell what the customer looked at. This protects honest screens from a load changed under them (the reported problem). A deliberately false caller is out of scope: they can already complete with any proof today.
- **The gap today (facts):**
  - Completion delivers and bills whatever lines are on the delivery when the call runs (`_complete_delivery_authorized_impl`, #2324 body `20270304160000`, reached from `complete_delivery` and `start_and_complete_delivery`). A full delivery sends no line list (`p_quantities` only for partial ones: `DeliveryDetail.tsx` ~1222, `FieldStop.tsx` ~460, Mark Delivered never).
  - A ticket photo is a `delivery_photos` row checked by id, delivery, caption and file (`_complete_delivery_evidence_impl_20270104`, newest body `20270227110000`); nothing ties it to the lines.
  - Lines change only while the delivery is `scheduled`: clients cannot write `delivery_items` (`20270126110000`); `edit_delivery` deletes and re-inserts them only while scheduled; the parent-lock trigger (`20260530121534`) refuses line writes on an `in_progress` or `completed` delivery outside the completion's own override. So the swap happens before start: proof captured on a screen loaded before the swap (Mark Delivered from the list; the detail or field screen started without reloading), or a ticket photographed before it.
- **"The same load"** (Mason decision 3 below; amounts added 2026-11-24 after Sol round 11 on #2324): the same products in the same scheduled amounts from the same order lines, delivered in the same amounts, compared as a multiset of `(order_item_id, product_id, quantity, delivered)`, amounts as numbers. `delivered` is what the screen showed when the proof was taken; on the server side it is the call's figure for that line (`p_quantities`, kept between 0 and the scheduled quantity, as the body delivers it) or the scheduled quantity when no figures are sent. The screen's figure is kept to the same range. Line ids are left out, so dispatch re-saving an identical list (which re-creates the lines) does not void the proof. Unit relabels, notes, brands and totes are left out.
- **Smallest change (database PR, then screen PR, then a small "required" migration):**
  1. **Binding values.** `complete_delivery` and `start_and_complete_delivery` gain a last optional `p_lines_seen jsonb` (`[{order_item_id, product_id, quantity, delivered}]`, the lines the screen showed when the signature was drawn). `delivery_photos` gains `lines_seen jsonb`, written by the screen when the photo is taken (the lines it showed at that moment); a CHECK allows only a list (or nothing), and a trigger keeps the saved value on any later update (a photo can never move to another delivery: the existing provenance guard refuses it). Today's public functions are renamed unchanged behind thin wrappers (the `p_brand_base_seq` pattern, `20270104120000` §9) that pass the values down in one transaction setting (`crx.proof_binding`), as `crx.brand_base_seq` is. The setting carries the call's own delivery, evidence and photo id, and the check uses it only when they match the completion being checked; each wrapper restores the earlier value when it returns, so a binding never reaches another call in the same transaction. Only the wrappers write it.
  2. **One check, in the shared completion step**, re-emitting #2324's `_complete_delivery_authorized_impl` with one added block. It runs only for a real completion (#2324's own test: the delivery is `in_progress` and no receipt is saved for the key), after the delivery row lock, #2324's line lock and the nothing-delivered check. By then every existing rule has passed: who may complete it, the replay decision, the admin-only no-proof rule, the signature image and the ticket photo checks (the evidence step has already locked that photo row). Refusals:
     - evidence `signature` with `p_lines_seen` given and not the same load → `DELIVERY_LOAD_CHANGED`;
     - evidence `paper_ticket` whose photo has `lines_seen` and it is not the same load → `PAPER_TICKET_LOAD_CHANGED`.
     Left at site and no-proof completions are not checked (neither is proof of products). Malformed binding values (a JSON null, not an array, an entry missing a field, a quantity that is not a JSON number) count as "not the same load"; only a missing value (SQL NULL) means "not sent".
  3. **Screen PR (merges after the database is live):** each screen freezes the lines it shows with the signature or photo; a reload that changes them clears that proof with a message; the photo row is saved with them; Mark Delivered loads the delivery's lines before it lets the customer sign; `errorSanitizer` maps both codes; a refusal clears the stale proof and reloads the delivery (no automatic retry).
  4. **Required (later, Mason decision 2):** a small migration refuses a fresh signature or paper-ticket completion with no binding.
- **Who may act:** unchanged. The wrappers do no checks of their own; EXECUTE grants copy today's (`complete_delivery`: authenticated, service_role; `start_and_complete_delivery`: authenticated). The renamed bodies and the trigger function have no client EXECUTE. `lines_seen` is readable by whoever may read the photo row (the same people who may read the delivery's lines).
- **Files:** `supabase/migrations/20270305110000_proof_bound_to_load.sql`, `docs/reference/migrations.d/` record, `docs/changelog.d/` note, `scripts/smoke/prove-proof-bound-to-load-real-schema.mjs`, reverse script, `src/lib/errorSanitizer.ts` (+test, both codes; harmless before the screens send anything).

## State and failure

- **Automatic record changes:** none. A refusal rolls back that call. Earlier separate saves (an uploaded signature file, a saved ticket photo, saved brand choices, a delivery started by `confirm_delivery`) stay as they are today when a completion fails.
- **Lines cannot change under the check:** the delivery row is locked `FOR UPDATE` first; a new line's foreign-key check needs a key-share lock on that row, so it waits; existing lines are locked by #2324's line lock; and an `in_progress` delivery refuses line writes anyway (parent-lock trigger).
- **Existing rows:** existing photos keep `lines_seen` NULL and are accepted as today until step 4; nothing is backfilled (today's lines would bless an old ticket). Completed deliveries and their saved receipts are untouched; replays never reach the check.
- **Rollout:** the deployed app sends no binding: nothing changes for it (no new refusal reaches it until step 4). The screen PR merges after the database is live.
- **Timing:** retry with the same key after a lost reply → the saved receipt, as today (the binding is not in the server fingerprint, like `p_brand_base_seq`; the evidence step's own fingerprint still decides replay). A refused attempt saves no key; the screen clears the stale proof so a new attempt mints a new key. A dispatch edit racing a completion: one waits for the other on the delivery row lock; the check sees the committed lines. Mark Delivered: the outer wrapper sets the values; its body's nested `complete_delivery` call passes NULL, which keeps them (the brand pattern), so the check runs once in the shared step.
- **Undo (a switch-off):** the reverse script restores #2324's completion step only. The wrappers' optional `p_lines_seen`, the column, its CHECK and trigger stay, so screens already open and queued offline calls keep working, and saved photo lists survive a re-apply. If the later "required" migration is live, reverse it first. Deliveries completed before the fix are not changed by either direction.

## Proof cases (disposable Postgres with the real migrations, #2324 included)

1. Signature, via `complete_delivery`: screen captured the scheduled load (A); dispatch swaps A for B (`edit_delivery`); driver starts (`confirm_delivery`); completion with `p_lines_seen` = A is refused `DELIVERY_LOAD_CHANGED`; the delivery stays in progress, no stock, order-line or invoice change, no key saved.
2. Same swap via Mark Delivered (`start_and_complete_delivery` on the scheduled load): refused; the delivery stays scheduled.
3. Ticket photo saved with `lines_seen` = A, swap to B, paper-ticket completion (both entry points): refused `PAPER_TICKET_LOAD_CHANGED`. A photo saved with B completes.
4. A quantity change (same product) and an added line are refused like a swap; an identical re-save (new line ids, same contents) and a reordered list complete; a malformed list (object, missing field, string quantity, one entry twice, a JSON null) is refused.
5. Unchanged: signature with matching `p_lines_seen`, signature with none, a ticket photo with NULL `lines_seen`, left at site, no-proof (admin) all complete as before: status, stock, order line, invoice.
6. Error order unchanged: a driver's no-proof attempt with a stale list still gets `NO_PROOF_ADMIN_ONLY`; a missing ticket photo still gets `PAPER_TICKET_PHOTO_MISSING`; a caller not allowed to complete still gets `Not authorized to complete this delivery`; nothing delivered still gets `DELIVERY_NOTHING_DELIVERED`. (A partial delivery whose quantities were set against older lines gets #2324's `DELIVERY_QUANTITIES_STALE` before this check.)
7. Retry of a completed call with its key returns the saved receipt, even with a list that would now be refused.
8. A photo update (as admin) cannot change `lines_seen`; a photo saved with a value that is not a list is refused.
8b. Three completions in one transaction (Mark Delivered with one list, a ticket with an unbound photo, a signature with no list) each use only their own binding, and nothing is left afterwards.
9. Grants: anon cannot call either wrapper; no client role can call the renamed bodies, the helpers or the trigger function.
10. Reverse script restores #2324's step; case 1 and case 3 complete again, and calls that still send a list or use a photo with one keep working.
11. After the live apply (not in this PR's proof): one real API call to each wrapper with and without `p_lines_seen` on a staging delivery, to confirm the API exposes the new optional input.

## Business decisions (Mason, 2026-11-23: the recommendation on all three; separate PRs, database first)

1. **Paper the app cannot read.** If the customer signed a ticket listing A, dispatch changed the load to B, and the driver photographs that same paper on a reloaded screen showing B, the app accepts it. Recommend: accept this limit and have the screen list the products next to the photo button ("check the signed ticket lists these"). Alternative: a printed ticket carrying a code the app checks (a separate, larger feature).
2. **When old app copies stop working without the binding.** Recommend: one week after the screen PR is live, a small migration refuses signature and paper-ticket completions that carry no binding. Alternative: never (old copies stay unprotected).
3. **Identical re-save.** If dispatch re-saves exactly the same products and amounts, recommend the customer's proof still counts (compared by contents, not by line ids). Alternative: any re-save needs fresh proof.

## Cold challenge round 2 settlement (Astra, gpt-6.2-astra high, 21 findings)

- Fixed: the binding carries the call's own delivery, evidence and photo id and is ignored for any other completion (1); a JSON null counts as sent, so it is refused (3); the check runs after `DELIVERY_NOTHING_DELIVERED` (4); comment wording (6); a CHECK keeps `lines_seen` a list (11); the reverse is a switch-off that keeps the inputs and column (14, 16, 17); the rollback proof calls the wrappers with a list after the switch-off (18); bindings in one transaction (19, case 8b); duplicate entries (20).
- Refuted: 2 (only the two wrappers write `crx.proof_binding`; PostgREST callers cannot set a transaction setting before the call); 7 (`order_item_id` and `product_id` are NOT NULL on `delivery_items`); 8, 9, 10 (the provenance guard `_guard_delivery_photo_uploader` refuses changes to a photo's delivery or file, so a retake is always a new row with its own list).
- Noted: 5 (a partial delivery after a re-save meets #2324's `DELIVERY_QUANTITIES_STALE` first, which already tells the driver to reload); 12 (an old screen completing with a photo a new screen saved with a stale list is refused, by design; the plain-words message ships here); 13 (proof case 11); 15 (undo text above); 21 (the "moves to another delivery" claim removed).
