**Words used here.**
- **Registration**: one row per EPA registration number, holding the facts printed on that label (signal word, restricted-use status, REI, PHI, label maximum rate, label adjuvants), its status (active or cancelled) and the label link. Every size and brand carrying that number reads these facts from it.
- **Size**: a `products` row. **Parent**: a `product_parents` row (PAR-1). **Brand**: a `product_parent_brands` row (PAR-2) or a legacy `product_brands` row.
- **Pass**: a private one-row permission slip (transaction ID plus target) inserted just before a governed write and deleted just after; a guard refuses the governed columns without one. Same mechanism as PAR-1's `product_parent_copy_passes`.
- **RUP**: restricted-use pesticide. Stored on the registration as `rup_status` in (`yes`, `no`, `unknown`).
- **Seeded**: the one-time seed (section 5) has committed. Before it, no registration exists and every REG-1 guard and tool is inert or refused; after it, every size or brand with a number has a registration.
- **Sale capture**: the EPA number, RUP answer and signal word stored on an invoice line by the database when the line is saved.

## 3. Shared design

### 3.1 Tables

All new tables have RLS on, a `SELECT` policy for active users (except the private ones), and no write grants. **Every function in this sheet** (RPCs, helpers, trigger functions, re-issues) is `SECURITY DEFINER` with `SET search_path = public, pg_temp`, follows `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role`, and grants `EXECUTE` to `authenticated` only for the public RPCs; helpers and trigger functions get no grant. **"Admin" means enforced, not named:** every admin RPC's first statement is `v_actor := public._product_parent_require_admin();` (PAR-1's helper, `20261108120000:512-519`: refuses a missing `auth.uid()`, then a caller for whom `is_admin()` is false), before the replay lookup and before any lock. The actor recorded on every event, and `created_by`/`updated_by`, is that returned `v_actor` (or `auth.uid()` in a trigger), never a parameter. Every mutating RPC takes `p_idempotency_key text DEFAULT NULL`, refuses a missing key, and uses `_product_parent_replay(p_key, p_scope, p_fp)` with its own operation name as the scope.

- **`epa_registrations`**
  - `epa_registration text` primary key, strict CHECK as on `product_parent_brands`.
  - `registration_status` in (`active`, `cancelled`, `unknown`), default `unknown`; `cancelled_on date` (required when cancelled, else null).
  - `label_url text` (https only), `label_accepted_on date`, `source text`, `checked_at timestamptz`.
  - Label facts: `signal_word` (same CHECK as `products.signal_word`, nullable), `rup_status` in (`yes`, `no`, `unknown`) not null default `unknown`, `rei_hours`, `phi_days`, `max_label_rate`, `max_label_rate_unit` (same CHECKs as the product columns).
  - `label_adjuvants jsonb` nullable, default NULL meaning **not reviewed** (products have no adjuvant column, so the seed leaves it NULL); `'[]'` means reviewed, none on the label. Otherwise an array of `{kind: required|recommended, adjuvant_type text, note text}`, checked by an immutable validator function.
  - `registration_version bigint` (starts at 1; every successful write to the row increments it and sets `updated_by` and `updated_at` in the same statement), `created_by`, `created_at`, `updated_by`, `updated_at`.
- **`epa_registration_events`**: append-only (update and delete refused). `event_type` in (`seeded`, `created`, `updated`, `assigned`, `draft_committed`); `reason`, `before_values`, `after_values`, `affected jsonb` (per parent, size or brand written: table, ID, before and after); `changed_by`, `changed_by_name`, `changed_at`.
- **`epa_registration_copy_passes(txid bigint, target_table text, target_id uuid, event_id bigint)`**: private, no grants.
- **`label_draft_targets(draft_id uuid primary key, epa_registration text, product_epa_registration text, product_id uuid, product_label_fingerprint text, registration_version bigint, proposed_values jsonb)`**: private, no grants. Filled by the draft-create functions, read only by the commit. `epa_registration` is the draft's own number at creation; `product_epa_registration` is the product's number at that moment.
- **Sale capture columns on `invoice_items`** (part C): the existing `epa_registration` becomes the number sold; new `sale_rup_status text` in (`yes`, `no`, `unknown`) (NULL = not captured, never "No"; tri-state so a Not reviewed label is never stored as No), `sale_signal_word text`, `sale_facts_captured_at timestamptz` (NULL = not captured), `sale_facts_source text` (`registration:<number>@<version>`, `product:<id>` for a numberless product, with the prefix `seed-assumed:` on lines captured by the seed, e.g. `seed-assumed:registration:<number>@1`, so a seeded line carries its registration version like any other). Clients cannot write them (column grants revoked for these four, set only by the database; see Q7 for the grant change).

### 3.2 Locking

**One shared lock first.** Every function that reads or writes an EPA number, a label fact or a sale capture takes the transaction-level advisory lock `pg_advisory_xact_lock(hashtext('crx_epa_registration'))` **before it reads any product's number or facts**:
- **Exclusive** (`pg_advisory_xact_lock`): the seed, `set_epa_registration`, `assign_epa_registration`, the draft commit, `apply_product_setup`, the brand upserts, `move_product_size`, `_insert_parent_size` / `add_product_size` / `create_product_with_parent`, and 7.7's correction.
- **Shared, readers of numbers for a saved target:** `create_label_draft` and `bulk_create_label_drafts` (they record the product's number and label fingerprint in `label_draft_targets`, so they must not interleave with an assignment).
- **Shared** (`pg_advisory_xact_lock_shared`): `save_invoice`, `generate_rup_sales_records` and (with 7.7) `save_job`, so invoice saves never wait on each other, only on a registration or number change. **Posting entry points:** every outer function that reaches `generate_rup_sales_records` (the `post_invoice` wrapper, which locks invoices and lines before its implementation, `20261022022000:458-482`, plus group and batch posting; the build lists them from `pg_proc` callers) is re-issued to take the shared lock **as its first statement, before its existing invoice locks**, so posting never holds an invoice lock while waiting for the seed's exclusive lock (no lock inversion); the inner call's own shared lock then re-enters harmlessly.

So a save cannot read a product's number, then see it change before it locks: nothing that changes numbers or facts can run between the read and the commit. Direct client writes do not take the lock, but the guards (3.3) refuse every direct change to a number or label fact once seeded, so they cannot race.

**Row order after the shared lock:** invoices (ID order) → registrations (number order) → parents (ID) → products (ID) → brands (legacy, then parent brands, ID) → invoice lines and RUP records (ID) → the rate lock `FOR SHARE` where already taken. Today's PAR-1/PAR-2 orders (parent → products → brands; approval: proposal → products → rate lock; `move_product_size`: both parents in ID order → size → brands) are a suffix of it.

**Creating a registration that does not exist yet:** `INSERT … ON CONFLICT (epa_registration) DO NOTHING`, then `SELECT … FOR UPDATE`. Under the exclusive shared lock two creators cannot overlap; an admin create with a null expected version that finds a row is refused as stale (`EPA_REGISTRATION_STALE`), never with a raw key error.

### 3.3 Guards (part D; inert until seeded)

Each guard first checks whether the seed has committed (a `seeded` event exists, read through a stable helper `_epa_registrations_seeded()`); before that it does nothing, so the database PR changes no behaviour until Mason approves the seed.

- **`trigger_zz_guard_product_registration`** on `products` (`BEFORE INSERT OR UPDATE`, `SECURITY DEFINER`, `search_path = public, pg_temp`, owned by `postgres`). Name sorts after `trigger_zz_guard_product_parent_values` (so a grouped size gets the parent message first) and before `trigger_zzz_guard_product_rate_lock`.
  - **UPDATE:** a change to `signal_word`, `is_rup`, `rei_hours`, `phi_days`, `max_label_rate` or `max_label_rate_unit` on a row with a number, without a pass, is refused: `EPA_REGISTRATION_FACT: <column> belongs to EPA registration <number>; edit it on the registration (reload the app if you do not see a Registration panel)`. A change to `epa_registration` without a pass is refused with `EPA_REGISTRATION_ASSIGN: use Change EPA number`, including adding a number to a numberless size. An update that resends unchanged values passes. A numberless size edits its own `is_rup` freely (it has no registration).
  - **INSERT** with a number: the trigger first takes the shared advisory lock in shared mode (3.2) and locks the registration row `FOR SHARE`, so an insert from any role (including a privileged one outside the app) waits for a running `set_epa_registration` and reads its committed facts. The number must already have a registration, else `EPA_REGISTRATION_NEW_NUMBER: add this EPA number's registration first`. The row's label facts are overwritten from the registration; a sent fact that is not NULL and differs is refused (`EPA_REGISTRATION_FACT_CONFLICT: <column> on EPA registration <number> is <value>`). For RUP on insert, only a sent `true` against a registration that is not `yes` conflicts; a sent `false` against `yes` is not refused and is overwritten to `true`, because a boolean cannot tell a default `false` from an intended No (the comparison rule in the next bullet is for updates only); Q7 removes the direct insert grant so that only the admin functions (which take RUP from the registration) insert. The trigger never creates a registration; every insert function that brings a new number creates the registration first through the internal create helper from its `p_new_registration` (label facts entered from the label, `rup_status` as `yes`/`no`/`unknown`), else it is refused with `EPA_REGISTRATION_FACTS_REQUIRED`.
- **The size's `is_rup` boolean under a registration** is a mirror: `true` only when `rup_status = 'yes'`, else `false` (so `unknown` reads as unticked, exactly as today's default). Screens and reports that show RUP read `rup_status` (tri-state) after the screens PR; until then old screens show today's tick box, which is what they show today. Comparisons of a sent boolean with a registration on **update**: `true` conflicts unless `yes`; `false` conflicts only with `yes`; `false` against `unknown` is accepted and changes nothing (a boolean cannot set or clear Not reviewed; only `set_epa_registration` can).
- **Brand guards** on `product_brands` and `product_parent_brands`: same rules for `signal_word`, `is_rup` and `epa_registration`; brand `is_rup` mirrors `rup_status` as `true` / `false` / `null`.
- **Invoice-line guard** on `invoice_items` (`BEFORE INSERT OR UPDATE`): an `INSERT`, or an `UPDATE` that changes `product_id`, `invoice_id`, `epa_registration` or a capture column, is refused without the capture pass (`INVOICE_LINE_SALE_CAPTURE`). Only the shared helper `_capture_invoice_line_sale(...)` (part C) takes that pass, and it fills the capture by the part C rules (before the seed: stores the number as today and captures nothing). Not seeded-gated: it applies from the database PR's apply, so every function that inserts invoice lines is re-issued in part C to go through the helper. Client code only reads `invoice_items` (checked 2026-11-06: `reconciliation.ts:919`, `FieldApplicationInvoice.tsx:1345`, `FieldAppSplitInvoiceEditor.tsx:666`, `InvoiceDetail.tsx:761`, `:1740`, `Invoices.tsx:508` are all selects).

## 4. REG-DB · The database PR (all database changes, one PR)

**Shape:** one PR, four migration files applied in order (parts A to D), all applied live before merge through the normal migration gate. At apply, data behaviour is unchanged (before the seed `save_invoice` and posting behave as today, section 4.C); every registration tool refuses with `EPA_REGISTRATION_NOT_SEEDED` and every product guard is inert until the seed (section 5). **Writes no live product or registration rows at apply.** What does change at apply is permissions (Q7): direct client inserts of products and direct client writes to invoice lines are removed, and all invoice-line writers run through one capture helper.

**Depends on:** KI-18 batch 1 (#1579) merged (part C re-issues `generate_rup_sales_records` from its body); #1581 merged (part D re-issues `_insert_parent_size` from its body); #1553 merged (the product page creates through `create_product_with_parent`, so Q7's removal of direct product inserts breaks no screen; the harness searches `src/` for a direct `products` insert and fails if one remains); Taha's `20261201110000_product_parent_review_fixes` (merged in #1586). Built from each function's body on `main` at build time and diffed against `pg_get_functiondef` on live before review.

### 4.A Storage, seed tools, registration RPCs, draft targets

- The tables in 3.1, with RLS, policies, the event table's append-only triggers, the adjuvant validator, and `_epa_registrations_seeded()`.
- `preview_epa_registration_seed()` (admin, read-only): per distinct normalized number on sizes and brand rows, the proposed registration facts, every disagreement (column, values, row counts, product IDs); the not-yet-posted invoice lines and their proposed sale capture (section 5); and a `fingerprint` of the whole result. RUP proposal: any row `true` → `yes`, else the seed's RUP default.
- `seed_epa_registrations(p_picks jsonb, p_rup_default text, p_expected_fingerprint text, p_idempotency_key text)`: section 5.
- `set_epa_registration(p_epa_registration, p_expected_version, p_changes jsonb, p_reason, p_idempotency_key)` (admin, key): exclusive shared lock; locks the registration, then the sizes (ID order) and brands carrying it; refuses a stale version; updates it; writes one event; copies the changed facts to every size and brand under passes. **Grouped sizes:** where a size carrying the number belongs to a parent, the parent row is locked (registrations → parents → products) and its matching label columns are written in the same transaction, and each size write carries both PAR-1's `product_parent_copy_passes` row and the registration pass, so `trigger_zz_guard_product_parent_values` (which runs first) accepts it and parent and sizes never disagree. Creates the registration when `p_expected_version` is null and none exists, writing a `created` event.
