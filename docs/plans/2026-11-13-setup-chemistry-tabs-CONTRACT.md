## Outcome and authority

An admin downloads and uploads Weights and Ingredients in the existing setup workbook. Once the workbook passes structural parsing and membership checks, each tab previews and saves independently. A malformed workbook is refused as a whole before any tab preview or write request. Weights save as drafts; ingredients create proposals for separate review. Applying a proposal is a separate explicit action. Existing Setup, Rates and Parent Rates behavior stays compatible.

Reuse the existing chemistry RPCs, ExcelJS archive/formula validation, shared database client and durable chemistry-save helper. Expected paths: `src/lib/productSetupWorkbook.ts`, focused new chemistry workbook/API modules and product components, `src/lib/productChemistry.ts` (literal RPC cases only), associated tests and documentation. No new database migration, job, table, timer or queue. This change adds RPC codes in `src/lib/db.ts`, which is on the Sol-required path list; a clean independent Sol high-effort review is required before the PR opens. No Sol review has been completed for this candidate, and this gate is not waived.

The server checks admin authority, allowed forms/units, source trust, versions, parent/ingredient membership and the current EPA refusal under lock. Uploaded IDs are locators, not authority. Actor comes from auth, never workbook data. Proposal reads use admin RLS, explicit columns, deterministic paging and an exact count. Non-admins cannot read proposals or invoke these APIs successfully.

## State and failure

- New downloads use manifest v3; v2 uploads still work and contain no chemistry actions. v1 remains refused. Missing chemistry sheets mean no chemistry changes, including v3, as explicitly settled by the DM-1b build sheet section 4. Chemistry sheets use their own variable-row parser, not the fixed-count legacy sheet reader. The existing whole-file membership check remains: grouping changes refuse the entire upload with a fresh-download instruction. Legacy tab size limits also refuse the entire upload before any chemistry preview is shown. Chemistry versions remain authoritative per subject/parent. All formulas and malformed cell values in parsed chemistry rows are refused with sheet/row context before any per-tab API preview is sent.
- Weights carry the exported subject and version, plus value, source, optional source note/reason/evidence. The editable value/source/note start at the draft when present, otherwise approved, otherwise blank. Approved and draft values remain visible separately. A hidden bound download record lets the parser send only rows whose value, source or source note changed (reason/evidence alone saves nothing, stated in sheet help); an untouched row never overwrites a draft and an unrelated untouched stale row does not block a save. Blank unrecorded values mean no request; source or note alone cannot create a weight and asks for a value, while clearing a recorded weight is invalid (no delete writer). Source values are exact lower-case codes `measured`, `sds`, `label`, `supplier`; the column note and refusal use those codes. Refuse values beyond four decimals rather than silently round. Each chemistry download is a complete snapshot and requires the chemistry read; if any snapshot read fails, do not offer a partial workbook that could omit a chemistry tab. Downloads refuse before generation if either chemistry sheet would exceed the parser's 10,000 data-row limit. Committing a tab saves drafts only; it never approves weights. Any invalid/stale sent row refuses the whole tab on the server, naming the subject. Source/trust rules remain the existing DM-2 rules.
- Ingredients carry parent ID/version, existing row ID or blank for add, name/CAS, strength/unit/basis, source and source note. Each active parent has three blank bound starter rows; use an unprotected Ingredients sheet with grey reference columns so Excel permits full-row copy/insert/omit. Safety comes from parser binding and server checks, never sheet protection. Chemistry rows have no fixed manifest count. Each parsed row must match its hidden parent/version binding and visible reference name; copied starters retain this binding. An inserted row with data but no binding is refused by sheet/row with a copy-a-starter instruction. An ingredient name displayed in the download may be trimmed for workbook comparison; hidden IDs and downloaded identity remain authoritative. Each hidden record also contains the downloaded editable values, so only changed/add/delete rows are sent and an untouched parent's stale version does not block another parent. An existing ingredient row can be moved but cannot be relabelled as another parent/ingredient. Omitted and untouched rows do nothing. A dedicated `action` column accepts blank or `__delete`; the marker never replaces the name/CAS. Delete requires a cited source note and separate proposal review. A blank starter row does nothing. Blank strength means unknown, but strength unit and basis are still required, including for unknown strength; only `pct_ww`/`lb_per_gal` units and `active_ingredient`/`acid_equivalent` bases are accepted. A blank existing name or changed identity is invalid, not implicit deletion. A changed/new ingredient needs its cited source note. Ingredient source values are exact lower-case codes `label`, `sds`, `supplier` and `other`; the column note and refusal use those codes. Commit creates one open proposal per changed parent and changes no live chemistry. Any invalid, stale or EPA-refused parent refuses the whole tab. Flag EPA refusals and EPA-filled rows as reference; the current server decision still controls. A shared-ingredient rename after download is shown as a refusal with a fresh-download instruction; the screen does not advise deleting and re-adding it. The download refuses before generation if the Ingredients sheet would exceed the parser's 10,000 data-row limit. Check the server limits of 2,000 sent rows per tab and 200 ingredient changes per parent before preview.
- Open proposals are not replaced by new uploads. Warn when the upload concerns a parent with another open proposal. Show parent, submitted actions/new values, source citations, delete warning and status/version. During the initial proposal read, show a checking state and disable Ingredients confirmation; do not report an empty list until the read succeeds. Resolve existing row IDs through explicit paged `product_parent_ingredients` and `active_ingredients` reads, including retired rows. Existing change/retire names and CAS come only from the currently linked catalog row; the submitted old name cannot replace or stand in for a missing link. New-add names come from the submitted proposal. Names are labelled current lookup values; no historical before values are promised, since the proposal does not snapshot them. Refuse to offer Apply if a referenced name cannot be resolved. Apply is offered only without deletes; Apply delete only with deletes and a ConfirmModal that names removal; Reject is explicit and needs no written reason, per the build sheet. The server rechecks proposal version, base chemistry version and EPA gate. Applying one may make another stale; retain history, refresh and explain that it must be rejected or replaced. A newly pending EPA lookup can restore the EPA refusal. No UI undo: subsequent corrections use the existing chemistry history path.
- Each chemistry write creates one retry key at confirmation, stores exact arguments/user/scope before sending and reuses it after uncertain failure. All three write kinds use the shared constant scope `setup-workbook-chemistry`. Reuse `startChemistrySave`/`finishChemistrySave`; expose an explicit Finish action when opening the workbook modal even before upload, never automatically replay. An unresolved workbook chemistry operation blocks every replacement chemistry write in that scope, independently of the product-page chemistry scopes. While a chemistry request is actually in flight, disable modal Close, Upload and Download so a new panel cannot invite a duplicate Finish; an unresolved stored request with no active send remains visible but does not lock those modal controls. Keep accepted per-product Rates and Parent Rates previews and idempotency keys after an uncertain reply, including when Setup is saved; skip per-product Rates re-preview while its retry is pending. A known Rates stale/lock refusal clears its retry and returns the tab to fresh-preview/locked state. A new upload clears only the retry-pending UI state and deferred own-Setup rebase; the per-payload idempotency-key map remains intact. A known business refusal on a Rates replay clears that retry and displays the server message, while auth, PostgREST, and transport uncertainty retain the prior request. If an own Setup save had to skip a pending Rates retry, a later stale refusal uses only that save's safe row rebase for the next preview. Parent Rates invalidates on its five authoritative stale-preview refusals and reloads the preview after a rate-lock refusal; auth and PostgREST refusals on a pending replay preserve the request, with sign-in/admin guidance for auth errors. Use workbook-specific failure wording. Storage failure prevents sending. A first-send authentication or role refusal removes only its new retry key because access is checked before the server can have done work for that request; show sign-in/admin-access guidance so the operator can retry after restoring access. On Finish, authentication or role refusal retains the exact prior request because the server may check access before looking up an earlier receipt; restore access and use Finish rather than creating a replacement request. Other PostgREST gateway errors during Finish also retain the intent without being labelled as an authentication problem. Retained records from another user are never displayed or replayed. The existing idempotency receipt expires after 24 hours; the UI blocks Finish conservatively after 23 hours, and also blocks malformed, non-finite or future timestamps. It retains the pending record, blocks all workbook chemistry writes and tells the operator to reconcile current drafts/proposals with support; it never clears, remints or retries an expired record. Clearing browser storage cannot be recovered by this UI.
- Disable duplicate actions while sending and check the current actor/open generation before starting or rendering asynchronous results. Closing/reopening, replacing a file or changing actor invalidates old read/preview results. A save already accepted by the server may finish after close; preserve its durable outcome but do not apply stale UI state or callbacks to another actor/file. Independent tab outcomes stay explicit; no all-tabs automatic save.
