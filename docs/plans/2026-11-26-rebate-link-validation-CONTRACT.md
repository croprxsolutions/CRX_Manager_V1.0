# Rebate claim link validation

Mason confirmed on November 26, 2026 that customers billed on a split order qualify for a linked claim and that admins follow the same rule as sales reps. The approved screen lets reps see all customer claims and create pending claims. Admins retain program management and claim transitions.

When both an order and a customer are selected, use the order's effective Bill Split payers. An ordinary order uses its customer. For an order with a Bill Split, use positive payer rows on at least one line from `_bill_split_line_shares(order_item_id, 0, 0)`. The helper applies line overrides and returns only positive percentage shares. A primary customer fully displaced from every line is refused. For an order with no lines, use its configured order-wide shares and the primary customer's unallocated remainder. Field billing is outside this change, including any separate eligibility derived from field allocations or invoices. Orders the billing system excludes from Bill Split retain their primary-customer rule. Order status and visibility are unchanged.

Both roles use the same check for an explicit product when the selected rebate program names one. Optional links, manufacturer-level programs, existing claims, amounts and transitions keep their current behavior. The link checks apply only to existing references so unknown references retain their foreign-key errors. The wrapper takes a shared lock on the selected program and order for new claims. Order-wide and line-share writers acquire an exclusive lock on the same order. Eligibility is checked at the time of the claim and does not guarantee serialization with order-line additions or removals or field allocation changes. A matching committed replay skips link checks after confirming current access. A refused claim creates no claim or receipt.

Follow the established Page Access rule in `20270201100000_page_access_locks_reports.sql`. A sales rep with the `rebates` key hidden cannot read rebate claims or programs or create a claim. Use the active-role and deny-list predicate inline in the two read policies and the claim creation wrapper before its receipt lookup. The migration requires one expected read policy per table at install before it scopes both to authenticated users. Admins keep their existing Page Access exemption. The screen continues to offer the existing selectors and explains how to correct a rejected link.

Ship the checked database wrapper first. It preserves the current RPC signature and grants and leaves #2632's browser write restrictions in place. The screen change follows that protection. A reviewed forward rollback restores the earlier wrapper.

Prove both roles on invented data. The ordinary primary and a positive secondary payer succeed. A fully displaced primary, a card payer overridden on all lines, an unrelated customer, and an explicit product mismatch are refused. A no-line order uses the card. Prove unlinked claims, missing references and an exact retry after changing eligibility. A rep with the page hidden gets no program or claim rows and cannot create a claim. Run the approved browser flow with the same database candidate, including hiding the page for an individual rep.

The database PR includes `20270314170000_validate_rebate_claim_links.sql`, the migration record, a changelog note and the isolated database prover. It requires Luna, Opus and Sol pre-PR reviews. The screen PR includes the Rebates route and controls, readable link-error messages and tests.
