**Words used below.** The grand plan's words (stage, package, migration, RPC, retry key, harness, 💲) mean the same here. Also:
- *Parent*: one exact formulation. Its sizes are ordinary product rows.
- *Size*: one product row (2.5-gal jug, 265-gal tote, Bulk, 5-lb bag). Product IDs never change.
- *Copied value*: a value the parent owns and the database copies onto every size in the same step, so every existing screen keeps reading it from the size row.
- *Pass*: a row in a small private table, keyed by the current transaction, that one trusted database function writes so a guard knows the write came from it. The rate lock already works this way (`product_rate_correction_passes`).

## 2. Corrections to the grand plan, from current code

1. **`pricing_version` and parent edits.** PAR-1's draft "Done when" says a price edit's `pricing_version` check is unaffected by a parent edit made at the same time. That holds for a category change only. A parent Use Timing or rate change copies down and bumps each size's `pricing_version` by the existing guard, because those values feed the price sheet and per-acre prices. So a concurrent price edit is refused as stale and must reload. That is the safe direction and is kept; the "Done when" below is reworded to match.
2. **Brands are empty.** The grand plan's staged brand move (overlap 13) assumed brand lists to reconcile. Live has 0 brand rows, so PAR-2's brand step starts from zero today. The move mechanism is still built, because brands may be typed before PAR-2 runs (section 5.1). Brand PR B's planned `(product_id, brand_id)` delivery reference (`2026-10-22-product-brands-step1-PLAN.md` §4) is redesigned against parent brands before PR B starts.
3. **`ingredient_map` is empty.** DM-1's "old page read-only" step turns off writes to an empty table; nothing is lost.
4. **No `products` column is added.** The grand plan left open where membership lives. A new membership table keeps every grant routine (section 3, rule 2), and keeps `PRODUCT_COLUMNS` unchanged.
5. **BLK-1b is parked** with the inventory-costing roadmap (D12).
6. **Every product gets a parent, including a one-size product.** Weight per gallon and chemistry are stored per parent, so a product with one size needs a parent of one. PAR-2 proposes single-size parents too. Until a product has a parent it keeps today's behaviour.
7. **The blend checker no longer adds gallons to pounds.** DM-2's "fixes C-39" is already half done: `validateBlendMath` reports a mixed total as "not checked" instead. DM-2 makes it a checked total once weights exist.
8. **The price workbook is a Use Timing writer.** Its rate columns are read-only since 11a-1, but its Use Timing, quote-notes and internal-notes cells are still editable. PAR-1 makes its Use Timing cell read-only for grouped sizes.
9. **An established product form is not correctable in place.** `guard_product_setup_fields` refuses changing a saved product's non-blank form, stock unit or container unit (it allows filling a blank one, `20261102102000:108-113`). Every active product already has a form (DM-0 gate). So the identity correction never changes form; a size of the wrong form is a misgrouping and moves.
10. **No category rename exists.** `upsert_product_category` adds or retires categories but has no rename (`20261102102000:169-211`); the foreign key's `ON UPDATE CASCADE` only matters for a hand-run rename. PAR-1 gives the parent's category foreign key `ON UPDATE RESTRICT`, so such a rename is refused while a parent uses the category instead of silently splitting a parent from its sizes.
11. **Shop-filled totes are fertilizer only.** Mason settled on 2026-11-04 (inventory-costing planning) that chemical totes are stocked already filled and bulk storage exists only for fertilizer. BLK-1a is therefore scoped to fertilizer totes, and PAR-2 defaults chemical totes to vendor-filled packages.
12. **Quote lines do not store category or Use Timing**, so they are not a snapshot that protects old quotes from a parent change; old-record readers are traced in PAR-1 (section 4.1).

## 3. Rules for every Stage 2 package

Every package inherits the Stage 1 build sheet's section 1 rules and the grand plan's section 3 rules. In short, and with Stage 2 specifics:

1. **One package, two PRs, database first** (`docs/workflows/DATABASE_CHANGE_CHECKLIST.md`, migration-plus-callers); REG-1 is the one exception, with four (section 7.3). The database PR lands and is applied before the screen PR merges.
2. **New tables follow the `product_brands` lock-down**: RLS on, no direct write for any role, writes only through admin-checked `SECURITY DEFINER` RPCs with `SET search_path = public, pg_temp`. Reads are by `is_active_profile()` unless the package says admin-only. Grants on new objects are routine for the apply gate; any grant, revoke or policy change on an **existing** table or `products` column needs Mason's `I approve`, and each package says whether it has one.
3. **Every mutating RPC** requires `p_idempotency_key`, checks the caller before the replay lookup, and copies the replay pattern in `20261022086500_product_brands.sql:162-269` (refuses a NULL key, fingerprints the request, binds the receipt). The proof includes an unauthorized call that writes nothing, a replay that writes once and the same key with a different request refused. When one RPC calls another writer, it calls a private helper (no grant, no key of its own) inside the same transaction, so the outer key covers the whole request and a replay of a partly failed request cannot write twice.
4. **Copied values are written only by the parent's own functions.** A guard on `products` refuses a change to a copied column on a grouped size unless a pass row exists for this transaction and that size. Only parent functions write pass rows; no app role can read or write the pass table. **Each pass is inserted immediately before its one governed write and deleted immediately after it**, as `correct_product_rates` does (`20261107060000:745-747`), so a later write in the same transaction is refused.
5. **The rate lock is never bypassed.** A parent rate change while locked goes only through the one-parent correction. Grouping that would change a live rate waits for that correction or for a logged unlock (overlap 11).
6. **Money stays in exact whole cents.** The per-acre price columns are legacy dollar `numeric`, rounded as today under the legacy exception in `docs/workflows/SAFE_DEVELOPMENT_RULES.md`. New money arithmetic (cost per lb of active, BLK-1a's catalog estimate) states its unit factors and rounds once, at the end, to the cent.
7. **Proof is local.** Database behaviour is proven in the schema-matched harness with seeded edge cases; the app is observed against the private test copy (WP-PM-0, `scripts/local-app/`). A flow the test copy cannot run is recorded as owed, never passed. Live checks are read-only unless Mason approves the exact live test in that conversation.
8. **Real product rows stay private.** Proposal lists, disagreement lists, tote answers and baselines go to `C:\Users\mason\Documents\Obsidian Vault\Products\Product Master review\`, never into this repo, a PR or a report. The repo carries counts and status.
9. **Every database PR delivers:** the migration, its ledger record (`docs/changelog.d/<date>-<slug>.md`), a migration record (`docs/reference/migrations.d/<stamp>_<slug>.md`), a harness proof script with named cases (`scripts/smoke/prove-<slug>-real-schema.mjs`, as 11a-2 does), a rollback section in the migration header, `docs/reference/rpc-functions.md` entries, updated `src/types/index.ts` and `src/types/supabase.ts`, the schema registry refresh after apply, the live function snapshot entries, and the post-apply `npm run db-sweeps:live`. Every screen PR delivers component tests and the observed-flow notes.
10. **Sol.** Whether a PR needs Sol is decided by its final file list against `docs/reference/sol-required-paths.md`. Every database PR does (`supabase/`); most screen PRs will, because they touch `ProductDetail.tsx`, `Products.tsx`, `BulkProductImport.tsx` or inventory files. Each migration also needs its exact-head Sol proof before apply (`.claude/commands/ship.md`).
11. **Live data steps are Mason's.** A migration or RPC run that writes live catalog rows (PAR-2 approvals, REG-1's reconciled label facts, drafted weights and chemistry) needs his review of the private list and his go at the time. A destructive change needs his explicit approval for that exact change. Routine mechanism migrations (new objects, no live rows written) apply under the autonomous-landing rule.

## 4. PAR-1 · Parent record per formulation, plus nickname

**Goal.** One parent record holds the values that are the same for every size of a formulation. Each size keeps its ID, price, SKU, stock, vendor links and return policy. Every existing screen keeps working, because the parent copies its values onto the size rows and those copies cannot be changed on their own.

**What the parent owns.**

| Kind | Values | Where they live |
|---|---|---|
| **Copied onto every size** | `category`; `use_timings` (and `use_timing`, kept in step by its trigger); `rate_per_acre`, `rate_unit`, `suggested_rate` | parent row, copied to `products` |
| **Parent only, editable** | name, nickname | parent row |
| **Parent identity** (set when the parent is created; changed only by the correction) | product form, formulation type, safener, the generic EPA number | parent row; the EPA number is also on each size's `epa_registration` |
| Added later | weight per gallon (DM-2), ingredients and strength (DM-1) | their own tables |

**Stay on each size:** name, SKU, container size, unit and type, prices, cost, stock, reorder point, vendor links, return policy, notes, quoting notes, internal notes, manufacturer, and, until REG-1, the label facts. Quoting notes often name the size ("2x2.5 gal case") and four shared EPA numbers already show different manufacturers per size, so both stay per size; they can move up later if Mason finds himself typing the same note on every size.

**Every product gets a parent eventually**, including one sold in a single size, because weight and chemistry are stored per parent. Until a product has a parent it behaves exactly as today.

### 4.1 Database PR: migration `<stamp>_product_parents`

**New tables** (RLS on; `SELECT` for active users through a policy; no write grants):
- `product_parents`: `id uuid`; `name text` (not blank; unique among active parents, ignoring case); `nickname text` (optional, trimmed); `product_form text` (not null, one of the `products.product_form` values); `formulation_type text`, `safener text` (nullable; blank means unknown, never guessed); `generic_epa_registration text` (normalized: trimmed, spaces removed, upper case; nullable); the copied values `category` (FK to `product_categories`, `ON UPDATE RESTRICT`), `use_timings text[]`, `rate_per_acre`, `rate_unit`, `suggested_rate`; `parent_version bigint` (moved only by the database); `is_active`; `created_by`, `created_at`, `updated_by`, `updated_at`.
- `product_parent_members`: `product_id uuid` primary key (a size has one parent at most); `parent_id`; `size_role` in (`package`, `bulk`, `fixed_tote`); `fill_source_product_id uuid` (shop-filled fixed totes only; PAR-2 sets it); `added_by`, `added_at`. A partial unique index allows one `bulk` row per parent. A trigger refuses a fill source that is not the `bulk` member of the same parent, and refuses moving or removing a `bulk` row that is a fill source until the tote's source is cleared or replaced.
- `product_parent_events`: append-only (update and delete refused, like `product_rate_events`). `id bigint`; `parent_id`; `event_type` in (`created`, `updated`, `size_added`, `size_moved`, `identity_corrected`, `rates_set`, `rates_corrected`); `reason`; `evidence`; `before_values jsonb`, `after_values jsonb`; `affected jsonb` (per size: product ID, before and after of each copied value); `changed_by` and `changed_by_name` from the database session; `changed_at`.
- `product_parent_copy_passes(txid bigint, product_id uuid, parent_event_id bigint)`: private, no grants.
- `product_grouping_state`: one row, `grouping_version bigint`, moved by every membership change.
- `product_parent_settings`: one row, `epa_correction_enabled boolean` (default false; no write grant, changed only by a migration).

**Changes to existing objects (no grant or policy change):**
- `product_change_history` gains nullable `parent_event_id bigint`. Its `SELECT` is a table-level grant (checked live), so the new column is readable with no new grant. The `change_type` CHECK becomes the superset (`created`, `updated`, `parent_copy`) and the field-name CHECK treats `parent_copy` like `updated`. `write_product_change_history` is re-issued from its latest definition (`20261102100000`) with one change: when a pass row exists for the size, its entries are `parent_copy` and carry the pass's `parent_event_id`. One parent edit is then one event row, and every size entry it caused carries that event's ID. `src/types/index.ts` (`ProductChangeHistoryEntry`, `:475-478`) and `ProductChangeHistory.tsx` (`:78-92`) show `parent_copy` entries as "Changed on parent <name>".
- **Guards on `products`** (new `BEFORE UPDATE` trigger functions, `SECURITY DEFINER` with `search_path` pinned and owned by `postgres`, like `guard_product_rate_lock`, so a direct app update reads the private pass table and gets the parent message, not a permission error):
  - `trigger_zz_guard_product_parent_values`: on a grouped size, a change to `category`, `use_timings`, `use_timing`, `rate_per_acre`, `rate_unit` or `suggested_rate` is refused unless a pass row exists: `PRODUCT_PARENT_VALUE: <column> belongs to parent "<name>"; edit it on the parent (reload the app if you do not see a Parent panel)`. The reload hint is in the database message because an already-open old page shows the error text as it is. An update that leaves those values as they are is never refused, so an old editor that resends unchanged values keeps working.
  - `trigger_zz_guard_product_parent_identity`: on a grouped size, a change to the normalized `epa_registration` is refused unless a pass row exists. Form needs no new guard (section 2, item 9).

The harness proves the multi-timing old-workbook case and a grouped old-client category change that leaves timings in place.

The harness reads the order back from `pg_trigger` and checks each refusal's text.

**RPCs** (all `SECURITY DEFINER`, `search_path = public, pg_temp`; `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role`, then `GRANT EXECUTE … TO authenticated` for the public ones; helpers get no grant). **Every mutating RPC** is admin-only, checked before the replay lookup, and requires a retry key. **Previews** are admin-only and read-only. **The two reads** (`get_product_parents`, `search_product_parents`) are open to every active user, take no key, and return no cost or price.
- `create_product_with_parent(p_parent jsonb, p_size jsonb, p_idempotency_key)`: **"New product"**. In one transaction, inserts the new product row and a new parent and makes the row its first member. The parent's identity fields are entered here. The insert goes through the setup insert path that PM-10 lands (one product-setup write path); if that path is not on `main` when PAR-1 is built, PAR-1 stops and re-plans this call and `add_product_size` together rather than adding a second insert path (`apply_product_setup` from 11a-2, now on `main`, only updates existing rows). **While locked**, a new product cannot carry a rate (the existing lock rule for inserts).
- `add_product_size(p_parent_id, p_expected_parent_version, p_size jsonb, p_idempotency_key)`: **"Add a size"**. Generates the new product ID first, inserts pass rows for that ID in both `product_parent_copy_passes` and `product_rate_correction_passes`, inserts the row through the same PM-10 setup insert path (same condition as above) with the parent's copied values (rate included), adds the member, deletes both passes. So while locked the new size takes exactly the parent's unchanged rate; a `p_size` that carries any rate, category or Use Timing of its own is refused. Refused if the size's form differs from the parent's or its normalized EPA number is set and differs.
- `update_product_parent(p_parent_id, p_expected_parent_version, p_changes jsonb, p_reason, p_idempotency_key)`: changes **name, nickname, category and Use Timing only**. Identity fields are refused here (they use the correction). Locks the parent, then its sizes in product-ID order; refuses a stale version by name; writes one event, then each size's copy under its own pass. The copy is an ordinary update, so the existing category and timing checks run on every size. **Category change:** when the new category does not allow the current timings (timings exist only on Herbicide and Foliar Fertilizer, DECISION_LOG 2026-10-28; `20261103210000:166-170`), the call must carry `use_timings: []` and the screen asks Mason to confirm the clear first; without it the call is refused.
- `preview_parent_rates(p_parent_id, p_rate_per_acre, p_rate_unit, p_suggested_rate)`: read-only, admin. For each size: its `pricing_version`, current rate and tier 1–3 per-acre prices, and the new per-acre prices from `preview_product_rate_correction`, so preview and save use the same math.
- `set_parent_rates(p_rows jsonb, p_performed_by uuid, p_idempotency_key)`: the parent version of `set_product_rates`. Each row carries `parent_id`, `expected_parent_version`, the new rate, unit and suggested rate, and **the preview snapshot for every size**: its `pricing_version`, `unit_size`, `inventory_unit`, `product_form`, old rate and previewed new per-acre prices, the same inputs `set_product_rates` checks (`20261107060000:445-467`). It takes the rate lock `FOR SHARE` as `set_product_rates` does, so it is refused while locked and cannot race the switch. It checks every size's snapshot against the locked row and refuses the whole call on any difference, then writes the parent and each size through `_write_product_rates` under its pass. After each write it compares the recalculated per-acre prices with the previewed ones and raises on a mismatch, so the whole call rolls back, as `set_product_rates` does (`:535-555`). Like `set_product_rates`, it writes no `product_rate_events` row (those are for lock switches and corrections); the parent event and the size history record it.

**Goal.** The app proposes groups for today's products, Mason approves groups as shown, and approved groups become parents. Nothing about a size's ID, units, stock, prices or history changes.

### 5.1 Database PR: migration `<stamp>_product_parent_proposals`

**New tables** (RLS on; **reads admin-only** through `is_admin()` policies, because proposals carry review data; no write grants):
- `product_parent_proposals`: `id`, `proposal_version`, `status` (`open`, `superseded`, `closed`), `built_by`, `built_at`.
- `product_parent_proposal_groups`: `id`, `proposal_id`, `suggested_name`, `product_form`, `generic_epa_registration`, `identity_basis` (`epa_number` or `owner_confirmed`), `members jsonb`, `conflicts jsonb`, `flags jsonb`, `group_fingerprint`, `status` (`proposed`, `approved`, `rejected`, `held`), `decided_by`, `decided_at`, `reason`. The JSON fields hold only this allow-list per member: product ID, name, SKU, form, container size and unit, inventory unit, active flag, category, Use Timing, the three rate fields, EPA number, manufacturer, suggested size role, brand list summary. No cost, price or stock.
- `product_parent_brands`: the parent's brand list (section "Brands" below): `id`, `parent_id`, `brand_name`, `epa_registration`, `manufacturer`, `is_currently_sourced`, `is_rup`, `signal_word`, `row_version`, `status` (`active` or `retired`; `retired` is final and set only at approval or by `upsert_parent_brand` with a reason), `legacy_brand_ids uuid[]`, who and when. Every change appends a row to `product_parent_brand_events` (old and new values, who, when, reason; active-user reads, no write grant). A **partial** unique index on (`parent_id`, lower `brand_name`) `WHERE status = 'active'`, so a retired variant can keep the same name. Readers, pickers and delivery choices show active rows only. Reads for active users.

**How groups are proposed** (`build_product_parent_proposal(p_idempotency_key)`, admin):
- **Members:** every product without a parent, active and inactive (inactive ones are flagged, so they get a parent before anyone reactivates them; reactivation itself does not require one).
- **Base name:** the name with size and container words removed (a fixed list in the function: volumes and weights with units, `jug`, `case`, `bulk`, `tote`, `bag`, `box`, pack counts). Quality, formulation and strength words are never removed ("Higher Quality", "Ester", "Amine", "safened", "4L", percentages). A volume is removed only when written as a size (a number, a space or none, and a unit word from the list, standing apart from the name, such as "2.5 gal"); a token that could be either ("4L") stays, and names that differ only by such a token are held for review.
- **Grouped only when** base name and form match, seed or each members share one stock unit, and no two members carry *different* normalized EPA numbers. Same EPA number with a different base name is a flag, never a merge, so `Gen Liberty` and `Gen Liberty: Higher Quality` stay apart.
- **Identity basis, recorded on every approved group:**
  - `epa_number`: every member carries the same EPA number. One registration is one registered formulation, so the label is the identity; Mason still approves the group as shown, with any flag (manufacturer differs, strength or quality words differ) resolved first.
  - `owner_confirmed`: no member has an EPA number. Approval needs Mason's explicit "same product" tick for that group.
  - **Mixed:** some members have the number and some are blank. The group is proposed but **held**, flagged "fill the missing EPA numbers first"; the blanks are filled by the ordinary product edit (DATA-2), and the next proposal groups them under `epa_number`. So every grouped size carries its parent's EPA number, or none does.
  - A group whose formulation cannot be told from the data (for example strength missing from the names of products that could differ) is held, not guessed.
- **Single-size groups** are proposed too. **Size role:** Bulk by name or container is the `bulk` candidate, a tote is a `fixed_tote` candidate, everything else `package`; two Bulk candidates is a flag.
- A new proposal supersedes the open one.

**Approval** (`approve_product_parent_groups(p_proposal_id, p_proposal_version, p_groups jsonb, p_idempotency_key)`, admin): each entry carries `group_id`, `group_fingerprint`, the final parent name (the preview suggests the base name, adding the form or EPA number when another active or proposed parent already uses it, since parent names are unique), the chosen value for every conflict, the `owner_confirmed` tick where needed, size roles, and for each fixed tote whether it is shop-filled and its Bulk source. In one transaction it:
1. locks every member row in product-ID order (`FOR UPDATE`); the re-issued `upsert_product_brand` and the new `upsert_parent_brand` take the same product-row lock (for a parent, every member row in ID order) before they read or write a brand, so a brand insert or edit cannot slip between the check and the move;
2. **recomputes each group's fingerprint and conflicts from the locked current rows, including each member's complete brand set**, and refuses the whole call if any group changed since the download (a rate, EPA number, category, timing, active flag or brand changed), if a member now has a parent, or if the proposal version moved;
3. refuses a conflict with no chosen value, two Bulk rows, a shop-filled tote without a same-parent Bulk source or outside a fertilizer category, and, while locked, any chosen rate that differs from a member's live rate;
4. also recomputes, for each member whose rate changes, its new tier 1–3 per-acre prices, and refuses if they differ from what the approval screen showed (the approval entry carries them); the screen also lists each changing member's open lines, informational as in section 4.1;
5. creates each parent and its members through the same internal step `create_product_with_parent` and `add_product_size` use, writing copied values under passes, one parent event per group;
6. moves brands (below) and marks each group `approved`.
**There is no other way to group existing rows**: PAR-1's public RPCs create new rows only, so nothing existing is grouped without this approval.

`hold_product_parent_group(p_group_id, p_expected_proposal_version, p_group_fingerprint, p_reason, p_idempotency_key)` and `reject_product_parent_group(...)` with the same arguments keep a group out with a reason: admin, retry key, authorization before replay, refused when the proposal or the group changed, a repeat returns the first result. Held and rejected products keep today's behaviour; a new proposal may propose them again. **Review fixes (3a, `20261201110000`):** a new proposal carries a rejection (reason, who, when) while the group's sizes are unchanged and proposes it again, with the earlier rejection named, once one changes; it holds a group whose EPA number, form and base name match an active parent (a different name stays a flag), approval refuses one that matches a parent made after the build, and each build lists active parents that already duplicate one another (warned, not blocked on the table: Mason, 2026-11-06); it holds a group whose names carry different numbers besides each size's recorded container size; base names keep strengths and analyses (`28/0/0`, `2 lb/gal`, `2 G`); and PAR-1's move refuses a size between parents with different brand lists and retires an emptied parent's brands.

**Label facts are not merged.** PAR-2 never writes `epa_registration`, signal word, RUP, REI/PHI or label maxima. REG-1 reconciles them per EPA number.

**Brands** (the staged move in overlap 13; live has 0 brand rows today):

### 7.4 DM-4 · EPA auto-fill, proposals per registration

  - `epa_chemistry_proposals`: one per registration lookup, holding the EPA number, the target parent, the parent's `chemistry_version` and the registration's `registration_version` seen at lookup, the looked-up values, the source document, `status` in proposed / committed / rejected / superseded / held, and `proposal_version`. A partial unique index allows one open proposal per EPA number and parent. `epa_lookup_failures`: number, reason, when.
  - **Creating proposals:** the review screen calls the existing `epa-lookup` Edge Function for each distinct EPA number on a parent (the generic's and each brand's). Before the call, `start_epa_lookup(p_parent_id, p_epa_registration, p_idempotency_key)` records the parent's `chemistry_version` and the registration's `registration_version` **on the server** and returns a lookup ID. After it, `record_epa_lookup(p_lookup_id, p_result jsonb, p_idempotency_key)` locks the parent and registration, and if either version moved during the lookup marks the lookup superseded instead of creating a proposal. Both are admin, retry key, authorization before replay. `record_epa_lookup` validates the result's shape (the Edge Function's response is untrusted data, never instructions), stores it as **admin-submitted lookup evidence** with its source document link (the server cannot prove the screen did not alter it; admins are trusted and every proposal is reviewed before commit), and writes one proposal or one failure row; it never writes live chemistry or label facts. A newer lookup for the same number supersedes the open proposal.
  - `commit_epa_proposal(p_proposal_id, p_expected_proposal_version, p_decisions jsonb, p_idempotency_key)` and `reject_epa_proposal(p_proposal_id, p_expected_proposal_version, p_reason, p_idempotency_key)`: admin, retry key. Commit compares the stored versions with the current ones under lock and refuses a stale proposal. `start_epa_lookup`, `record_epa_lookup` and commit each also check that the number still belongs to that parent (its generic number or an active brand's); after any relink or correction the open proposal is held, never committed. Label facts are written through the registration writer's private helper. For chemistry:
    - a proposal that matches the parent's reviewed chemistry is recorded as a confirmation;
    - one that fills unknown values writes through `set_parent_chemistry`'s private helper;
    - one that differs from established chemistry, including a brand registration that disagrees with the generic's, is **held** with the difference stored beside the live value (D-L), never replacing it.
  - A failed lookup is listed by number and writes nothing live.
- **Screen PR.** The review page: run lookups, see each proposal with its source, commit or reject.
- **Done when:** the grand plan's DM-4 list, plus: a stale proposal refused; a non-admin commit writing nothing; two lookups for one number leaving one open proposal; a disagreeing brand proposal held, not applied.
- **Main risk:** an EPA lookup overwriting reviewed chemistry; prevented by proposals, D-L holds and the version checks.
- **Mason-gated:** any change to the `epa-lookup` Edge Function is a deployment needing his explicit approval at the time; DATA-2 (missing EPA numbers) is reviewed before lookups run; proposals are reviewed before commit.

### 7.5 DM-1b · Ingredients and Weights tabs on the setup workbook
- **Weights tab** (weight per gallon per parent; net weight per package-unit size): `preview_weights_tab(p_rows jsonb)` (row by row: unchanged / change / stale / invalid, each with its source) and `commit_weights_tab(p_rows jsonb, p_idempotency_key)` (admin, all-or-nothing, each row's fingerprint and expected version checked under lock). Commit saves through DM-2's private writer helpers as `draft` (DM-2's review gate), returns the exact saved rows, and refuses a row with no source.
- **Ingredients tab:** `preview_ingredients_tab(p_rows jsonb)` and `commit_ingredients_tab(p_rows jsonb, p_idempotency_key)`. Each row carries the parent, its expected `chemistry_version` and the row fingerprint from the download. **Commit writes proposals, not live chemistry** (grand plan §6 DM-1b: "an upload lands as proposals, each value citing its source document"), into `chemistry_change_proposals` (target parent, the parent's set of EPA numbers and their versions at upload, row, kind add / change / delete, source, `proposal_version`, the `chemistry_version` it was based on, status).
- `promote_chemistry_proposal(p_proposal_id, p_expected_proposal_version, p_decision, p_idempotency_key)` (admin, retry key): `p_decision` is one of `apply`, `apply_delete` or `reject`; `apply_delete` is required for a delete proposal and refused for any other, and `apply` is refused for a delete proposal. It refuses a proposal whose base `chemistry_version` is no longer current and does nothing on a repeat. It applies through a private helper `_apply_chemistry_proposal` (no grant), which re-checks the proposal's review, decision and base version, and for a parent with EPA numbers also checks eligibility **across every usable number on the parent** (the generic's and each active brand's): each must have a failed lookup whose attempt is bound to the number's current `registration_version` and its current link to this parent, with no later successful lookup, open proposal or committed proposal for it. A failure on one number never unlocks chemistry while another number has a reviewed or pending result; only then does it write through the chemistry writers' private helpers. The public `set_parent_chemistry` keeps refusing EPA-bearing parents. A promoted delete retires the chemistry row (kept with its history, never hard-deleted), so no data is lost. An absent row changes nothing.
- A parent with any usable EPA number has its workbook chemistry refused by name, with the reviewed manual-proposal path when its lookup failed (D-Z per registration).

- **Main risk:** an upload deleting or replacing chemistry without review; prevented by proposals and the explicit `apply_delete`.
