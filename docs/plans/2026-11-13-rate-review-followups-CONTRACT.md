# Rate review follow-ups — behavior contract (2026-11-13)

Read at `origin/staging` `36e535557`: issues #1831 (visible Rate Outcomes name must match its hidden download name), #1829 (recover unanswered Confirm after leaving Products), #1826 (allow the same upload to re-set an outcome cleared by its rate edits); `src/lib/rateReviewWorkbook.ts`, `src/components/products/RateReviewWorkbookModal.tsx`, `src/lib/pendingRetry.ts`, and `supabase/migrations/20270104110000_product_rate_review.sql`. This refines the RT-3 contract for these three fixes only.

## Outcome and authority

- A downloaded Rate Outcomes parent name must still name the parent in that row's hidden download record. A changed visible name refuses the upload before any preview or save. New Draft Rates still select a parent by the visible Rate Outcomes name, case-insensitively; duplicate names remain ambiguous. Bump the workbook format, so old files without the binding ask for a fresh download.
- If an edited rate clears a recorded nonblank outcome, the same upload may set that outcome again when the admin marks `reconfirm` = yes on Rate Outcomes. The parser sends the downloaded outcome **and note** with its downloaded version, even when those cells are unchanged. Without that explicit choice, the rate change clears the outcome as today and the preview warns. A changed outcome or note is sent once through the normal edit path. `reconfirm` = yes is refused when the downloaded outcome was blank, either visible outcome or note also changed, or no rate on that parent was edited in the upload; the row message names the conflicting or unnecessary choice. This fail-closed rule gives no hidden precedence to contradictory spreadsheet instructions. The existing server saves rates first and checks the outcome version captured under its parent lock before those rates; it then rechecks the requested outcome against the resulting rates. A failed validation refuses the whole commit. Reconfirm makes the uploader the latest decider, with a new event; the old decision remains in event history.
- An admin's unanswered Confirm keeps the exact parsed upload, preview and idempotency key in this tab's session storage (`rate-review:<profile id>` via `pendingRetry`), scoped to the signed-in profile. On return, label the preview as the picture shown at the first Confirm, show its age, and offer an explicit retry with the saved payload and key. Never send on mount. The modal checks for a stored pending entry before every new send and blocks other uploads while one is unresolved. If the profile ID is missing or storage fails, refuse the initial send with a usable message; a large review can be split into smaller uploads. After the client-side 24-hour window, refuse replay and ask for manual checking; keep the record visible until the admin explicitly clears it after checking a fresh download against the pending rows.
- Only the admin who made the original request may see and retry its saved intent. `commit_rate_review` derives the actor from auth, requires admin, binds the key to actor and payload, and rechecks all rows. The browser's row IDs and versions are locators and concurrency checks, not authority.
- Files: the existing workbook module and modal, their focused tests, this contract and a brief rollout note. A planning pilot row follows when the work closes. No schema or shared retry-helper changes. RT-3 migration is already in the staging base; no new database delivery is needed. A later PR targets `staging`; no push or PR in this task.

## State and failure

- The modal writes the pending record before calling `commit_rate_review`. It clears that record only after a receipt, or a definitive first-send refusal that guarantees nothing saved. `IDEMPOTENCY_*` never counts as such a refusal. After any unanswered send, every further refusal keeps a valid record for a hand check unless the original receipt is returned. Leaving Products, reloading, and a later upload in the same tab cannot silently retire a valid record. Closing the browser tab discards `sessionStorage`; recovery after tab closure is outside issue #1829.
- A repeated Confirm uses the same key and exact payload. The server returns the first receipt if it committed, or executes once if the first request never arrived. A stale or invalid row refuses the whole transaction. Concurrent admins serialize on parent locks; the losing version is stale. Preview is advisory, and retry never refreshes it into a new intent.
- `pendingRetry` uses the browser clock to refuse replay after 24 hours. Clock skew can make that estimate wrong; the server's version and uniqueness checks prevent an expired receipt from silently repeating a rate edit, but the screen may need a manual check if the old receipt is gone. A missing or corrupt stored record cannot be used to replay. Workbook files and retry records stay in the browser tab; no email, file or external effect is added. Rate and outcome event history remains the server's append-only history.
- **Deferred MED, tracked in #1829:** the shared `pendingRetry` helper removes a corrupt or invalid session-storage record when loading it. The modal then cannot tell that an unanswered Confirm existed and may accept a later upload without a manual check. The exact old payload and receipt are unrecoverable from that damaged record; the server's row versions and uniqueness rules prevent a known repeat write, but the operator may need a fresh workbook to settle what saved. A follow-up should surface a durable "retry record unavailable" state and block new uploads until an explicit check. This change leaves the shared helper untouched.
- Issue #1829 remains open; PR #1867 closes only #1831 and #1826. It also retains the LOW usability follow-up of allowing an earlier explicit manual check after repeated uncertain network failures. This change preserves the agreed safe-retry window: an unexpired unanswered request keeps its original retry key, and the hand-check exit appears on expiry, a missing retry record or an unsafe/refused receipt.
- Issue #1829 also tracks a missing-reminder case involving an overlapping refused attempt and an unanswered retry. A fresh workbook can settle that result; the server's payload, version and uniqueness checks still prevent a repeated write. Retiring a request after its matching success receipt is intentional; an old unmounted callback must not resurrect a reminder the admin already retired.
- New code and old app can coexist: this frontend-only change uses the existing RT-3 RPCs. Old downloaded workbook format is deliberately refused with an accurate "older workbook" fresh-download instruction; in-progress v1 edits must be copied to a fresh download.

## Proof cases

1. Real ExcelJS round trip: swap a visible Rate Outcomes parent name but leave its hidden state; parse refuses. An unmodified v2 file parses, and a new Draft Rates row still resolves a case-insensitive unique name. Old v1 format refuses.
2. Real ExcelJS round trip: change one rate on a parent with a recorded outcome, leave outcome cells alone; parse does not send that outcome and preview warns it will clear. Mark Reconfirm yes; parse sends the old outcome and note once with its downloaded version. Changing the outcome/note without Reconfirm sends the edited row once. Reconfirm with an edited outcome/note, blank downloaded outcome, or no edited rate on that parent is refused by name. Preview and commit use the same parsed rows.
3. Real migrated database (Docker prover) with synthetic rows: changing a rate and re-setting its old outcome in one upload succeeds only if the resulting rates meet the outcome rule; a stale version or invalid outcome refuses the entire upload. No production writes.
4. Component/browser path: after a lost Confirm reply, unmount/remount Products and reopen Rate Review; the original preview appears, no RPC runs automatically, and explicit Confirm reuses the original payload/key and shows its receipt.
5. Component/browser path: while that intent is unresolved, a different upload cannot overwrite it. At/after expiry, Confirm refuses replay and the intent remains visible. Storage failure or missing profile refuses the initial Confirm. A different actor never sees the prior actor's record. An idempotency mismatch retains the intent for a hand check.

## Business decision

Mason chose explicit Reconfirm on 2026-11-13. Issue #1826 asks that a single upload be *able* to set again an outcome cleared by a rate edit. An unchanged outcome cell alone does not show a new decision, so it leaves the outcome cleared; `reconfirm` = yes deliberately sends the prior outcome and note for validation after the rate edits. Conflicting cells are refused rather than guessed (technical resolution of the targeted challenge's M3).
