# Credit-limit notices after New Order saves

Reviewed against staging `de2fad0fec13f4816c843730474b84092d00b82e`. This contract covers ordinary New Order. Both quote conversion screens and the shared job warning keep their current paths for this unit.

## Business behavior

- Keep both existing credit rules. The pre-save warning considers the proposed order. After an ordinary order commits, the customer credit check warns only when the current eligible outstanding balance exceeds the customer's positive credit limit. Eligible invoices remain posted, overdue or unposted and not deleted. Rush orders keep their current behavior.
- A checked ordinary save can cause one notice per active admin. Use the customer identified by the successful original save, even if a later edit changes the order. This matches the existing screen's saved customer snapshot. The signed-in actor supplies neither text, recipient, customer nor amount to the alert operation.
- Rep and admin save permissions, exact amounts, pricing approval and the existing order receipt behavior stay in the existing save operation. A notice failure must leave the saved order and the user's existing warning path available.

## Mechanism and rollout

- Add an ordinary order wrapper that shares the existing per-key lock and delegates to `create_direct_order` for all save and validation behavior. The wrapper checks for an unexpired existing receipt under that lock. Only a new successful save through this wrapper can carry an alert authorization marker on its actor-bound order receipt. Pin its customer at that point. Keep this metadata available for the existing 24-hour receipt window. The wrapper adds no separate save authorization check. If recording the optional marker fails, report the technical failure and leave the success result available. A missing marker means the checked notice operation has nothing to send.
- New Order calls a second operation after the save, using its original key. The operation requires an active office user and an unexpired, actor-bound ordinary order receipt with a marker. Lock the receipt row before reading or changing notice delivery state. Derive the original customer from the checked marker. Compute the warning with the existing credit check and return it to the currently authorized caller. Store only marker and delivery state in the order receipt. Keep the balance, credit limit, and farm name out of that receipt and all legacy recovery responses. A duplicate can return a freshly checked balance while exact retries cannot send again after a decided outcome.
- A successful send or a completed under-limit check consumes the notice. A notice insert failure returns the warning and a technical failure flag without consuming the right to retry. Use the existing notification failure logging on the screen. Let query cancellation unwind the separate notice transaction. The order is already saved. If the alert read is unavailable or the marker is missing, the screen may use the existing authorized read-only credit check for its warning. Keep the old direct send out of the new screen and keep order navigation working.
- Both new mutations accept and enforce `p_idempotency_key text DEFAULT NULL`; document the same-key receipt reuse for the applicable idempotency check. Scope the new entry points to authenticated browser callers. The original save keeps its existing signature, grants and required result fields. Old callers that retry a new save can get nonfinancial workflow metadata in the result. The ordinary screen keeps the key in memory, so a refreshed client does not inherit it. Do not deduplicate old customer-only notices by matching text or recipients.
- The database operations ship first. Keep them installed through an application rollback so cached clients can still save. Later removal of the old direct send fits the separate application PR. Global browser notification writes stay until all valid notice paths have migrated.

## Required local proof

- Authorized admin and sales rep save normally. Driver, inactive profile, wrong actor, absent key, wrong operation, expired key and legacy receipt cannot create a notice. Confirm local privileges deny direct changes to the underlying receipt.
- Two transactions racing on a save or notice produce one order per original save and one notice per eligible admin. Separate orders for the same farm each alert. The active-admin set matches the current notice. A legacy first save gets no new alert permission. A changed or stale recovery cannot expose a balance after the actor loses office access.
- Exact financial check and formatted alert golden cases include $1,000.01 against $1,000.00, equality, a nonpositive limit, negative balances, ignored drafts and voided or deleted rows. If an order changes before its alert, the original customer is used. Verify the title, actor and destination.
- Force a marker failure, notification insert failure, and cancelled notice query independently. Order save remains available. The screen records failure and retains the normal warning and navigation. Real browser proof covers a lost save response, a lost notice response, and re-opening the saved order as an eligible rep. No direct browser notice write occurs on the new workflow.

## Observed and unresolved

The original contract got a cold review. A targeted Opus review on this staging source found no blocker or high finding for the shared-lock and actor-bound authority. Its two medium findings concerned conflicting contract language and the need to log notice failures. The previous multi-path wording is superseded by this single mechanism. The test prototype's cached failure and financial snapshot are deliberately excluded from production. That also addresses the old-path display risk if the actor later loses office access. Keeping the original customer and the existing threshold preserves the current business result. Any proposed expansion of recipient or threshold rules remains separate.

The sealed Docker lane rebuilt 416 migrations and 1,339 ledger rows. The throwaway marker-table test and the existing-receipt variant both passed. The latter forced deferred constraints to run, exercised old and new replays, refused another office actor, sent once per active admin, and preserved the $1,000.01 warning and the order after an injected notice failure. Both rolled back. No production function or application change was installed. The tests did not prove independent transactions, browser loss, the exact formatted notice, or the revised nonfinancial marker and failed-attempt behavior.
