# Behavior contract: who pays for a field (packages FP-1 to FP-4) and the Chem Man field import

**Master copy (2026-11-24).** Newest answers only; git history keeps earlier drafts. Business rules: `SPEC.md`. Build order and gates: `BUILD-PLAN.md`. Billing: `CONTRACT-field-billing.md`.

**Words.** *Split*: who pays for a field and what share, as two share sets, **product shares** and **application shares**, each exactly 100%. *Version*: one saved split with the date it starts. *Resolver*: one function answering "who pays for this field on this date". *Micro-percent*: 100,000,000 = 100%, so thirds are 33,333,334 / 33,333,333 / 33,333,333.

## Rules for every package (and for `CONTRACT-batch-stock.md` and `CONTRACT-field-billing.md`)

1. One package is one database PR through `ship.md`, with its screen PR after it (`BUILD-PLAN.md` names the file owner). Merging into staging needs no `I approve`. Each `I approve` marker below names an access or constraint change to call out in the PR body and the migration's `docs/reference/migrations.d/` record; since Mason's 2026-11-24 slice 0–1 batch it is **not** a separate yes: a non-destructive one applies under AGENTS.md › Autonomous landing (Taha's `Ready to merge`, the migration-apply proof gate), and one the repo guard classes as destructive still asks Mason itself.
2. **Grants and security, one matrix for every field-app table and function:** RLS on every new table in the same migration; no direct writes from `authenticated` or `anon` (RPCs only); office (admin, sales rep) reads all; applicators and the mixer read only through the narrow paths each contract names; `anon` gets nothing. SECURITY DEFINER functions set `search_path = public, pg_temp`, check the caller's role inside, revoke execute from `PUBLIC`, `anon` and `authenticated` and grant only the public entry points to `authenticated`; internal helpers are never granted. Every RPC that takes ids checks they belong to the named record.
3. **Retry keys:** every new write RPC, and every existing one a package changes (`save_field`, `save_job`, `transfer_job_to_invoice`, the quote-to-job writer), takes `p_idempotency_key` bound to the actor, the operation and a hash of the request. The role check and the caller's current access to the named record run first; then a stored result for the same actor and key is returned before any business-state check; the same key with a different request is refused. The key is claimed atomically (inserted before the change, or looked up again after the record lock) and stored in the same transaction as the change, so two identical requests at once return the same result. An old signature kept as a wrapper (rule 4) passes a null key and keeps today's behaviour; the retry guarantee starts with the screen that sends a key, released together with the RPC. The screen keeps one key per action across retries and reloads.
4. **Rollout:** a changed signature is added beside the old one; the old one stays (as a thin wrapper) until a release where nothing calls it, then a later PR drops it. A revoke of a browser write lands in the same release as the screen that stops using it. Each PR lists the callers it checked.
5. Proof in the schema-matched Docker harness with the **fixture set**, built in FP-1 and extended by each package: fields at 100% one payer; 50/50; thirds; 50/25/25; 2/3–1/3; 60/40 where the landlord pays 0% application; a single payer who is not the owner; a field with no stored acres but a job acreage. Every path also gets a 1-cent line split three ways and its −1-cent credit, and a line where the main customer is at 0%. Callers tested: admin, sales_rep, applicator, inactive applicator, driver, entity_recipient, anon (and the mix-site account once it exists).
6. **Cutover inventory:** taken inside the migration's own transaction, after it locks the tables it changes, so nothing can be written between the count and the change. Any real (not test) record the migration would convert, refuse or cannot preserve stops the apply until reviewed with Mason; each migration names which records those are and their permitted live counts. Real batch-path jobs made after slice 2 is live are expected and do not stop it. (After Taha's reset, live starts with no jobs or invoices.)
7. **Old screens are for testing only** (Mason, 2026-11-08): the old field-invoice, job-transfer and blend-ticket screens stay on for jobs on the old stock path; every route refuses a batch-path job (`CONTRACT-field-billing.md` › Every route).
8. Stay out of Taha's areas until 2026-12-15 (the list is in `BUILD-PLAN.md` › How the work stays safe, item 6); after that, with his review. Comment on his PRs only.

## FP-1 · One split per field, with history (DB + Field Setup)

- **Tables:**
  - `field_billing_split_versions`: field (`ON DELETE RESTRICT`), version number (unique per field), `effective_from` date, `history_known`, reason, who, when.
  - `field_billing_split_payers`: version, customer (`ON DELETE RESTRICT`), `product_share_micro_pct` and `application_share_micro_pct` (integers 0–100,000,000, `NOT NULL`). Unique (version, customer).
  - `field_payer_notes` (field, customer, `pricing_note`, `notes`; unique per field and customer): plain editable notes, **not** part of a version (Mason 2026-11-24). Saved by the same writer; never creates a version; a save that sends no notes leaves them as they are. This is why `20270224110000`'s CHECK (notes barred on `field_billing_defaults`) fits.
  - Append-only: a trigger refuses UPDATE and DELETE on the version tables, and refuses a payer added to a version not created in the same transaction. A deferred constraint trigger refuses, at commit, a version with no payers or whose product or application shares do not each total exactly 100,000,000. A payer may be 0% on one side (a landlord who pays no application) or both (a named party who normally pays nothing).
  - No primary flag on versions: who takes the leftover cent is decided at billing (the job's customer, `CONTRACT-field-billing.md` B3). The transition copy sets `field_billing_defaults.is_primary` on the field owner's row, for today's readers only.
- **Read access:** admins and sales reps read all versions and notes. Applicators keep reading the current split through `field_billing_defaults` and its `_can_see_field` policy, never the version tables.
- **`fields.customer_id`** changes from `ON DELETE CASCADE` to `ON DELETE RESTRICT` (check no customer-delete flow relies on the cascade). `I approve`.
- **Writer:** `set_field_billing_split(p_field_id, p_effective_from, p_payers, p_notes, p_reason, p_idempotency_key)`; `save_field` and the Chem Man import call the same internal function. It locks the field row `FOR UPDATE` and writes the whole version (all payers) at once. **The office picks any start date, past or future** (Q3). A save that sends no split (a name-only or notes-only save) writes no version; a save that sends a split writes a version unless it matches the version in force on that date **and** starts on that version's own date (so a dated change the office schedules is kept even when the payers match). Payers can be any active customer added to the field (Q1).
- **Resolver:** `field_split_as_of(p_field_ids, p_on_date)`, SECURITY DEFINER, office only, refuses unknown or duplicate ids and a null date; latest `effective_from` on or before the date, then highest version number; returns both share sets, version id and `history_known`. Billing calls it inside the invoice transaction after taking `FOR SHARE` on each field row. No version: returns "no split"; the job then bills 100% to the grower the field was added under (FP-4, GR5).
- **Lock order:** the split writer takes the field row `FOR UPDATE`; every invoice writer takes `FOR SHARE` on each field it bills, in field id order, before reading the split.
- **Transition copy:** the same transaction rewrites `field_billing_defaults` to the version in force today (Central date; product shares; 0% payers left out because that table refuses 0%), recording which version it came from. A `pg_cron` job just after midnight Central takes the same field lock and rewrites every field whose in-force version differs from its copy, so a missed run is caught by the next. Readers of `field_billing_defaults` show product shares only and never bill from it. Each keeps reading this copy until its named move: Job Detail, `SelectLocationsModal`, the applicator sheet, the loader worksheet, the chemical application report and the billed-customers lookups (FP-4); the order screen's field-share preview (`OrderDetail.tsx`, spring). Slice 0 re-lists the readers from code. Payer search (the office field picker and the applicator's extra field) reads the split in force today from the version tables and counts a payer with a share above 0 on either side; a party at 0% on both sides is not a match. Direct writes to `field_billing_defaults` are revoked from `authenticated`. `I approve`. Field Setup reads and saves through the version tables in this same package, so a 0% payer is never lost.
- **Unused field price:** the migration stops if any `field_billing_defaults.price_override_cents` is set (slice 0 counts them on staging and live; a live one goes to Mason as a live-billing change before the release); `save_field` stops accepting it.
- **Backfill:** each field's current split becomes version 1, both share sets equal to today's percent, `history_known = false`, effective from the earliest possible date (for lookups only; the backfill date, its `created_at`, is the known-history boundary drafts name). Percent × 1,000,000; any difference to exactly 100,000,000 goes to the largest share (ties: lowest customer id); a difference over 10,000 micro-percent stops the migration and lists the field. Fields with no split get no version, so GR5 applies to them.
- Field Setup shows split history (date, who, payers, "imported" for version 1) with two share columns, and the payer notes.

**Done when (on staging):** thirds save as 33,333,334 / 33,333,333 / 33,333,333 and show 33.33% each; the database refuses (also called directly) a set totalling 90%, the same customer twice, a negative or blank share, a version with no payers, a payer added to yesterday's version; a 0% application payer saves; a split save and a new invoice draft on the same field at the same moment run one after the other; a name-only save writes no version and keeps the notes; a notes-only save changes the notes and writes no version; a named 0% payer survives two Field Setup saves; same key resent writes nothing, same key with different payers is refused; a direct write to `field_billing_defaults` is refused; an applicator on a job still sees that field's current split and cannot read the version or notes tables; deleting a customer who owns or pays on a field is refused; every field with a split has version 1 and fields without one have none. **Release check (read-only, after the live apply):** the same version-1 count on live. **Size:** L.

## Chem Man field import (one time; slice 1, after FP-1)

- **File:** Mason's export, kept outside the repo (private folder Mason names); never committed. The first step reads its columns and writes the mapping (Chem Man column → CRX field) into the PR, with no real names.
- **Matching:** each Chem Man grower is matched to a CRX customer by a mapping list the office checks once; an unmatched grower stops that grower's fields and lists them. A field whose customer and name (case and spaces ignored) already exist in CRX is **skipped and listed** for the office (Mason 2026-11-24); the same rule applies within the file, so two rows with the same customer and name import once and are listed as a collision.
- **Writes** through the FP-1 internal writer, so splits get version 1 (`history_known = false`); acres go to `total_acres`; blank or 0 imports as blank (unknown) and is listed.
- **Runs:** a dry run prints counts (in file, matched, skipped as existing, unmatched, to import). Trial on a local test copy of the database (Docker harness), **not staging**. Live: once, after Taha's reset, with Mason's yes in the slice 1 batch, then the office checks the list by hand. No re-run matching is built; a failed live run is rolled back whole (one transaction).

## FP-2 · Billable acres (DB, then Job Detail)

- Generated column `fields.billable_acres = COALESCE(override_acres, measured_acres, total_acres)`, matching `src/lib/fieldGeometry.ts` `billableAcres`; database fallbacks to `total_acres` use it instead. It sets **planned** acres only; billing always uses sprayed acres.
- **Blank is not zero.** `CHECK` that stored acres are positive when present (`total_acres`, `measured_acres`, `override_acres`, `job_fields.acres_to_treat`). The migration first sets existing zeros to blank and lists them, then adds the checks validated. The quote-to-job writer writes blank instead of 0; Job Detail sends blank as `null` and `save_job` refuses a typed 0 with a plain message.
- Acres keep 4 decimals for billing; screens show 2. `SelectLocationsModal` shows `billable_acres`.

**Done when:** a field with no stored acres plans with the job acreage; a job with planned acres and no work entry bills nothing; a legacy NULL stays unknown and a historical zero becomes blank; a zero-acre write is refused; an old job with unknown acreage saves a notes edit without anyone typing acres. **Size:** S–M. After FP-1. After 2026-12-15 (its quote-to-job change is Taha's quotes area), with Taha's review.

## FP-3 · Fields are archived, never deleted (DB + Fields list)

- `fields` gains `archived_at`, `archived_by`, `archive_reason`; archive state changes only through `archive_field(p_field_ids, p_reason, p_idempotency_key)` and `restore_field(...)`, enforced by a trigger. `is_active` follows `archived_at`, and the same trigger refuses a direct `is_active` change; existing inactive fields are archived with reason "inactive before archiving existed".
- **Who** (Q5): admins and sales reps archive; only admins restore. Bulk calls are all-or-nothing.
- **Blocked while work is owed:** any job not `completed`, `invoiced` or `cancelled`; a `completed` job not yet invoiced (an all-$0 set counts as invoiced, `CONTRACT-field-billing.md` B7) whose first spray day is on or after the billing switch-on date (before the date, or with no date set, it counts as billed in Chem Man) and not marked billed in Chem Man; an unposted invoice; an undelivered or uninvoiced order line on the field; an uninvoiced blend ticket. The RPC names each blocking record.
- **No new work on an archived field**, enforced in the database: archive locks only field rows (`FOR UPDATE`, id order); every writer that attaches work (job, quote, blend-ticket, field-app and order-allocation writers; a trigger on `order_item_field_allocations`) locks its own record, then the field rows `FOR SHARE` in id order, and re-checks `archived_at`. Re-opening a job counts as new work ("restore the field first"); editing an old record does not.
- Fields-list bulk delete becomes bulk archive; pickers hide archived fields. DELETE on `fields` revoked and the `fields_delete` policy dropped. `I approve`.

**Done when:** a rep archives a field and it leaves every new-work picker while old records still open and save; a rep's restore is refused, an admin's works with history intact; archiving a field with an open, paused or ready-for-review job is refused and names the job; an archive and a new job at the same moment cannot both succeed; a direct `DELETE` is refused. **Size:** M. After 2026-12-15 (it changes quote, blend and order writers), with Taha's review; before billing switches on.

## FP-4 · Jobs carry the field's split (DB, then Job Detail)

- `job_field_shares` gains `product_share_micro_pct`, `application_share_micro_pct`, `source` (`field_version` with version id, `office_override` with reason, or `legacy`) and a deferred exact-100% check per side per job field; its `> 0` check becomes `>= 0`. `split_pct` stays, filled from the product share, until every reader moves in this PR; `is_primary` is set on the job customer's row for today's readers.
- **Planned split:** `save_job` and the quote-to-job writer copy each field's split from the resolver on the job date (today if none) **when the field is first added**. The grower each field was added under is stored on every job-field link at add time (job screen, quote, booking, extra field); a field with no split on a spray date bills **100% to that grower** (GR5). Nothing else re-reads it; the office re-plans with `refresh_split` (today's date) or sets an office split. Billing does not use the planned split: it uses the split in force on each spray date (`CONTRACT-field-billing.md` B5).
- **Office split on one job** (Q1): changes the shares only among payers on the field's split in force the day it is saved (that list is stored with it); saved with a reason; wins over the field split at billing for every spray date. A payer later removed from the field stays on the office split until the office changes it; the draft flags it.
- **Readers moved in this PR:** `get_job_billed_customers` / `get_jobs_billed_customers`, `resolve_line_split_vector`, Job Detail (including its browser-built shares), the Jobs list customer filter, the applicator sheet, the loader worksheet and the chemical application report (`src/lib/chemicalApplicationReportFetch.ts`).
- **Existing rows** stay, marked `legacy`, and bill as an office split; a row that does not convert cleanly is listed and its job refused by the transfer until the office re-saves its split. Job fields with no share rows get the resolver's split, marked `legacy`. A version with `history_known = false` used for a spray date shows "split history before <the backfill date> unknown" on the draft.
- **Old transfer until the new engine lands:** `transfer_job_to_invoice` refuses every batch-path job, and for old-path jobs refuses (a) an office split (`source = office_override`; a migrated `legacy` row is judged only by (b) and (c)), (b) fields with different payers or shares, and (c) a job billed wholly to someone other than its customer, each with "this job is billed through field billing". These are the two live bugs found on 2026-11-08; nothing has been mis-billed live.
- **Billed in Chem Man** (`job_external_billings`, copied from `delivery_external_billings`, `20261007150000`): for the rare job on or after the switch-on date that Chem Man billed anyway. Admin only, reason required, retry key, RLS; un-marking needs a reason and never makes pre-date work billable. Marking and invoicing take the same job-row lock; marking is refused while the job has an unposted or posted invoice; every invoice writer and post entry point refuses a marked job.
- **`refresh_split`** is built here with its `job` mode: `refresh_split(p_source_type, p_source_id, p_line_ids, p_field_ids, p_reset_hand_edits, p_reset_overrides, p_reason, p_idempotency_key)`; it re-reads the version in force, logs who, when, why, old and new versions, and returns a before-and-after per line. The billing contract adds the `invoice_draft` mode.
- Direct writes on `job_field_shares` revoked once `save_job` is its only writer. `I approve`.

**Done when:** Job Detail, the Jobs list, the applicator sheet and the billed-customer lookups show the same payers for each fixture job; an office split survives a notes edit, a date change and a retried save; a field split change after the field was added leaves the job's planned split unchanged; `refresh_split` is logged with old and new versions; the old transfer refuses a batch-path job and the three cases above; a marked job cannot be transferred, and one with an invoice cannot be marked; a direct write to `job_field_shares` is refused. **Size:** M–L. After FP-1 and FP-2 (it changes the same quote-to-job writer), after 2026-12-15 with Taha's review.
