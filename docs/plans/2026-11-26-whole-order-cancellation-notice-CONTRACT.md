# Whole-order cancellation notices

This change moves an existing Order Detail staff alert to a checked database operation. The first combined proof used staging `e6e7ab2f0f3a235c981a697590810e47c78606a5`.

## Behavior

- A fresh whole-order cancellation sends one alert to each active admin. The cancellation actor is the sender. The title is `Order cancelled`, the notification type is `order_status` and the destination is the saved order. The existing message is `Order {number} for {farm name or customer} is now cancelled`. Use `customer` when the name is missing or empty. The existing screen does not send a separate creator alert.
- A successful remainder close keeps its current fulfilled result and no full-cancellation alert. A denied or rolled-back request, an already-cancelled outcome and an exact replay produce no new alert. The screen keeps the existing status activity entry, confirmation and refresh behavior.
- Keep the existing public cancellation and its private implementation intact. Add a checked `cancel_order_with_notice` entry point with the same order locator, actor check, required nonblank key and cancellation result. Require an active admin. Set `search_path = public, pg_temp`. Grant execute to authenticated only, with no access for PUBLIC, anon or service_role.
- Use the existing private lifecycle receipt functions for an outer operation bound to the actor and order. The outer retry key uses its own operation namespace. An exact outer replay returns the saved result immediately. A fresh outer claim generates a new internal key inside the database and calls the existing cancellation function with it. Keep the original function's invoice, delivery and order lock order within that call. The two wrapper keys are scoped to the wrapper so ordinary legacy clients never use those locks. Do not derive freshness from order status before the save, transaction identity, or an existing notice.
- Treat a call as eligible for a notice only when this checked operation ran the underlying cancellation with its new internal key, received the exact JSON boolean success true and mode full_cancel, and the saved order is cancelled. A legacy already-cancelled outcome can say full_cancel and cancelled with no success field. It receives no alert.
- Bind the original cancellation result into the outer receipt before entering the best-effort sending block. A receipt write failure aborts the wrapper before any notice. A send error keeps the successful cancellation and its bound receipt and records a notice failure. An exact retry then returns the result without another send. An outer rollback removes the cancellation, both receipts and any notice together. Keep the outer receipt metadata out of the public result.

## Delivery

The additive database migration and its focused proof ship first. It preserves the current client, receipt behavior and table grants. Include a changelog entry, checked types, migration reference and the applicable schema guidance without regenerating against an unrelated database. The subsequent Order Detail change switches the single caller, preserves its activity entry and removes the obsolete browser sender. The final notification grant is a separate cutover after existing browser workflows have checked replacements. For rollback, restore the old client before removing the added operation. Existing records, receipts and sent notices are retained. The database PR requires Luna and exact Sol review before opening.

## Local proof

- An active admin cancels an invented undelivered order through Order Detail. The saved cancellation and both existing activity entries are visible after reload, one from the database status trigger and one from the screen. Each currently active admin gets the correct notice with the actual sender, and neither an inactive admin nor another role receives it. The updated screen issues no browser notification insert. An admin activated after the send is eligible only for future actions.
- An inactive admin and other roles cannot call the new operation. Invalid actor or key, denied cancellation and a legitimate remainder close produce no full-cancel alert. Preserve their existing results and ledger behavior.
- Test same-key lost replies, two admins with distinct keys racing, and a receipt past its normal expiry. A visible cancelled order stays cancelled once. One fresh success sends, an already-cancelled outcome sends none, and the exact retry recovers its result without another alert or activity entry. Test a concurrent change to admin eligibility.
- Force a notification failure and an outer receipt write failure independently. Neither can create a duplicate. A failed send keeps the successful cancellation and reports the failure. An outer rollback removes the cancellation, receipt and notice together.
- Run cached old and updated browser versions against the additive database. A stale old screen cannot duplicate a new screen's alert through its ordinary save, and a new screen following an earlier old save refreshes the existing order without sending retroactively. Verify an earlier raw cancellation and receipt cannot receive a second notice from the checked operation. Check the empty farm-name fallback.

## Verified baseline and review disposition

The newest public cancellation body is in `20270308140000_commission_settles_on_posting.sql`. Its current inner cancellation and bound receipt are in `20260721152604_block_partial_cancel_with_received_returns.sql` and `20260719060256_allow_governed_split_terminal_lifecycle.sql`. The current sole app caller and notice are in `src/pages/OrderDetail.tsx` and `src/lib/notificationTriggers.ts`. The older restore function has no authenticated execute grant. The proposed additive delivery follows the approved Receiving deployment pattern from `20270311110000_receive_po_items_with_excess_notice.sql`.

Two rollback-only database rehearsals on the 413-migration local staging build confirmed the existing behavior. Whole cancellation replays the original result. A second admin using another request key gets mode full_cancel and status cancelled without success. An extra private receipt field left the replay response unchanged. A legitimate remainder close finished as fulfilled. The existing server-side remainder reminders and escalation also worked with direct browser insert revoked. These are baseline results. Both tests rolled back and Docker was stopped.

The initial challenge rejected changing the existing cancellation writer and proposed an additive wrapper. The targeted review identified the need for a trusted freshness signal and an explicit retry rule. The local rehearsal replaced row metadata with its own outer retry receipt and a new server-generated key on first use. The ordinary old operation is unchanged.


A disposable local prototype on the same staging schema passed the existing admin and sales-rep access checks, exact replay, a legacy cancellation, a PostgreSQL subtransaction and an injected notification failure. With two sessions, the follower was observed blocked in both cases. Two admins using different keys saved one cancellation and one administrator fan-out. Two requests sharing a key returned the same result and still sent one fan-out. No browser, production migration or broader system lock order was tested by this prototype.
