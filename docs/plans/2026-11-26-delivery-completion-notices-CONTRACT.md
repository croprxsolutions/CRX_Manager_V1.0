# Delivery completion notices

Behavior contract based on staging `5df2ecbb5f608f3bec93cb26c3e61e12b2e45328`. This permissions change moves existing internal completion and remainder sends into a checked, best-effort operation. The delivery save, billing, stock, signature, delivery-issue alert, customer receipt and offline workflows retain their existing behavior.

## Recipients

| Signed-in completer | Existing recipients to preserve |
| --- | --- |
| Assigned driver | Their own completion confirmation. A remainder notice only if they also created the delivery. The old completion fan-out to other people remains refused. |
| Sales rep | Active admins and the assigned driver. For a qualifying remainder, active admins and the non-admin delivery creator. The legacy commission lookup sees only this rep's own rows while Reports is available. Hiding Reports suppresses only commission alerts. |
| Admin | The same active-admin, assigned-driver and qualifying creator rules. The legacy commission lookup sees all rows for the order. |

For a commission notice, exclude cancelled or null statuses and recipients whose public role is admin. Preserve the old comparison that excludes the already-notified driver when the stored text matches the assigned driver ID exactly. Preserve working UUID-shaped legacy values, including uppercase and inactive recipients where the existing lookup and insert succeed. A display name does not become an address merely because there is a newer recipient ID column. Treat an ordinary confirmation and a commission confirmation as different notice kinds, so an existing uppercase legacy commission confirmation keeps its audience. If multiple spellings resolve to the same person and notice kind, send that message once. Resolve and send per eligible recipient so a malformed historical field or one failed single-recipient send cannot roll back other notices. Preserve the existing sender stamp. Expected recipient exclusions do not generate failed-notification records. Mason approved preserving existing recipients.

## Saved completion and send

Use a separate checked post-save operation, like receiving damage notices. Only the three interactive screens call it. The new screens remove their legacy direct sends in the same UI change. Older cached applications keep their existing senders during the transition. The scoped completion keys are held in a mounted React component and are never carried over when a different app build loads. Each cached build uses independent keys and the database refuses a new completion attempt on an already completed row. A lost save response followed by a full reload still has the existing gap: reopening verifies the saved delivery, but the app cannot recover its old key to send the notice. Leave that existing behavior in place. Prove the old/new client transition and a lost response in the same mounted screen. Do not add a notification-table trigger.

The new screens opt in when calling the corresponding completion operation. Both completion entry points keep their existing arguments and defaults. Capture the interactive source and a server-generated event identity when the completion actually saves. Keep the event in private database storage with RLS and no browser grants. Keep its nonfinancial data separate from the existing receipt result. The list and its nested direct receipt identify the same event. Only the outer receipt can authorize the list send, and only an ordinary direct receipt can authorize the detail or field send. A caller naming the inner list receipt must never get detail or field notices. Do not recognize old receipts, offline queue receipts, or a replay as a new interactive event. The offline processor has no interactive opt-in and keeps its existing notice behavior.

The sender verifies the original receipt and its expiry, the signed-in actor, current delivery authorization, the source recorded by the server, and that the delivery still represents this completion. The screen sends the receipt locator and a separate required `p_idempotency_key text DEFAULT NULL`, rejecting empty keys. Execute is granted to authenticated callers only. Revoke default access and pin `search_path = public, pg_temp`. Derive notification text and recipients from saved facts. Claim each event, recipient and notice kind in private storage in the same transaction as that notice insert. A failed insert rolls back only that claim, and the same retry key can send the missing notice without repeating a successful one. Keep successful claims through ordinary retry-cache cleanup. Refuse a receipt for an earlier completion after a void or any permitted reopen. Keep request-mode selection and trusted event capture out of the client-controlled notice request.

Derive partial and remainder text from the approved completion facts. Preserve the list's completion-only format and the detail/field remainder template, including its existing internal order reference. Keep existing readable decimal formatting, with no padding added by PostgreSQL. For a legal submitted amount under 0.01 that the save normalizes to zero, retain the validated original amount for the legacy remainder wording only. The saved delivery and all business logic still use zero. Test the old wording with 0.004 and the stored quantity with zero. Never accept a quantity or message on the separate send operation.

The ordinary save must survive an optional notice-registration failure. A later send failure leaves a successfully saved delivery intact and logs only actionable failures. The three screens keep their existing save recovery and receipt behavior. Roll back the screens first and retain the additive database interface for cached new clients. If the sender's mechanism must be disabled, keep the completion signatures and leave a checked sender that reports the temporary inability to send without changing the completion result. The new client records that failure through its existing logging path. Do not drop the additive interface while installed clients can still call it. Prove old screens against the original and additive database, and new screens against both the active and disabled sender.

## Local proof

- As an authenticated admin, sales rep and assigned driver, exercise actual full and partial completions with invented deliveries. Compare the exact sender, recipient set, numbers and messages to the existing screens, including current commission visibility, historical IDs, inactive recipients and current driver exclusions.
- Exercise the list save, the detail/field save, one Quick Delivery and the existing offline recovery path. Quick Delivery creation adds no completion or assignment notice, and it sends the existing notices only after interactive completion. The offline path creates no new ordinary completion notices. Keep the deferred issue alert and prove it still reaches active admins once.
- Use real retries and separate database sessions for one completion. Force one recipient to fail, then retry and verify that only the missing notice is sent. Verify that the outer/inner list calls cannot compete across modes, and test a stale receipt, role loss, expired cache, another actor, lost response, a disabled sender, and a newer completion reusing a business date or the supporting lifecycle refusal. Simulate expiry separately from a partial send. Force registration to fail during completion and prove the delivery, stock and billing still save without creating a notice event. Verify that a refused completion, including a fractional whole-item quantity, creates neither event nor alert.
- Use the browser on the exact local composite for all three entry points, including older cached clients and rollback order. Keep fixtures invented. Stop the local stack afterward.

## Current evidence

The authenticated list and direct baseline on staging `5df2ecbb5f608f3bec93cb26c3e61e12b2e45328` passed on loopback with 418 migrations and 1,341 ledger rows. The list has two linked saved receipts. The outer result equals the inner result plus its `started` flag. A direct save has one receipt. Both expire after 24 hours, with no permanent completion event ID. Exact replay returned the saved outcome without moving more stock. The recipient-policy check passed using invented admins, reps and drivers. Both proofs rolled back. The app and database stopped.

The per-recipient rollback probe on the same loopback build produced two notices while one recipient's insert was forced to fail, three after retry, and still three after another retry. The failed insert left no durable claim. Sender attribution in an owner-run insert explicitly comes from `auth.uid()`. The existing notification trigger fills it only for API-user inserts. The probe rolled back.

The revised migration (`6b4bce6c333ae4f367a943d4998494153e608cf3dfe723df940e2e35515b1d26`) ran in the sealed loopback build with 420 migrations and 1,343 ledger rows. The rollback suite passed with invented users and deliveries. It observed an ordinary office alert with Reports hidden and no commission alert for that rep. It also observed one separate issue alert per active admin after a driver completion, preserved driver-only completion and remainder alerts, excluded an inactive admin and a name-only commission row, and refused sending after the originating user's role changed. Two independent PostgreSQL sessions each observed real lock contention and produced one alert per eligible admin in both retry cases.

Three interactive browser paths and a disabled-sender rehearsal passed after refreshing the screen worktree to staging `db791e99d5f9db09181f36ade3fc0ea75287f7bb`. That browser run used the preceding migration revision. The original Delivery Detail browser was exercised before and after installing the additive database. Original Deliveries and Field Stop were not exercised separately as legacy browsers. Explicit tests of a post-completion driver reassignment and fractional whole-item refusal with alert opt-in remain open.

The approved read-only production catalog check confirmed the source notification and commission policies, receipt and delivery column types, and old function grants. Production still exposes completion signatures without `p_lines_seen`. Staging contains that argument in both wrappers through `20270309170000_proof_bound_to_load.sql`. Require the staging versions of these wrappers in the candidate preflight. Preserve their existing arguments and behavior, including `p_lines_seen`. Treat proof-of-load and the subsequent quantity normalization as migration dependencies. Do not install this candidate directly on the earlier production signatures.

The Existing Brand Completion history already gives each successful completion an immutable database-generated sequence. It is written inside the completion transaction and indexed by delivery. The sender uses only that sequence and the actor to validate the current event. It does not read brand details or create an additional completion lifecycle trigger.
