## 2026-11-05 — send-email: #1302 review follow-ups (not yet deployed)

- Sales reps can no longer send `ar_reminder` (collection reminder) emails; only admins can. Reps keep invoices and statements (Mason, 2026-11-05, revising the 2026-11-02 answer to Taha's #1302 question).
- Two retries of the same failed email at the same moment send it once: a retry claims the log row only while it is still `failed`, and two first sends racing on one key get "already in progress" instead of an error.
- The call to Resend gives up after 30 seconds. Only one of Resend's documented refusals (400, 401, 403, 404, 405, 409, 422, 429) marks the email `failed`, so a retry may send it. No answer, a dropped connection, a 408 or 5xx reply or an unreadable OK reply may mean the customer already has it, so the row stays `pending` with the reason written on it and the caller gets 504 `needs_reconciliation`; the existing pending check refuses a re-send under that key until someone checks Resend. While such an unconfirmed send exists, a new send of the same email (same type, record and customer) is refused under any key too, because some screens make a new key per click; a send with no key is stored under an automatic record-tagged key so this check sees it, and record ids are compared in lower case. Known limit: two first sends with different keys in the same instant can still both go; a partial unique index would close it. This deliberately differs from the review's "mark it failed": a failed row would allow a blind second send.
- `supabase/functions/send-email/send_email_test.ts` runs the real function against an in-memory database and Resend: wrong-customer record, reused key, legacy key dedupe, rep refused an A/R reminder, rep and admin allowed a statement, both races, a timeout, an unreadable OK reply, a refused request and a gateway error. CI's Deno test step now allows only the named settings the function reads (`--allow-env=...`).
