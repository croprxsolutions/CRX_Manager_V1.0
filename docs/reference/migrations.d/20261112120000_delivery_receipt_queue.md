KI-25: a customer receipt owed after a delivery completion is recorded in the database in the same transaction as the completion, so a lost phone signal can no longer lose it.

**What it adds.** `delivery_receipt_queue` (RLS; admins and sales reps read; no API role writes; one row per delivery; the receipt body, contact name included, is frozen at completion), a trailing `p_email_receipt boolean DEFAULT NULL` on `complete_delivery` (fingerprinted only when TRUE; NULL and FALSE fingerprint as before, so earlier completions still replay), and three service_role-only worker calls, each taking `p_idempotency_key`:
- `claim_delivery_receipts` claims due rows (10-minute lease) after settling rows that must not be sent: delivery no longer completed (`cancelled` if no send was ever authorized, else `needs_check`), moved to another customer, no email now, five attempts used, 23 hours since the first authorized send, or a retry after an authorized send to a changed address (all `needs_check`). After an authorized send a retry keeps that exact address. A retried key returns the claims it still holds.
- `confirm_delivery_receipt_send` is called immediately before each external send; the worker sends only on `send`. It locks the queue row and (FOR SHARE) the delivery and customer, so it waits for an in-flight void or email edit, then checks the claim is held and inside its lease (`stale` otherwise), the delivery is still completed and this customer's, the email still matches the claimed address, and the 23 hours have not passed; on `send` it records `send_authorized_at` and renews the lease. Its key is bound to the receipt and claim and a retry always re-checks.
- `finish_delivery_receipt` records sent / retry / check against the token; `sent` is refused unless confirm said `send` to that same claim (`send_confirmed_token`) (backoff 2, 4, 8, 16 minutes; five attempts). A sent finish whose delivery, customer or email changed while sending becomes `needs_check` and keeps the send it recorded.

`_delivery_receipt_keep_owed` refuses deleting a pending, sending or needs_check row (so a hard delete of its delivery is refused). A delivery completed again after its receipt was cancelled (never sent) owes a fresh receipt. `pg_net` is enabled and `deliver-receipt-queue` runs every 2 minutes; it only posts a wake hint when a row is due and both Vault secrets exist (neither is created here), and it changes no row. Until the secrets exist, a receipt asked for at completion goes straight to `needs_check`.
