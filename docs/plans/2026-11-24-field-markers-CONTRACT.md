# Field marker behavior contract

## Outcome and authority

Staff see field entrances and hazards before they spray. Applicators can mark a saved field they can see and maintain their own pins. Office staff retain control of all pins. Each pin has one point, a type, an optional note, its original author, and its creation time.

Mason approved revision 7 of the Google Maps design in PR #2454 (head `c48be6cd4`). The marker rules are in item 11, D1, D4 and the two build checklists. The first crew screen is the phone Field View job map (`src/pages/FieldView.tsx`). Office paths are Field Setup and Job Detail. The print work follows the paperwork lane in the design's print step. Account and field access rules come from `origin/staging` at `59280e2e7`, including `20261217100000_job_access_ends_with_the_job.sql`.

The existing `field_obstacles` table and SELECT policy stay in place. Staging's catalog confirms the seven existing types, the object-only geometry check, and office-only writes. Add field entrance, washout, pole, garden, well, pivot, sensitive crop and gate. Keep all seven existing values. The database checks active role and, for applicators, `_can_see_field(field_id)` on INSERT and on old and new rows for UPDATE. DELETE requires a still-visible field. Applicator UPDATE and DELETE also require ownership. Drivers, entity recipients, inactive and unassigned applicators receive no additional access.

The database sets the requesting account and timestamps in one before-write trigger, replacing the existing timestamp trigger. It rejects changes to id, field, author or creation time. The insert field id and edit/delete pin ids locate records. RLS determines whether the actor can act on those records. The trigger also checks the same caller and field authority before allocating entrance numbers. Its narrowly scoped owner privileges permit a transactionally updated per-field counter that has no app access. The trigger is schema-qualified and sets `search_path`. Revoke EXECUTE explicitly from public, anonymous and authenticated clients. A stored positive entrance number is unique per field. The trigger ignores caller-supplied numbers on insert and update and assigns the next number when a pin becomes an entrance. Changing an entrance's kind retires that number. Changing it back assigns a fresh number. Existing entrances keep their assigned numbers when edited. Numbers are allocated within the pin's transaction and monotonic, with gaps allowed. The counter and pins follow the existing field-delete cascade.

The client id is the insert's primary key. The database requires a GeoJSON Point with exactly two numeric coordinates in range for newly inserted or changed geometry. Points outside the field outline are allowed. Old coordinates stay as stored, and unusable points stay in the text list as “Could not place.” Existing 3D points with usable longitude and latitude can still be shown in 2D. No existing pin is edited by the migration. Notes appear as plain text. New and changed crew notes have a 500-character limit. The new UI applies that limit to all new and changed notes, while the database continues to accept current office-client note writes. Valid legacy notes and geometry can remain as-is during other edits.

## State and failure

- Call the read-only invoker function once per saved field shown on screen. Each call checks that field's marker access and reads its rows in the same database snapshot. It uses the marker SELECT predicate, including active role and `_can_see_field`, which differs from field-row access on older spray records. It returns unavailable or a complete ordered marker list with a count. Absence, mismatch, or a failed field read has an explicit status, and only a confirmed complete empty field says “None recorded.” Clear data on sign-out, account change, field change or confirmed loss of access. Recheck on resume and discard outdated responses. After a signal failure on the same account and field, show the already-loaded pins in memory only, with a “May be out of date” warning and last successful check time. Disable marker writes until a complete authorized read succeeds again.
- Show every returned marker and note in the text list. The map filter affects symbols only and starts at all types. Show the stored entrance number regardless of filter. Unknown new kinds have a generic pin and label. Names come from the existing authorized `profile_public_view`, with “Unknown” for missing names. Show the original author and date plus the last edit time when the row has been edited.
- Bind creates to the original field, signed-in account and frozen payload. Reserve one pending create per account and field in a browser IndexedDB transaction before sending. Use `add()` with a unique composite key for that slot so a second tab can recover the original pending pin and cannot replace its ID. Make creation of the slot conditional on its active account and sign-in session inside the same transaction as the add. Sign-out and account changes clear the session and pending records in a single transaction. Use INSERT only. The database writes a private create receipt keyed by the immutable pin ID in the same transaction as the pin. The receipt keeps the ID, field ID, original actor and timestamps, survives pin deletion and follows the field-delete cascade. Nullable actor supports existing service inserts. A second insert with a used ID fails even if a previous insert was followed by deletion. A read-only database function checks account scope, receipt and pin together. If a duplicate response has no authorized matching receipt, keep the pending record and show an unconfirmed result. A saved and later removed pin is reported as such and cannot come back on retry. Existing rows are covered before deletion can remove their IDs.
- **Mason's decision, 2026-11-25.** Keep a pending marker save in the same browser profile so it can be recovered after a reload or after leaving the screen. Store a versioned record of the actor and original submitted pin ID, field, type, note, and coordinates before sending. Refuse to send a new create if local persistence fails. Restore it only to the same signed-in account after a fresh complete authorized marker read for that field. A damaged record blocks the slot with a message to inspect that field before attempting another pin. Never show or send its contents. Purge every record, including damaged records, on explicit sign-out or a sign-out event. At authenticated startup or account change, clear pending saves if the saved browser session differs from the current one. Keep already-loaded map pins in memory. The app never sends a saved placement automatically.
- A draft with no reserved submission can be canceled. After any uncertain submission, close the editor with “Keep for later” while retaining its pending save, so work on other fields can continue. At unavailable fields, hide the loaded pins and pending form. The original signed-in account may recover its pending save only after a new complete authorized read. Map scope comes from all currently assigned fields, independent of List search. A partial location lookup or failed geometry lookup must not show an old field that fresh dispatch shows was removed. Keep a last good marker read only for fields still in scope.
- Edit and delete in the new screens include field ID, pin ID and the exact `updated_at` string received from the database in the write filter. The database advances the version on every update. Older office clients keep their existing delete behavior until the screen rolls out. Zero affected rows in the new screens is a failed save with a refresh prompt. A late result from another account, field or job view cannot apply to the current view. Deletion removes the pin after confirmation and uses the existing hard-delete model. The create receipt retains no pin notes or geometry and provides no undo.

## Proof cases

- A browser rendering a future kind shows a generic pin and label. Invalid stored geometry remains in the text list. Existing mapped pins look and read as before.
- On a migrated isolated database, authenticated admin and sales rep can add, edit and remove any pin. An assigned applicator can see coworker pins, add a new pin and change and delete their own. A coworker's UPDATE and DELETE returns no rows. Reassignment, unassignment, inactivity, driver, entity recipient and anonymous cases cannot write outside their scope. Repeat the role cases on staging with test accounts and fixtures.
- In the isolated database, all 15 types are valid, unknown types and malformed or out-of-range new points fail, metadata is assigned by the database, immutable values cannot change, and legacy geometry remains editable for note-only updates. The same client id cannot create a second row. Two writes using the same prior version cannot both succeed. Concurrent creates allocate distinct entrance numbers. Caller-supplied numbers are ignored on insert and update. Deleting Entrance 1 leaves Entrance 2 numbered 2 and the next entrance is 3. Changing an entrance to another kind and back assigns a fresh number.
- In the real phone and office screens, choose a saved field and place a pin just outside its outline. Verify creation, optional note, author/date, edit time and delete. Entrance labels and text remain visible when their symbols are filtered. Verify a true empty read, incomplete and failed reads, account or field changes during read or save, and a visible old spray record with unavailable markers. A lost connection keeps the previously loaded pins with a warning through a retry, while a successful access-loss check clears them.
- Drop a real committed save response, reload, and recover a single pin with its original ID, text and placement in both editors. Exercise an original insert that never arrived, a pin deleted before recovery, sign-out during a save, a different account, a failed permission check, overlapping tabs, and unavailable browser storage. Set a pending draft aside, let the original request commit late, and check that opening it again still recovers the same ID. Use the staging fixtures after the applicable database and screen batches are ready.
- In the real screen, interrupt a create response, retry, and verify one stored row and one confirmation. Verify a second editor cannot silently overwrite or delete a changed pin.
