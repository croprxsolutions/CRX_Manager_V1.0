**Stored receipts.** A saved answer is replayed only after the key check, so a receipt stored under a key the new rule refuses could not be replayed. The preflight therefore refuses (`IDEM_KEY_PRINTABLE_1912_WEAK_RECEIPT`) while any live (unexpired, or with no expiry) `idempotency_keys` row of one of these 19 functions' operations holds a non-printable key (receipts of other operations keep replaying and never block the apply); receipts last 24 hours, so the apply waits for them to expire. Before scanning, the apply takes a short table lock (`SHARE ROW EXCLUSIVE`, 15 s timeout) on `idempotency_keys`: it waits for in-flight receipt saves and holds new ones back until the migration commits, so no old-code write can save a bad-key receipt between the scan and the new bodies. The only leftover is a call that passed the old check and is blocked on that lock; it is at most one in-flight request. The public wrappers that read receipts before the key check (`record_vendor_payment`, `update_vendor_bill`, `void_vendor_bill`, `receive_po_items`) are covered by the same guarantee: no live bad-key receipt exists after the apply. The app never builds such keys (Taha's review and the 19 Nov live count agree).

**Rollback:** a new reviewed migration re-emitting the prior bodies (as replayed from `origin/staging`).

**Apply in a quiet window (Mason, 2026-11-23).** Run this apply only when the app has no traffic (for example after hours, with the app idle for a few minutes first). A request that passed the old key check and is still in flight at the cutover can save a bad-key receipt afterwards; if its answer is lost and the caller retries under a fresh key, that one request can repeat (for `create_inventory_hold`, reserve twice).
