Mason's decision (2026-11-02): while a cycle count is open, the warehouse stops shipping and receiving the products being counted. Before this, stock that moved during an open count was counted twice. The count kept the snapshot from the start, the shelf count already included the movement, and completion added the difference on top of the moved stock.

- **Freeze.** A `BEFORE UPDATE OF quantity_available` trigger on `inventory` (`trg_freeze_inventory_during_cycle_count`, function `_freeze_inventory_during_cycle_count_20261102`, postgres-only) refuses any on-hand change to a row listed in an `in_progress` count. The error is `INVENTORY_FROZEN_FOR_CYCLE_COUNT` and names the product, location and count number. One trigger covers every stock path: receiving, delivery complete/void/cancel, job and blend application, returns and manual adjustments. Booking (`quantity_prebooked`) and holds do not change on-hand stock, so they keep working. Completing the count is exempt through the transaction-local setting `crx.cycle_count_applying`, which names the count being applied. Reversing a completed count is refused while a different open count covers the row.
- **Atomic start.** New `create_cycle_count(p_warehouse, p_notes, p_idempotency_key)` (admin only, key required, intent-bound replay). It numbers the count, refuses a second open count for the same warehouse (`CYCLE_COUNT_ALREADY_OPEN`), and snapshots every inventory row at that location while locking them, all in one transaction. `CycleCounts.tsx` now calls it instead of three browser writes.
- **Safety net.** `complete_cycle_count` refuses with `CYCLE_COUNT_STOCK_MOVED` when a counted line's current stock differs from its snapshot. This catches counts started the old way, for example from a stale browser tab.

- **One open count per warehouse** is also a partial unique index (`cycle_counts_one_open_per_warehouse`), so a direct insert cannot open a second one.

Queued field-app actions refused by the freeze are never dropped (`src/lib/offlineSync.ts`). They stay in the offline queue with the error shown and retry automatically after 30 seconds, 2 minutes and 10 minutes. After 4 failed attempts they are marked as needing attention, and someone presses "Retry saved work" once the count closes. The error text avoids the phrases that mark a failure as permanent.

Still open (pre-existing, admin only): admins keep direct table write access to `cycle_counts` and `cycle_count_items`. An admin could therefore delete a line, which lifts the freeze on that row, or hand-edit `expected_qty`. An admin could also set a count's status directly: setting `completed` lifts the freeze without applying the count, and flipping a reversed count back allows a second reversal. Stock with more than 2 decimals (one live row on 2026-11-02) is snapshotted at 2 decimals, so completion can land up to 0.005 off the counted quantity, as before. Removing that access changes permissions and needs Mason's approval, so it is left for a follow-up.
