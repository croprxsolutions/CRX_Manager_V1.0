## 2026-11-23 - #2265: an invoice whose payments were all voided can be unposted

- Migration `20270225130000_unpost_ignores_voided_payment_history.sql`: Unpost (single and group) no longer refuses an invoice just because a voided payment's allocation rows are still kept as history. An active payment, order or invoice allocations, write-offs, prepay and applied credit still refuse, as before.
- On unpost, those history rows lose only their link to an invoice line (they keep the amount and payment, and an older row with no invoice recorded gets this one), so saving the unposted draft no longer fails on the line delete. An older row that names one of this invoice's lines but records a different invoice stops the unpost (`UNPOST_HISTORY_NEEDS_HAND_CHECK`) for a person to check. The audit row keeps which line and amount each one covered (`voided_payment_history_unlinked`).
- Proof: `node scripts/smoke/prove-unpost-voided-payment-history-real-schema.mjs` (`UNPOST_VOIDED_PAYMENT_HISTORY_PROOF_PASS`, local Docker): reproduces the refusal, then shows unpost, draft save with its lines and re-post work, the save would fail without the unlink, two voided payments on two lines both unlink, the file changes nothing when its check fails even under plain `psql -f`, unpost racing a payment void on the same invoice does not deadlock, active or partly voided payments (and an active payment allocation with nothing marked paid) still block, and group unpost works the same way for a group with no invoice-type allocations (the proof links two drafts into a group by hand; a group drafted by a split keeps its invoice-type allocations, which still block by design).
