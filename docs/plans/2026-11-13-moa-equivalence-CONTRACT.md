## Outcome

Treat leading zeroes in a group code's numeric component as insignificant when deciding whether two groups are the same. The comparison key includes the scheme, so `HRAC M1` equals `HRAC M01`, and `HRAC 1` equals `HRAC 01`; `HRAC 1` is distinct from `FRAC 01`. Keep each official/source spelling intact in database rows, API results, audit/history, and user-visible text. Do not remove zeroes from stored or displayed codes.

Apply this rule consistently to (a) duplicate validation for an ingredient's list, (b) derived-versus-typed group-set comparison, and (c) typed product-group addition and the existing-row checks used when retaining/moving typed groups. Refuse a duplicate within its relevant ingredient/product scope. Server validation remains authoritative; a screen-level warning is only for earlier feedback.

## Rules and boundaries

1. **Canonical identity is comparison-only.** Compare `(scheme, canonical_code)`. For an ASCII alphanumeric code, strip leading ASCII `0`s from each run of `[0-9]`, keeping at least one digit. Never cast to integer/numeric: `9999999999` must not overflow. Preserve letters and their position; `M001A02` compares as `M1A2`, with its stored/display spelling intact. Existing validators still do their current trim/uppercase. A legacy typed code containing punctuation, internal spaces or other non-alphanumeric characters stays exactly as validated and is compared exactly (for example `2.01` remains distinct from `2.1`, and `M-01` from `M-1`). No new acceptance/rejection shape rule.
2. **Scheme stays significant.** Equal canonical codes in different schemes are different groups.
3. **Duplicates refuse atomically.** Within one ingredient list or one product+ingredient group set, two active/requested rows with equal comparison identity are a duplicate. Reject the whole write, without partial row changes, version advancement, event/history writes, or idempotency receipt changes beyond established writer semantics. Retired rows remain historical and do not block a new active spelling. New partial unique expression indexes protect both active scopes after a collision-refusing preflight; keep existing exact indexes needed by current ON CONFLICT clauses. The new immutable private key helper has deliberate grants/revokes and no elevated privileges.
4. **Typed and derived sets compare by identity.** `_parent_mode_groups` reports `matches` when the typed and derived sets have the same canonical identities, even if their official spellings differ; e.g. a derived HRAC M1 and a typed HRAC M01 are compatible and report `matches`, not a user spelling replacement. It continues to return the original spellings in `typed`, `derived`, and `live`; where existing behavior selects typed rows for `live`, retain that preference. Distinct values within a set remain distinct groups. The product summary folds equivalent groups across ingredients once, using a deterministic existing source spelling (lexical minimum), while ingredient-level arrays keep every source spelling. No normalized display code is invented.
5. **Do not rewrite legacy data.** No migration-time update, deletion, automatic retirement, or silent deduplication of existing rows. A read-only preflight must detect active alias collisions by canonical identity in both ingredient lists and product typed groups. If any exist, migration aborts before persistent changes and reports counts plus opaque IDs sufficient for an admin to reconcile using reviewed existing workflows. Do not publish or apply until each collision has an explicit resolution; retain retired rows and history.
6. **Preserve write/version/history contracts.** Reuse existing admin authorization, locks, expected-state/version checks, idempotency behavior, EPA gate, refusal prefixes, event/audit semantics, grants, and RLS. An ingredient-list request that supplies an active code using a different equivalent spelling refuses the entire save, names both submitted and stored spellings, and makes no partial change. This includes replacement requests that omit the old spelling: with active/expected `[FRAC M1]`, requested `[FRAC M01]` alone refuses before writes. It does not silently retain or rewrite either spelling. Use the existing `CHEMISTRY_MOA_INVALID` refusal prefix with a clear spelling-specific message; a duplicate within one requested list uses the same prefix and names the two submitted spellings. Retiring the current spelling and adding its replacement is a two-save operation through the existing ingredient-list writer or the product correction/fast-entry paths. The first save records the retirement; a later save can add the replacement once no equivalent spelling is active. During that interval, typed-versus-derived groups are temporarily one-sided (`typed` or `derived`, according to which source still has a row); after the replacement is added, canonical comparison returns `matches`. No new UI shortcut or behavior is added. The typed product add path uses `CHEMISTRY_ROW_EXISTS` for an active equivalent row and names submitted and stored spellings. For a duplicate of the exact same code within one request, the prior implementation reached the active-row check and returned `CHEMISTRY_ROW_EXISTS`; this candidate detects it earlier and returns `CHEMISTRY_DUPLICATE_CHANGE`. That intentional error-prefix change has no current `src` consumer; the duplicate codes and refusal behavior are unchanged. A same-request alias collision also returns `CHEMISTRY_DUPLICATE_CHANGE` and names both submitted spellings. Consolidation is an existing, distinct operation: if a selected source code is canonically equal to an active destination code, retain the destination row and its exact spelling, retire the source row with history, and do not insert a duplicate. A canonical destination check is required before insertion so the new unique index cannot turn the established deduplication into a failed save. New rows keep the caller's validated spelling. Events/history reflect actual final rows. Expected snapshots and retry fingerprints remain exact: a different raw request under one key still refuses. No public payload/signature change.
