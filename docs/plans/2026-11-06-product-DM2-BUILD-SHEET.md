**Status: PLAN, 2026-11-06. NOT STARTED.** This is DM-2's own build-sheet section, required by `docs/plans/2026-11-04-product-stage2-BUILD-SHEET.md` section 7 ("before any of these packages is built, it gets its own full build-sheet section and its own Sol review against PAR-1 and PAR-2 as built"). The Stage 2 sheet's section 3 rules all apply; this sheet names only where DM-2 adds to them. The review record is section 9.

**Goal.** Store how much a liquid weighs per gallon (one value per formulation) and how much one package of a dry product weighs, each reviewed before use, and show the crew the weight where they mix: the job's loader worksheet and the blend ticket. Fix the blend checker so a dry blend with liquid parts is a checked total (C-39). No saved record changes.

## 2. Corrections to the Stage 2 outline (section 7.1 and 7.8), from current code

1. **Nothing to group yet.** The outline assumed parents would exist; live has 0, and PAR-2's grouping switch is off. DM-2's mechanism can ship now; real weights wait for PAR-2's data step. Until a liquid size has a parent it shows "put this product in a parent to record its weight", as the outline said.
2. **No dry product needs a stored net weight today.** All 83 active dry products are stocked in a weight unit. The stored net-weight table is still built (a new dry product may be stocked in `Ea` or `Unit`), but its live use starts at zero, and DATA-4's dry list is empty unless such a product is added.
3. **Weight units are `Lb`/`LB`, `Dry oz`, `g` and `MG`**, read from `unit_conversions` (`unit_type = 'dry'`), not "lb, oz, kg". `oz` and `Oz` are fluid ounces in this database (`unit_type = 'liquid'`); DM-2 never treats them as weight. The app's existing converter (`fieldAppPricedQuantity`, `chemCalculator.ts:471-503`) lower-cases units, reads `oz` as a weight ounce for dry, and does not know `g` or `MG`, so DM-2 does **not** use it for weight; it uses the database's own factors (section 4.1).
4. **A count unit is `Ea` or `Unit`** (`unit_type = 'both'`). The outline's "bag, box" are container types, not stock units; no stock unit is called bag or box.
5. **The snapshot cannot ride on "the ticket's save RPC".** Three RPCs write ticket lines (`create_blend_ticket`, `save_blend_ticket`, `commit_blend_ticket_ocr_result`, the last called by the `process-blend-ticket` Edge Function), and `authenticated` still holds column `INSERT`/`UPDATE` grants with RLS write policies, so a direct API write is possible even though no screen makes one (section 3.4). So the snapshot is taken by a trigger at the line boundary, which catches every writer, as section 7.8's direction says.
6. **Key the snapshot by ticket and product, not by line.** `commit_blend_ticket_ocr_result` deletes the lines nobody corrected and re-inserts them; `save_blend_ticket` deletes lines missing from the save and inserts new ones. A snapshot keyed by line ID would be lost on those paths and re-taken at today's weight, changing a saved record. Keyed by (`blend_ticket_id`, `product_id`) and written "first time only, never changed", a re-saved, OCR-replaced or re-ordered line keeps the weight its ticket first used.
7. **Saved loader worksheets get their own snapshot, taken when the worksheet is saved** (7.8's round-8 item). `job_loader_worksheets` stores only plan settings and every product amount is recomputed from the job's lines, so there is no line to hang a weight on. DM-2 adds a per-(worksheet, product) snapshot written by a trigger on `job_loader_worksheets` (section 3.4b). The legacy loader (a job with no worksheet row) and the batch (master mix) summary are live views, labelled "current approved weights".
8. **There is no blend-ticket printout.** The outline said the ticket "prints" its weight. No per-ticket PDF exists; the only blend PDF is the ticket list export (`BlendTickets.tsx:200-222`), which has no quantities. The ticket screen shows the saved weight; no printout is added.
9. **The checker cannot check a spray tank with dry parts.** A gallon total with dry rows would need the dry product's volume, which no one records. Only a weight total whose unit is in the unit table (`Lb`/`LB`, `Dry oz`, `g`, `MG`, in any letter case) becomes a checked total, by converting liquid and package rows to pounds and then to the header unit through the database's factors. A `ton` or `kg` header (no row in `unit_conversions`) with liquid rows stays "not checked", with that reason. A spray tank keeps today's one-sided bound, and dry rows stay the one quiet exclusion, as today.
10. **Seed and each products never have a weight.** The outline did not say. They are refused by name ("weight isn't tracked for seed or each products"), and the checker's existing seed/each notice stays.
11. **The loader worksheet does not know which product a line is.** Its input (`LoaderProductInput`, `loaderWorksheet.ts:31-38`) carries only name, total and unit. The screen PR adds `product_id` and `product_form` to it at its two sources (`loaderWorksheetFetch.ts:65`, `:173-179`; `JobDetail.tsx:2392-2403`) and through `masterMixSummaryFetch.ts`; the outline's file list missed these.
12. **The outline's file list misses the PDF and fetch files.** `masterMixSummaryData.ts` only builds data; the batch PDF is `masterMixSummaryPdf.ts`, and its inputs come from `masterMixSummaryFetch.ts` and `chemicalApplicationReportFetch.ts`. Section 4 lists the real set.
13. **An admin's typed value is approved, not a draft.** The Stage 2 sheet's section 7 (`:319`) says a value an admin types on the product page is that admin's reviewed entry, and only agent-drafted or uploaded values land as drafts. The outline's "every value is a draft" is narrowed to match: the public setters save an **approved** value with who and when; only DM-1b's workbook (through the private helpers) saves drafts, which an admin then approves (section 3.3).

## 3. Database PR: migration `<stamp>_product_weights`

### 3.1 New tables

All follow the Stage 2 rule 2 lock-down (the snapshot table's read policy differs, below): RLS on, `SELECT` policy `USING ((SELECT public.is_active_profile()))` to `authenticated`, `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role, metabase_ro`, then `GRANT SELECT … TO authenticated` (the PAR-1 pattern, `20261108120000:184-199`). No write grant to any role. Owner `postgres`.

- **`product_parent_density_values`**: `id uuid` primary key; `parent_id uuid NOT NULL` FK `product_parents(id) ON DELETE RESTRICT`; `lb_per_gal numeric(10,4) NOT NULL CHECK (lb_per_gal > 0 AND lb_per_gal <= 25)`; `entered_value numeric NOT NULL`, `entered_unit text NOT NULL CHECK (entered_unit IN ('lb_per_gal', 'specific_gravity'))`; `source text NOT NULL CHECK (source IN ('measured', 'sds', 'label', 'supplier'))`; `source_note text` (trimmed, ≤ 1000); `review_state text NOT NULL CHECK (review_state IN ('draft', 'approved', 'superseded'))`; `reason`, `evidence` (only on corrections); `created_by`, `created_at`, `reviewed_by`, `reviewed_at`, `superseded_at`. - **`product_size_net_weight_values`**: the same shape per size: `product_id uuid NOT NULL` FK `products(id) ON DELETE RESTRICT`; `net_lb numeric(12,4) NOT NULL CHECK (net_lb > 0 AND net_lb <= 4000)` (the net pounds of **one stock unit**: one `Ea`, one `Unit`); no `entered_unit` (entered in pounds); the same source, review, who/when columns and the same two partial unique indexes.
- **`product_parent_density_state(parent_id uuid PRIMARY KEY` FK, `density_version bigint NOT NULL)`** and **`product_size_net_weight_state(product_id uuid PRIMARY KEY` FK, `net_weight_version bigint NOT NULL)`**. A missing row means version 0. Every write takes the row (`INSERT … ON CONFLICT DO NOTHING`, then `SELECT … FOR UPDATE`), checks the caller's expected version, and adds one. So two writers on one subject serialize on this row, and a stale screen is refused by name.
- **`product_weight_events`**: append-only (update, delete and truncate refused by trigger, as `product_parent_events`, `20261108120000:201-215`). `id bigint` identity; `subject_kind` in (`parent_density`, `size_net_weight`); `parent_id`, `product_id` (exactly one set, by kind); `event_type` in (`draft_saved`, `draft_replaced`, `approved`, `corrected`, `returned_to_draft`); `value_id`; `before_value jsonb`, `after_value jsonb`; `reason`, `evidence`; `actor_kind text NOT NULL CHECK (actor_kind IN ('user', 'system'))`, `changed_by uuid` and `changed_by_name text` (both nullable, as on `product_parent_events`): `auth.uid()` and `profiles.full_name` when a user is signed in (a profile with no name leaves the name NULL, never an error), or `actor_kind = 'system'` with both NULL when there is none (a service-role, migration or background update reaching the section 3.5 trigger); `changed_at`. Only the section 3.5 trigger can write a `'system'` event; every RPC requires an admin first.

If those ticket policies change later, this one changes in the same migration.

### 3.2 Reading the one approved weight

**Every new function** (readers, writers, private helpers, trigger functions) is created with an explicit security mode, owner `postgres`, `SET search_path = public, pg_temp`, and `REVOKE ALL ON FUNCTION … FROM PUBLIC, anon, authenticated, service_role` right after it is created (PostgreSQL otherwise lets `PUBLIC` execute a new function). Only the public RPCs named below then get `GRANT EXECUTE … TO authenticated`. "Private" in this sheet means that revoke and no grant, as PAR-1's helpers (`20261108120000:509-521`). The proof reads back every function's `prosecdef`, owner, `proconfig` and grants from `pg_proc`.

- **`_product_weight(p_product_id uuid) RETURNS jsonb`** (private, `STABLE`, `SECURITY DEFINER`). The one place every reader and the snapshot trigger resolve a size's weight:
  - `liquid`: the size's parent (`product_parent_members`), then that parent's `approved` density row. Returns `{kind: 'density', lb_per_unit: lb_per_gal, per_unit: 'Gal', value_id, source, reviewed_at}`. No parent: `none` / `no_parent`. Parent but no approved row: `none` / `no_approved_weight`. A draft beside it is ignored.
  - `dry` with a stock unit whose `unit_conversions.unit_type = 'dry'` (exact match on `unit_name`, as the database stores it): `{kind: 'unit_weight', lb_per_unit: factor_oz / 16, per_unit: inventory_unit}`. Nothing stored; the stock unit is locked once set, so this is the product's reviewed setup data.
  - `dry` with a count stock unit (`unit_type = 'both'`): the size's `approved` net-weight row, `{kind: 'net_weight', lb_per_unit: net_lb, per_unit: inventory_unit, …}`, else `none` / `no_approved_weight`.
  - `dry` with any other or missing stock unit: `none` / `unit_not_convertible`. `seed` or `each`: `none` / `seed_or_each`.
- **`get_product_weights(p_product_ids uuid[])`**: `STABLE`, **`SECURITY DEFINER`, owner `postgres`, `SET search_path = public, pg_temp`** (it must call the ungranted `_product_weight`), `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role`, `GRANT EXECUTE … TO authenticated`. It refuses a caller who is not `is_active_profile()` before reading anything; read-only, no key; at most 500 IDs. Returns, for each ID, `_product_weight` plus, for the screens that show review state, the current draft (value, entered value and unit, source, note, reason, evidence, who/when) and the subject's version; and once per call a `units` map (built by the private `_weight_unit_factors()`, which the snapshot triggers also use) from `unit_conversions`: every `dry` unit's pounds per unit (`factor_oz / 16`) and every `liquid` unit's gallons per unit (`factor_oz / 128`), keyed by `lower(trim(unit_name))`, because the checker and old OCR lines lower-case units. Live, every lower-cased name that appears twice (`Lb`/`LB`, `Qt`/`qt`, `oz`/`Oz`) has the same type and factor; if two rows ever share a lower-cased name with a different type or factor, that name is left out of the map (so it is refused by name, never guessed), and the proof checks this. No cost or price. Everything it returns is catalog data every active user can already read (`products`, `product_parents`, `unit_conversions`).
- **`get_blend_ticket_weights(p_blend_ticket_id uuid)`**: **`SECURITY INVOKER`**, `EXECUTE` to `authenticated` only (after the revoke above, so `anon` cannot call it). A plain read of the snapshot table **joined to the ticket's current lines** (only (ticket, product) pairs that still have a line in `blend_ticket_products`), so a deleted line's kept snapshot never reaches a screen or total. The snapshot table's office-only policy (section 3.1) decides what comes back: a user who cannot see the ticket gets no rows. Each row carries its own captured `unit_factors`.
- **`get_loader_worksheet_weights(p_worksheet_ids uuid[])`**: the same shape for saved worksheets (`SECURITY INVOKER`, at most 200 IDs), returning each worksheet's snapshot rows; the worksheet snapshot's policy decides access.

Every caller converts its own quantities through a `units` map (section 4.1): a saved record's own captured map, or the current map for a live view. So the database stores one basis per subject and never a pre-multiplied total, and the app and the database use one set of factors.

**Unit factors are treated as fixed.** `unit_conversions` factors are setup data; DM-2 reads them live for live views and new captures. A saved ticket or worksheet is unaffected by a later factor change (its snapshot stores `lb_per_unit` and the `unit_factors` it used). Any future migration that changes a `dry` or `liquid` factor must name its effect on DM-2 weights in its plan; DM-2 adds no runtime guard for it.

### 3.3 Writers

All `SECURITY DEFINER`, `SET search_path = public, pg_temp`, owner `postgres`, `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role`, `GRANT EXECUTE … TO authenticated`. Each one: `_product_parent_require_admin()` first, then `_product_parent_replay(p_idempotency_key, '<rpc name>', md5(request))` (so authorization runs before the replay lookup, a NULL key is refused, a repeat returns the first result, and the same key with a different request is refused), then the work, then `save_idempotency` last. This is PAR-1's pattern unchanged (`20261108120000:492-521`).

- **`set_parent_density(p_parent_id, p_expected_density_version, p_value numeric, p_unit text, p_source text, p_source_note text, p_idempotency_key)`**: the admin's own typed value, saved **approved** with `reviewed_by`/`reviewed_at` = the caller (correction 13). Refuses: a parent that is missing, inactive or not `liquid` (`PRODUCT_WEIGHT_NOT_LIQUID`); a stale version (`PRODUCT_WEIGHT_STALE`, naming the parent); a value out of range or non-finite; an unknown unit or source. Converts specific gravity once: `lb_per_gal = round(p_value × 8.345404, 4)` (`WATER_LB_PER_GAL`, pinned in the migration); a `lb_per_gal` entry is rounded to 4 decimals, half-up. **Trust order** (measured > SDS > label > supplier): a source lower than the approved row's source is refused (`PRODUCT_WEIGHT_LOWER_TRUST: the approved value is from the <source>; use Correct weight with a reason and evidence`). The trust order is checked against the approved row only; it is the same check in both public setters and both private draft helpers. The old approved row becomes `superseded`, an open draft (if any) becomes `superseded` too (a typed value replaces both), the version moves by one, and one `approved` event records before and after.
- **`set_size_net_weight(p_product_id, p_expected_version, p_net_lb, p_source, p_source_note, p_idempotency_key)`**: the same for one dry size whose stock unit is a count unit, with the same trust order. Refuses a size that is not dry (`PRODUCT_WEIGHT_NOT_DRY`) and a dry size stocked in a weight unit (`PRODUCT_WEIGHT_FROM_UNIT: "<name>" is stocked in <unit>, so its weight comes from the unit`), or with no stock unit.
- **`correct_parent_density(…, p_reason, p_evidence, p_idempotency_key)`** and **`correct_size_net_weight(…, p_reason, p_evidence, p_idempotency_key)`**: the same arguments plus a required reason and evidence (`_product_parent_reason`). The only way to replace an approved value with one from a lower-trust source. Saved approved, as above. Event `corrected`, with reason and evidence.
- **`approve_weights(p_items jsonb, p_idempotency_key)`**: approves drafts saved by DM-1b's workbook. Each item is `{kind, subject_id, draft_id, expected_version}`; at most 200 items; all or nothing. Locks every subject's version row in a fixed order (kind, then ID), checks each version and that `draft_id` is still that subject's draft, applies the trust order against the current approved row (a lower-trust draft needs its draft to carry a reason and evidence, saved by the helper), then for each: the old `approved` row becomes `superseded`, the draft becomes `approved` with `reviewed_by`/`reviewed_at`, the version moves, one `approved` event. A draft that has since been replaced, or a version that moved, refuses the whole call by name.
- **Private helpers for DM-1b's Weights tab** (`SECURITY DEFINER`, revoked from every app role per section 3.2, no key of their own; Stage 2 rule 3): `_save_parent_density_draft(p_parent_id, p_expected_version, p_value, p_unit, p_source, p_source_note, p_reason, p_evidence)` and `_save_size_net_weight_draft(…)`. They run the same checks as the public setters (form, unit, range, specific-gravity conversion, version) and save a **draft**: an open draft becomes `superseded` (`draft_replaced` event), the new one is inserted (`draft_saved` event), the version moves. DM-1b adds its own public RPC around them with admin check and key; DM-2 ships them unused.

- **`trigger_capture_blend_ticket_product_weight`**: `AFTER INSERT OR UPDATE OF product_id, blend_ticket_id ON public.blend_ticket_products FOR EACH ROW`, function `capture_blend_ticket_product_weight()` (`SECURITY DEFINER`, pinned `search_path`, owner `postgres`, no grant). It returns at once on an `UPDATE` where both `product_id` and `blend_ticket_id` are `IS NOT DISTINCT FROM` their old values (so `save_blend_ticket`, which re-sets `product_id` on every kept line, does nothing for an unchanged line). Otherwise, when `NEW.product_id` is set, it writes `_product_weight(NEW.product_id)` into `blend_ticket_product_weights` for (`NEW.blend_ticket_id`, `NEW.product_id`) with `INSERT … ON CONFLICT DO NOTHING`. **A snapshot row is never updated**, including a `none` row. So:
  - a ticket keeps the weight it first used for each product, through re-saves, OCR replacement, re-ordering, quantity edits and header-only edits;
  - a line moved to another ticket, or changed to another product, records the weight for its new (ticket, product) the first time that pair appears;
  - a later approval or correction never changes a saved ticket's weight;
  - a ticket saved before its product had a weight shows "no weight when saved" for that product, permanently (no saved record changes);
  - deleting a line leaves its snapshot (harmless; it is shown only for products the ticket still lists), and deleting the ticket removes them.
- A trigger is not a grant or policy change, so `blend_ticket_products` needs no `I approve`. A direct app write cannot skip it, and cannot write the snapshot table (no grant).
- **Live has 0 tickets**, so no back-fill is needed. The migration takes `LOCK TABLE public.blend_ticket_products IN SHARE ROW EXCLUSIVE MODE` first (it blocks inserts, updates and deletes but not reads, and is held until the migration commits), then refuses to apply if the table has any rows, then creates the trigger. So no line can be written between the check and the trigger. If a ticket was saved before the apply, the package re-plans a back-fill written with `captured_how = 'backfill_at_apply'`, which the ticket screen shows as "captured at DM-2 apply, original not recorded".

### 3.4b Saved loader worksheets keep their weight

- **`trigger_capture_loader_worksheet_weights`**: `AFTER INSERT OR UPDATE ON public.job_loader_worksheets FOR EACH ROW`, function `capture_loader_worksheet_weights()` (`SECURITY DEFINER`, private). For every distinct `product_id` on the worksheet's job (`job_chemicals` where `job_id = NEW.job_id`), it inserts `_product_weight(product_id)` with the current `units` map into `job_loader_worksheet_weights` for (`NEW.id`, product) `ON CONFLICT DO NOTHING`, except that a row recorded as `none` is filled when a weight now exists (`ON CONFLICT … DO UPDATE … WHERE weight_kind = 'none'`).

Unlike a ticket, a worksheet is a working plan, so a `none` row is filled (Mason question 1).
- A product on the job but not yet captured (added after the last worksheet save) is shown with the current approved weight, captioned "current approved weight; kept when this worksheet is next saved". Deleting the worksheet removes its rows.
- **Live has 1 worksheet row and 0 weights anywhere**, so nothing needs back-filling: that row is captured on its next save, and before then shows current weights with the caption. No lock is needed (a worksheet saved during the apply is captured on its next save in the same way).
- The trigger writes only the new table and reads `job_chemicals`, `products` and DM-2 tables; it never raises for a missing weight. `job_loader_worksheets` grants and policies are untouched (no `I approve`).

### 3.5 A changed pack returns its net weight to draft

`trigger_return_net_weight_to_draft`: `AFTER UPDATE OF container_size, container_type, container_unit, inventory_unit, unit_size ON public.products FOR EACH ROW`, function `return_net_weight_to_draft()` (`SECURITY DEFINER`, pinned, no grant). When any of those values actually changed (`IS DISTINCT FROM`) and the size has an `approved` or a `draft` net-weight row: an open draft becomes `superseded` (it was entered for the old pack); the approved row, if any, becomes `draft` again; the size's version moves by one (taking its version row as the writers do, so an in-flight approval of the old draft is refused as stale); and one `returned_to_draft` event records the changed values (actor per section 3.1, `'system'` when no user is signed in). ### 4.1 One shared helper: `src/lib/productWeights.ts` (new)

- `fetchProductWeights(productIds)` calls `get_product_weights` (through `src/lib/db.ts`, `assertRpcResult`), de-duplicating the IDs and sending them in chunks of 500, merging the results; `fetchBlendTicketWeights(ticketId)` and `fetchLoaderWorksheetWeights(worksheetIds)` (chunks of 200) call the snapshot getters. Results are keyed by `product_id`, never by position.
- `lineWeightLb(quantity, unit, form, weight, units)` returns `{ lb }` or `{ refused, reason }` with a plain message naming the product. `units` is the map from the RPC or the snapshot (section 3.2); the line's unit is looked up as `lower(trim(unit))`, the same key the map uses (`Oz` and `oz` are fluid ounces). It never guesses and does **not** use `fieldAppPricedQuantity` (correction 3):
  - **liquid** with a `density` weight, line unit a `liquid` unit: `lb = quantity × gal_per_unit[unit] × lb_per_gal`.
  - **dry**, line unit a `dry` (weight) unit, whatever the weight kind: `lb = quantity × lb_per_unit[unit]` (`Lb` 1, `Dry oz` 0.0625, `g` 0.0022046225, `MG` 0.0000022046225). So both live `MG` products work.
  - **dry** with a `net_weight` weight and the line in the stock unit itself (`Ea` or `Unit`): `lb = quantity × net_lb`.
  - Anything else is refused, with a reason that says what would fix it, from the weight's `none_reason` or the unit test: `no_parent` → "put <name> in a parent to record its weight"; `no_approved_weight` → "<name> has no approved weight yet"; `seed_or_each` → "weight isn't tracked for seed or each products"; a dry line in a fluid unit (`Oz`, `oz`, `fl oz`, `Gal`…) or a liquid line in a weight unit → "<name> is recorded in <unit>, which isn't a <weight|volume> unit"; any other unit → "<name>'s unit <unit> isn't in the unit table".
- `lbToUnit(lb, unit, units)` converts a pound total to a weight header unit through the same map (refuses a unit that is not `dry`).
- `sumWeights(lines)` returns a total only when **every** line has a weight; otherwise it returns `{ refused, reasons }`, and every screen shows "Total product weight not shown: <name> has no approved weight" (each reason) instead of a partial sum.
- Weights are computed unrounded and shown to 2 decimals (lb); a total is the sum of unrounded line weights, rounded once for display. No money is involved.
- Unit tests, hand-checked: 2.5 `Gal` at 8.3454 lb/gal = 20.8635 lb; 32 `Oz` of the same = 2.08635 lb; `LB`, `Lb` and `lb` all read 1 lb; specific gravity 1.15 saved as 9.5972 lb/gal; 50 `Lb` = 50 lb; 24 `Dry oz` = 1.5 lb; 1,000,000 `MG` = 2.2046 lb; 3 `Ea` of a 5-lb pack = 15 lb; a dry line in `Oz` refused (not 1 lb); and each refusal message.

## 7. Risks

- **A wrong or unreviewed weight reaching the loader worksheet.** Readers use only the approved row (one per subject, by index); a draft is never read; the proof shows a draft refused.
- **A saved ticket's weight changing.** The trigger writes first-time-only per (ticket, product), covers every writer including direct API writes, and the proof replays each route. A future writer that bypasses `blend_ticket_products` entirely (none exists) would need its own check.
- **The trigger blocking a ticket save.** It only reads products and writes one row; it never raises for a missing weight (it records `none`). The proof saves a ticket whose products have no parent.
- **Old browsers.** No existing screen or RPC changes behaviour; an old page simply shows no weights.
- **Unit spellings.** Weight conversion uses only `unit_conversions`, matched exactly; a fluid unit on a dry line (or the reverse) and an unknown unit are refused by name rather than guessed. The manual screen's unit picker already offers only `unit_conversions` names (`UnitSelect.tsx:35`); an OCR line in another spelling ("gallons", "lbs") gets no weight and the total stays "not checked" with that reason, as today. Rows the checker already converts keep today's conversion.
- **A unit factor changing.** Treated as fixed setup data (section 3.2); saved tickets keep their stored `lb_per_unit`.
- **Sibling packages.** DM-1's cost per lb of active reads DM-2's approved density and net weight through `_product_weight`; DM-1b's Weights tab saves through the two private draft helpers (section 3.3). Neither may read the value tables directly. Parallel migration PRs take distinct stamps and re-check the ledger at apply.

## 8. Questions for Mason

Each has a default the builder follows unless Mason says otherwise.

1. **A saved loader worksheet that had "no weight yet" for a product picks up the weight once it is approved, on the worksheet's next save.** A weight it already showed never changes (corrections only affect new sheets), as the Stage 2 rule says. Blend tickets are stricter: "no weight when saved" stays, because a ticket records what was mixed. **Default: accept this.** A worksheet is a plan the crew is still loading from, so a missing weight that becomes known should show up; a ticket is a record.
2. **Who may approve a weight.** **Default: any admin**, the same as other catalog data; no second approver. A weight an admin types is approved by that admin (the Stage 2 rule); agent-drafted weights wait for an admin's approval after your review. Each approval records who and when.
