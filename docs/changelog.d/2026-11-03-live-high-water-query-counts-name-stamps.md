## 2026-11-03 - Live high-water query counts ledger name stamps

- The create-migration skill, the run-loop command and the `scripts/next-migration-stamp.mjs` header now read the live high-water for `npm run next-migration-stamp -- --live <live high-water>` with `select greatest(max(version), (select max(m[1]) from supabase_migrations.schema_migrations s2, regexp_matches(s2.name, '([0-9]{14})', 'g') m)) from supabase_migrations.schema_migrations;` instead of a bare `max(version)`. The Product Master mission and the database checklist only rename the argument to `<live high-water>`.
- Why: `.claude/hooks/migration-ordering-lib.mjs` orders by the stamp in each ledger row's name (version only as a fallback), so a bare `max(version)` can sit below an applied migration. Taking the highest of every 14-digit run in any name and every version is never below the guard's bar, including names with a folder path or a doubled `<version>_<stamp>_` prefix.
- Read-only live check on 2026-11-03 (1104 rows, no name carries two stamps): bare `max(version)` `20261103132202`; highest name stamp `20261104130000`. A stamp picked from the bare figure could have landed below an applied migration.
